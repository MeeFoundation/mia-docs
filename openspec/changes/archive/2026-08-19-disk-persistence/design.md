## Context

A node's state is entirely in memory: the replicas and blobs sit in an in-memory redb backend, the endpoint takes a freshly generated secret key on every bind, and the runtime's own bookkeeping — which identities it hosts, which metadata pairs are open, which granted namespaces are bound — is built during the process and dies with it. Nothing about that is a limitation of the fork: the store it wraps is the same redb store on a file backend when told so, the persistent replica storage and the persistent default author are both already implemented and enabled by default features, and the endpoint builder takes a secret key. What is missing is the decision of where that state lives, and what a node does with it when it starts and finds it there.

The stand is what makes the question answerable. Until containers, a restart could only be imitated — a runtime dropped and another spawned in the same process — which proves nothing about a process that exits. A container can be stopped and started with its filesystem intact, and the harness that drives it already stops nodes; what it says today is that nothing restarts a stopped node, because a restarted one would be a stranger with a new node id.

Three facts about the code shape the design more than anything else. The private metadata directory is already the durable record of an identity's own state — its devices, the typed tickets to its own stores, and its connections — so a node that recovers one directory can reach everything else that identity has by reading it. The runtime already treats its own bookkeeping as rebuildable: the connection armer sweeps the directory's connection records and opens each metadata pair from its published tickets, and the grant binder imports whatever the counterparty's replica currently grants, both on a schedule rather than once. And the grant binder's unbind path is bounded to what that binder itself imported, which is why a withdrawal that lands while the node is off needs an explicit answer rather than an assumption.

## Goals / Non-Goals

**Goals:**

- A node configured with a directory keeps its replicas, blobs, author and wire key there, and comes back as the same node — same node id, same identities, same connections, same grants — with no ceremony repeated.
- Recovery reaches that state along the path the product already walks, so there is one description of what an identity has, not two that can disagree.
- The in-memory node stays exactly as it is and stays what the workspace's suites run on, named at the spawn site, so they neither slow down nor gain a temporary directory each.
- A withdrawal that happened while the node was off is honoured after it comes back, and the replica it withdrew is never served in the meantime.
- A restart is asserted where it can be asserted at all — on the stand, against a real process, after a clean stop and after a kill — with its denial beside it.

**Non-Goals:**

- A write-ahead log across stores. Recovery does not distinguish a clean stop from a kill: an acknowledged write commits within the stores' bounded settle window (the D11 finding), the node's own files are replaced whole, and both kinds of stop reopen through the same path. What stays out is completing a transition a kill cut between stores — an interrupted create or link is abandoned fail-closed as orphan replicas (D5), not replayed to completion, which is what a cross-store journal would buy.
- Encryption at rest, quotas, garbage collection of blobs, and any bound on how large the directory grows.
- Hardening against other accounts on a shared machine. Trusted-parent validation, symlink refusal, and re-checking the directory's identity after opening answer a multi-user host, and no deployment here has one: the embedded runtime lives inside an app sandbox and the stand inside a container, where the boundary is the platform's rather than the file permissions'. A server host with untrusted neighbours is its own change.
- Format versioning and migration. Nothing deployed holds data.
- Identity key material. The `PdnId` stays a random placeholder; the key that becomes durable is the node's wire key.
- Changing what the runtime services offer. Recovery uses the existing paths; it does not add an operation to any service.

## Decisions

### D1: Storage is an explicit spawn configuration with no default, and the host is persistent-only

`SpawnOptions` carries where the node stores its state, and the choice is required: memory by name, or a directory by name, with no unset form. Neither mode is a default because no caller wants one. The production consumer of the runtime is a mobile application that embeds it, and such an application must pass a directory inside its own sandbox — there is no path a library could invent for it. The workspace's suites want memory and say so at the spawn site. A default in either direction serves nobody and costs something: an implicit memory node lets a host promise persistence while holding everything in RAM, which from outside looks like a working node until its state is gone, and an implicit persistent node taxes every in-process test with a temporary directory and filesystem I/O.

The HTTP host exists for the container stand and is persistent-only: it reads `PDN_DATA_DIR`, passes the directory into the runtime spawn, and refuses to start when the variable is unset — the binary carries no invented path and offers no memory mode, because no consumer of the host wants either. The image sets the variable to its own data directory, so a container needs no per-node configuration: a container's filesystem is per-node already. Nothing below the host reads the variable.

The node's bind address is read from the environment inside the data layer (`PDN_BIND_ADDR`), and the storage location deliberately is not, for a reason that is about correctness rather than taste: the bind address is a machine-wide fact and every node in a process wants the same one, while a storage directory belongs to one node. The workspace's suites spawn several runtimes per test process; an environment-read directory would hand all of them the same path, where the second one to start meets the first one's exclusive file lock and the test fails for a reason that has nothing to do with what it tests.

Alternative considered: memory as the implicit default, which is the shape the code has. Rejected — the spawn sites are few and go through helpers, and the implicit form is exactly the one that lets a host run in memory while its operator believes it persists. Alternative considered: persistence as the default, matching what a deployment wants. Rejected — every existing test would then need a temporary directory and would pay for filesystem I/O, and the one thing the in-process suites are for is a fast inner loop. A deployment configures itself once; a test suite pays on every run.

### D2: One directory, and the wire key lives inside it

The configured directory holds four things: `docs/` for the fork's replica store and its persisted author, `blobs/` for payload bytes, and `node.key` for the endpoint's secret key. The node creates the directory if it is absent — with owner-only permissions, because the replica store inside holds namespace secrets and the blob store holds payload bytes in the clear, so the boundary sits on the directory rather than on the key file alone — reads the key if it is there, and generates and writes one with owner-only permissions if it is not. The key is written beside and renamed over, so a kill or a full disk mid-write cannot leave a half-written key; a key file that is present but cannot be parsed stops the start with an error naming it, because regenerating would silently change the node id — the exact failure this key exists to prevent.

The key is in the directory rather than beside it because the two are one fact. A node that persists its stores but not its key comes back holding a device record for a node id that no longer exists, tickets it minted that name an address nobody answers at, and peers whose contact list points at the same. It looks like a working node and is unreachable by everything it ever handed out — a worse failure than the honest empty one it has today, and one that a person cannot see from the outside. Keeping the key in the directory makes "persistent stores with a fresh key" a configuration that cannot be expressed rather than one that must be remembered.

### D3: One author per node, persisted with the stores

Each store mints its own author when it is constructed today, and store objects are constructed freely — a metadata pair reopened after a cache miss mints another. Nothing durable depends on that author's stability while everything is in memory. Once the replicas are on a disk it starts to matter in two ways. A key rewritten after every restart accumulates one live entry per author, so a node restarted a thousand times carries up to a thousand copies of each rewritten key, all of them live records in the replica and only the newest of them the answer. And the device set is read at record level: a device record written under one author and withdrawn under another leaves the withdrawn device present in the set, which turns a restart into a way of resurrecting a device that was removed.

So the node takes one author, and the fork already persists exactly that — the default author it keeps next to the replicas. Every store on the node writes with it; the runtime's provisional-write tracker recognises the node's own writes by the same one.

Finding, from implementation: of the two harms above, the accumulation is real and proven — the vacuity test fails the moment the author rotates — while the device-set resurrection does not occur through the current read path. Prefix deletion in the fork is scoped to the writing author, so a withdrawal written under a second author does leave the first author's record live in the replica, but the latest-per-key collapse selects the tombstone before empty entries are excluded, and the set reads the device as absent either way (verified by running the withdrawal scenario with per-start authors). The withdrawn-device test stays as a pin on exactly that query behavior: a read that excluded empties before the collapse would resurrect the device, and the test would catch it.

The cost is that a counterparty of two identities co-located on one node sees the same author id in both of their stores, which links them. That signal is already there in a stronger form: establishment publishes this device's node id into the store the counterparty reads, and it is the same node id in both. Co-located identities are not unlinkable to a counterparty of both today, and this change neither creates that nor closes it — closing it belongs with the trust-model question about what a multi-identity node is, along with the local read gate.

Alternative considered: one author per hosted identity, which would keep the two personas apart. It cannot be expressed: an entry write names the namespace's issuer and not the identity performing the write (`DataService::write(issuer, path, payload)`), so there is nothing at the call site to pick an author by. Giving the write path an "on whose behalf" argument is the same gap the trust-model question names, and it is a change of the service surface rather than a detail of persistence.

### D4: The hosted-identities file is the only thing written down

One file in the directory — `hosted-identities.json` — lists, per identity this node hosts, its `PdnId` and the namespace of its private metadata directory. Nothing else is recorded, because nothing else has to be: the directory is the identity's durable state (Invariant 1), so recovery opens it and reads out the rest. The data namespace comes from the `data` ticket, the connections from the `connections/` records, each connection's metadata pair from its two published tickets, and the granted namespaces from the counterparty's grants — every one of them through the mechanism that already exists for the identity's other devices.

Concretely, recovery per line is the tail of identity creation: open the directory replica the node already holds, register it for session classification, insert the hosted entry, start the connection armer. The armer's first sweep opens the pairs, each pair's binder imports what its grants name, and the node is back.

Alternative considered: record the whole picture — data namespace, pairs, bound grants — so a start does not depend on reading stores. Rejected on the operating conditions' own argument: a second bookkeeping of durable facts can disagree with the stores, and the disagreement is discovered by a decision that acts on it. The runtime already treats this bookkeeping as rebuildable and grounds destructive decisions in the grant records rather than in the memo; writing the memo to disk would be the first thing in the system to claim otherwise.

### D5: An identity is hosted when its line is in the file, and the line is written last

Creation provisions the store set, then writes the line, then registers and hosts. Linking imports the directory and the data namespace, completes its catch-up, then writes the line. A process that dies before the write leaves replicas nobody points at — inert, unregistered, and unserved, because a namespace nothing registers resolves to nothing. A process that dies after it leaves a fully provisioned identity that recovery picks up. There is no order in which a partially provisioned identity is hosted.

The file is never edited in place: every change — the first line, an added line, a removed line — writes a new file beside and renames it over. A kill or a full disk during the change therefore leaves the previous file intact and the operation failed: recording a second identity cannot lose the first, and a full disk at the commit point surfaces as a failed create or link rather than a truncated record. A file that cannot be parsed therefore means corruption, not a routine kill caught mid-write — which is what entitles the refusal below.

Hosting ends by removing the line, and the removal is the same commit point in reverse: what a later start does not read, it does not host.

An unreadable or malformed file stops the start with an error naming it. The alternative — start anyway, hosting nothing — produces a node that answers every request with "not hosted" while looking perfectly alive, which is the failure this change exists to avoid rather than one to add. An absent file is not an error: that is a node's first start.

### D6: A withdrawal that lands during an outage is honoured, and orphan replicas are named rather than collected

The binder's unbind path is bounded to what the binder imported in this process, so after a restart it holds nothing and can unbind nothing. That is not a hole, because of the order recovery produces: the pairs open from durable tickets, each binder's first sweep reads the counterparty's replica and imports what is granted there, and from that moment the binding is memoized again. A withdrawal written while the node was off is in the counterparty's replica and arrives on the first reconciliation after it comes back — into a binder that now has a binding to remove, which is the ordinary path.

Fail-closed holds throughout the gap: a granted replica's bytes are on the disk, but nothing registers its issuer until a live grant is read, and an unregistered issuer resolves to nothing on every read and every session. What survives an outage is bytes, not access.

What is left behind is a replica whose grant never comes back — withdrawn during an outage that outlasted the connection, or hosted by an identity that stopped being hosted. Those replicas keep their bytes on the disk and are never served. Collecting them is out of scope, and the reason is that a start cannot tell "no grant explains this" from "no grant has been read yet": the counterparty's own replica may be stale until it syncs, so a sweep at start that trusts what it sees would destroy the replica of a grant that is live. A collector belongs with a rule about when the evidence is complete, which is its own change.

### D7: One running node per directory, refused by name

The replica store takes an exclusive lock on its file, so a second node on the same directory cannot start. The node checks the directory and reports the refusal with the path and the cause, rather than letting a lock error surface from three layers down where it reads as a corrupt store. The demo gives every node a volume of its own, which is where this would otherwise be met by accident.

Finding, from implementation: the check cannot lean on the stores' own locks, because the blob store's open on a database another node holds hangs instead of failing — its error path shuts the store's internal runtime down from inside one of that runtime's own threads, so the failed open never returns (verified by a thread sample of the hung spawn; an upstream iroh-blobs defect, not the fork's). The node therefore takes an advisory lock of its own on a `lock` file in the directory, before either store opens: the second spawn is refused there, immediately and by name, and the stores' exclusive locks remain as the enforcement behind it.

### D8: The restart is a container restart, and its denial is a fresh directory

The stand stops a node's container and starts it again, which keeps the container's filesystem and therefore its data directory. The recovered node is asserted to be the same node — the same node id, the identity still hosted, the connection still listed, the grant still readable, an entry written before the stop still readable — and to need no ceremony to get there.

The scenario stops the node both ways: a clean stop, and a kill with no grace and no shutdown path. The operating conditions call the kill the ordinary end of a process, and the assertions are the same in both arms on purpose: recovery that differs by the manner of stopping would depend on the previous process having said goodbye, which is exactly what a kill does not provide. The kill arm waits out the stores' settle window before killing — the entry it asserts on must have committed, and the stores commit on a timer after the acknowledgement (the D11 finding); the mid-stream scenario is where the window itself is the subject.

One kill lands in the middle of a stream of writes rather than after them: every write acknowledged before the stores' settle window must read back after the restart, and a write the kill cut inside that window — acknowledged or not — must be absent or whole, never torn. The window exists because both stores commit after the acknowledgement, on a bounded timer (the D11 finding); the obligation asserted under fire is therefore bounded durability and no tearing, and it is the scenario the stress pass exists to hammer.

Its denial is in the same place, and it is what makes the assertion mean anything: a node started from the same image on an empty directory holds none of it. Without that arm the scenario would pass just as well if the recovered node had quietly re-created everything, or if the assertions were reading the harness's own memory of what it wrote.

One harness consequence: a container's published port is assigned when it starts, so the port a stopped container had is not the port it comes back on — and it may by then belong to another test's container. The harness re-reads the mapping after a start, and every URL it hands out afterwards comes from that read.

### D9: The demo keeps starting clean

Persistence makes state that outlives a run, and a demo that meets the previous run's state is the one thing a demo must never do. The compose file gives each node a named volume, and the teardown removes the volumes with the containers, so the show still starts from nothing. The image declares no volume of its own: an image-declared volume is created anonymously for every container that ever runs, which leaves a trail of dangling volumes on the machine and takes the decision away from the compose file that should own it.

The demo gains one step for what persistence buys: a node is stopped and started again mid-show, and the connection it holds keeps working with nothing re-established.

### D10: Operating conditions

Walked against `code-practices/operating-conditions.md`. Five conditions change the outcome here and are backed by scenarios; the rest are named and left.

- **The device restarts** — this is the change. Backed by the recovery scenario and its empty-directory denial (D8), and by the commit-point ordering (D5).
- **Capabilities move** — a grant withdrawn while the node is off, and a grant re-published over the same claim afterwards, both have to land on state that recovery rebuilt rather than on state it remembered. Backed by a scenario for the withdrawal during an outage, whose evidence is the counterparty's replica rather than the memo (D6). A grant narrowed or widened during the outage converges by the same mechanism — the binder imports what the counterparty's replica grants now and holds no memory of the old scope — so neither direction earns a scenario of its own.
- **The disk fills** — reachable for the first time, since an in-memory store fails by exhausting the process instead. The obligation is that the failure is loud: a write that the store refuses is reported as a failed write, not swallowed into a replica that reports itself converged. Backed by a scenario that gives a node a size-bounded filesystem for its data directory and writes until the store refuses. A full disk at a commit point — the key, the hosted-identities record — fails the operation and leaves the previous file intact, because both are replaced whole (D2, D5).
- **The process ends without warning** — the restart scenario's kill arm asserts that recovery after a kill is the same recovery as after a clean stop (D8), and an acknowledged write commits within the stores' bounded settle window (the D11 finding), so what was confirmed before that window is readable after the kill, and what was confirmed inside it is absent or whole. A ceremony in flight dies with the process and fails as any interrupted ceremony fails.
- **A write to several places is not atomic** — the node's own files are replaced whole rather than edited (D2, D5), creation and linking place the write that makes an identity hosted last (D5), and the order that makes an entry readable only once its payload landed belongs to the fork and is verified rather than assumed (D11). What a kill leaves between stores is an orphan replica, named, unserved, and collected by a later change (D6).
- **Several identities on one node** — the file holds several lines and recovery restores each, and the author decision touches co-location (D3). One scenario recovers two personas of one node, which is what makes "each identity comes back with its own connections" a property rather than a coincidence of testing one.
- **One device or several** — unchanged. A device's membership lives in the directory's device set, which is durable and replicated; a restarted device is the same device because its key is the same (D2), which is precisely what a fresh key would have broken.
- **A device links before, during, or after** — a link that completes is durable by D5's ordering, and one interrupted by the process ending leaves nothing hosted. A link cannot span a restart: the ceremony is a live dialogue with a short-lived secret, and a node that restarts mid-ceremony fails it, as it does mid-ceremony today.
- **The connection is unstable** — unchanged in kind. Recovery performs no dialogue and needs no peer: everything it reads is local. What comes after it is the ordinary reconnection path.

### D11: Nothing in the fork

Persistent replica storage, the persistent default author, and the exclusive lock are all in the fork already and enabled by its default features. If a task here cannot be done without a fork change, that is a finding of this change, not a task in it.

One property of the fork is load-bearing rather than merely configured, and is verified before a scenario states it: an entry and its payload live in two stores, so the readable order has to be payload first, entry last — a stop between the two must leave an entry that does not read as stored, never a stored entry whose payload never landed. If the fork commits the entry first, that too is a finding of this change.

Verified, with two findings. The readable order holds: the fork's write path stores the payload before it inserts the entry, and the data layer's read refuses to answer an entry whose payload is not in the blob store, so an interrupted write reads as absent, never as stored-but-empty. Durability at the acknowledgement does not hold, in either store, and both are findings rather than workarounds. The fork's replica store keeps one long-running write transaction and commits it on a timer (every 500 milliseconds), when a sync session opens (session setup takes a snapshot, which forces the commit), or at shutdown — ordinary reads commit nothing — so a kill can lose up to the last 500 milliseconds of acknowledged entries: a bounded loss back to the last commit, never a torn record. The blob store acknowledges a payload after its metadata table is updated but before the batched transaction holding that update commits, and it renames payload files into place without syncing them first — the same bounded-window shape against a kill, plus a power-failure exposure the page cache does not cover. The two stores commit independently, so the payload-first write order does not survive a kill inside the window: observed on the stand, a kill can commit the entry record while losing its payload, and the entry then reads as absent — fail-safe, but a locally unrecoverable absence until the path is written again or a peer holding the payload serves it. The fix for all of this lives in the write path of the store that defers — commit-on-acknowledgement or a durability knob — which is a fork change and therefore outside this change; the kill scenarios assert what the stores provide: writes acknowledged before the settle window read back, and newer ones are absent or whole, never torn.

## Risks / Trade-offs

- **Storage timing changes every scenario's margins.** A disk-backed store is slower than an in-memory one, and the stand's convergence budgets were sized against the latter → the workspace suites keep running in memory, so only the stand's own timings move; the change ends with a stress pass over the stand's suite, and any failure is diagnosed as a defect of this change rather than carried.
- **A session snapshot pins pages, and on a file that shows.** An open sync session holds a redb snapshot, so pages it references are retained until the session ends; on an in-memory store that is invisible, on a file it is growth → named here, measured by the scale work, and bounded by the session work that owns it. A node whose sessions all complete releases them.
- **Orphan replicas accumulate.** Withdrawn-during-an-outage and un-hosted identities leave bytes nobody serves (D6) → fail-closed by construction, unbounded in size, and collected by a later change.
- **The directory holds secrets in the clear.** Namespace secrets and the node key are files, protected by permissions and by whatever protects the host → stated, not solved; the threat model arrives with KERI key material.
- **A demo run that fails part-way leaves volumes.** The teardown removes them on every exit, the failing one included, matching what the recipe already does for containers → if a volume survives anyway, the next run's first symptom is state nobody wrote, so the teardown's coverage is a task rather than an intention.
- **Two nodes on one directory.** Refused by the store's lock and reported by name (D7); the demo's per-node volumes keep it from being met by accident.

## Migration Plan

None. No deployment holds data, so the on-disk layout has nothing to migrate from; a development machine that has an old directory removes it. The in-memory path stays available by name, so a caller that explicitly chooses it — a suite, a development flow — runs without a directory; the host is not such a caller and stops instead.

## Open Questions

- **Encryption at rest** — largely the platform's on a mobile host, where the operating system encrypts the app sandbox; what remains is the choice of protection class and hardware-backed key storage, which arrive with the KERI key material.
- **Backup and restore on a mobile host.** A cloud backup copies the directory, so namespace secrets and the node's key leave the device; a backup restored onto a second device is two live nodes with one wire key, which the exclusive lock cannot see across machines. Excluding the key from the backup makes a restored app a node that lost itself; including it makes a clone. The likely shape is product policy — a restore is a new device that links, not a resurrection — with KERI's duplicity detection as the identity-level answer; the wire key's answer is open.
- **When orphan replicas can be collected safely** — split by where the evidence lives. A replica this node provisioned itself is explained by local durable state alone — the hosted-identities record, the directories it names, their connection records — so the leftovers of an interrupted create or link are collectable at a start, after recovery and before admission; the safer shape is a marker written before provisioning and removed after the commit point, which names the garbage positively, rather than an unreachability rule, which breaks silently the first time a change adds a kind of replica the node holds for itself without extending the rule. What stays open is only the replica received under a grant, whose evidence is the counterparty's replica and may be stale until it syncs — the rule for "the evidence is complete", which D6 leaves open. The collector is its own change either way.
- **A create retried over computed namespace keys** — deferred to UWill, with the answer's shape sketched here. Today a retried create mints fresh namespace identifiers, so the leftovers of an interrupted create collide with nothing, and for identity creation that stays true under computed keys by consequence of the rules here: recovery never adopts orphaned key material, so a retry derives a fresh issuer and fresh namespaces — provided no identifier derived from abandoned material escapes the node before the commit point, which the D5 ordering ensures. The edge is real where the derivation inputs survive the kill: a namespace derived from an issuer that already exists, or a connection metadata store derived from the stable pair it serves. The sketch: the commit point of the owning record is the discriminator — present and recorded means a genuine error (an existing identity is linked, not re-created) or ordinary convergence through import, while present but unrecorded means the leftover of an abandoned attempt, which the create path replaces and the import path adopts. A per-attempt nonce in the derivation is rejected, because deriving the address from the issuer alone is the point of a computed key; a durable journal is not triggered, because the transition still collapses to one commit point.
- **Per-identity authors**, once an entry write can name the identity performing it. That would keep two personas on one node unlinkable to a counterparty of both, which D3 does not, and it is bound up with the same question as the local read gate.

## Costs, measured

The workspace's in-process suites are unchanged in wall-clock time: 149 tests in 149 seconds after the change against 140 tests in 146 seconds before it, and the difference is the 9 new persistence and recovery scenarios — every pre-existing suite still spawns on memory through its named helper, and no suite gained a temporary directory. The stand's container suite runs its 15 tests in about 12 seconds, level with the in-memory measurements recorded in the nextest configuration, so no convergence budget moved. The stress passes ran clean at 100 iterations of each: the two in-process suites (900 test runs, plus 300 more of the record-writer scenario alone) and the stand's suite (1,500 test runs). A demo node's state directory after a full show holds about 190 KiB — roughly 110 KiB of replica store, 60 KiB of blobs, and the record, key and lock files beside them.
