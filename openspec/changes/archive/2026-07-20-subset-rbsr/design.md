# Design: subset-rbsr

## Context

Invariant 2 says a node receives a claim only if it holds a read capability for it. Today reconciliation delivers every claim to any peer that syncs — no per-claim read control: the old ingest gate was removed by multi-identity-node, nodes host several identities, and access is bounded by ticket possession alone. This change enforces Invariant 2 by filtering what a serving node reveals during reconciliation, driven by the receiving peer's read capabilities — the read-side counterpart of the ADR-0008 ingest hook (the fork's `validate_entry`, available and uninstalled), and the first enforcement to land on that ungated baseline.

## Goals / Non-Goals

**Goals:**

- A serving node reveals only claims the peer is read-authorized for; unauthorized claims' content and existence stay hidden.
- A minimal, testable read-capability mechanism driving the filter.

**Non-Goals:**

- Full UWill (chains, revocation, token encoding) — ADR-0007.
- Efficiency — a filtered session may scan every entry in the replica; accepted.

## Decisions

### D1. Filter at reconciliation time, applied consistently

The filter lives in `pdn-store` at reconciliation time (the `ranger` path), as a per-peer predicate over which entries participate. It is new — the existing `validate_entry` hook is ingest-only. It MUST be applied uniformly: range fingerprints, split boundaries, offers, and item transmissions all computed over the filtered view. Partial application leaks — a fingerprint computed over the full set in a shared range would betray unauthorized neighbours.

### D2. Confidentiality = consistent filtering

Because every value the serving node sends is computed over the peer's authorized subset, the peer's transcript depends only on that subset. The peer's session is indistinguishable from reconciling with a node holding exactly that subset — so it learns neither content nor existence of the withheld claims. No PIO/ZK needed; this is "don't send it," enforced at the serving node.

### D3. Minimal read grant — the single-link precursor to UWill, scoped by claim ids

The capability the filter consumes is a single grant `{ issuer, audience, claims }`: the issuer whose replica it opens, the audience identity it is granted to, and the exact set of `ClaimId`s it grants read on — the same scope vocabulary as UWill's `res` (one claim per grant element, no prefixes or other geometry), so the grant's language never diverges from the format that supersedes it (ADR-0007). No delegation chain, no revocation crypto, no token encoding — the degenerate single-link form that UWill's chain validation later replaces. `ClaimId` is a `pdn-types` primitive, so the data layer speaking it breaks no layering.

**Interim claim identity — an explicit placeholder.** Until the PDN layer's gluing decides how claim identities are minted, the claim identity of an entry is derived deterministically: `ClaimId` = a domain-separated key-derivation hash of the issuer and the entry path (e.g. blake3 `derive_key` under a fixed context string; issuer is fixed-width, so the concatenation is injective). This deliberately takes the "derived" branch of the open fork "minted at creation vs derived from the attribute's identity": derivation keeps the id stable under value edits (a grant survives editing the shared claim — the load profiles depend on that) and computable from the entry key alone, which is what lets the filter evaluate with no mapping table (the ADR-0009 precedent against side indexes). Two costs are accepted knowingly: the id follows the path (relocating an entry changes its id, so a grant does not survive relocation — the same fragility a path scope would have had), and the id is invertible by a dictionary search over paths (claim-id topology is not hidden). If the domain later chooses minted ids, the derivation is replaced by runtime-side resolution above this layer and the grant type is unchanged; the filter then consumes a pre-resolved scope.

**Commands.** The grant carries UWill's command dimension in miniature: `read` is always granted — it is the only thing the egress filter consumes — and `write` is optional, mirroring uwill.md's flat command set. Granting `write` changes what the grant's ticket carries (D11), not the filter. The write side is not enforced by this change — write enforcement is the ingest hook's job (ADR-0008); until it lands, a write grant's authority is effectively whole-store and non-revocable, the accepted interim inherited from the write-tickets decision (D11 records both facts). The grant already carrying `write` per claim keeps issued grants stable across that later change.

**Evaluation direction.** The filter never resolves a `ClaimId` to a location. It checks membership in the reverse direction: for each entry key it derives the claim identity and tests it against the granted set. Reconciliation-time filtering therefore needs no id-to-location mapping in either future — derived or minted — and `pdn-store` stays domain-blind: the session filter arrives as an opaque predicate over entries, assembled by `data-layer`; the fork knows neither `PdnId` nor `ClaimId`.

Placement: the minimal type and the interim derivation live in `data-layer` for now; the domain issuance surface (`pdn-layer` `Capability`, then UWill) supersedes them later. The full comparison against path-scoped grants (and the rejected replicated mapping table) is recorded outside the spec tree; this design carries only the decision and its two accepted costs.

### D4. The replica's own devices are fully authorized

A device of the identity a replica belongs to is read-authorized for all of that replica's claims (composes with Invariant 1), so the filter admits everything for such a peer with no capability presented, and reconciliation between an identity's devices (the private-metadata directory, the data store) stays full. A connection metadata store extends the same whole-replica audience across the connection: the counterparty's devices read that replica whole by design (Invariant 3), so they too are fully authorized peers for it — the filter has nothing to narrow there, and capability-scoped reading applies to the data stores grants point at, never to the metadata channel that carries the grants. On a multi-identity node this is judged per replica, not per node: a node hosting several identities is a fully authorized peer only for the replicas of the identities it is linked into — plus its identities' connection-metadata `peer` replicas — and a capability-scoped peer for anything else it holds. How a peer proves being a device of the identity — today by its authenticated node id resolved through the published device sets, identity-bound proof with UWill — is answered by D8/D9.

### D5. Grantees are outside the swarm

The reconciliation filter alone does not enforce Invariant 2: live sync broadcasts full entries (`Op::Put(SignedEntry)`) and author-heads digests (`SyncReport`) to every swarm member. A broadcast cannot be filtered per recipient. The sender controls only its few active gossip neighbors (HyParView partial view — five by default); every further delivery is a relay performed by a swarm member outside the sender's control. A relaying member must hold what it forwards — Plumtree pushes full messages to eager peers and answers `Graft` requests with full content, and even the lazy path's `IHave` digests leak entry existence — so a capability-scoped relay would either obtain claims it is not authorized for (the exact transfer Invariant 2 forbids) or refuse to relay and tear the delivery tree, breaking delivery for fully authorized peers behind it. Filtering at every hop instead would require every member to know every neighbor's rights for every claim — distributing the access matrix, itself sensitive metadata, to the whole swarm. In short: a broadcast presumes members are interchangeable with respect to the topic's content, per-claim authorization breaks that premise, and membership is the only level at which gossip can be "filtered" without breaking the protocol.

Therefore the swarm consists of the replica's device sets only: the issuer's own devices, and, for a connection metadata store, the connection counterparty's devices too (Invariant 3). No grantee joins it: a capability-scoped member would break the broadcast premise above, and a whole-store grantee — fully authorized to read today — still must not be a member, for two reasons its authorization does not cover. Membership outlives revocation: sessions are classified when they start and broadcasts are never re-classified, so a member would keep receiving every entry for as long as it stays subscribed after the grant is withdrawn, while a reconciling grantee is re-judged at its next session. And membership relays: a member forwards full entries to whichever peers the topic's membership protocol pairs it with, and topic membership itself is unauthorized (see the enforcement-boundary risk below), so every member widens the very door that risk records. A grantee's only data path is the reconciliation it initiates — capability-filtered for a scoped grant, whole for a whole-store grant — which remains the single enforcement point and the sole carrier of correctness. A grantee that never reconciles simply never sees updates; reconciliation-on-contact is the baseline. Making that path prompt — a directed, content-free trigger to exactly the peers a written claim covers, coalesced per peer — is the separate `reconcile-trigger` change, a latency optimization on which correctness does not depend. D2's transcript property extends to that liveness path: a scoped peer is prompted only about claims it can read, so no side channel opens (the load profiles make the cost and the side channel concrete).

### D6. The filter is a session-scoped filtered store: snapshots for stability, views for speed

Three independent layers.

**Form.** A filtering adapter implementing `ranger::Store<SignedEntry>`, constructed at session setup from an entry source and the peer's rights, frozen for the session (rights changing mid-session would make the filtered view drift between rounds). The reconciliation engine is not modified and cannot read past the adapter — the trait is its only door to entries. Range fingerprints are filtered by construction: pdn-store computes them by iterating `get_range` (no cached aggregates — the fs store carries the upstream's own "TODO: optimize"), so filtering the iterators filters the fingerprints. This is the structural alternative to sprinkling a predicate through the reconciliation logic, where one missed call site would leak claim existence through a fingerprint.

**Source.** On the fs backend the entry source is a redb read transaction (`snapshot_owned` — already in the store's API, currently unused by reconciliation, which reads the current transaction): every session sees the data as of its start, fingerprints stay consistent across rounds, and MVCC makes this free of copying. The memory backend has no snapshot primitive and keeps the live store, with the same tolerance to mid-session drift the unfiltered engine has today (reconciliation is anti-entropy; drift heals next session). A snapshot buys consistency, not speed — iterating a snapshot costs the same as iterating the live store.

**Views, optional.** Where a profile makes per-fingerprint rescans expensive, a pre-filtered view is materialized and keyed by **audience** — the set of rights, not the peer: the SMB example's sessions fall into two audiences regardless of member count, and the sparse example's audiences are single-claim. The audience-resolution a covered write performs — the same index the reconcile trigger reuses (`reconcile-trigger` change) — doubles as the view's incremental invalidation. If implementation uncovers a reconciliation read path that bypasses `ranger::Store`, scoped sessions fall back to materialized views wholesale.

Two redb properties are verification items for implementation, not settled facts: long-lived read transactions pin old pages (so sessions must hold snapshots strictly within session bounds), and the store's `snapshot()` commits any open write transaction (its interaction with write batching needs checking).

### D7. When scoped peers reconcile — before access and on an interval

Since scoped peers pull, something has to trigger the pull. The baseline trigger — and, until `reconcile-trigger` lands, the only one — is self-initiated: a scoped peer reconciles a replica **before it reads from it**, and **on an interval** (hourly to start). That is what reconciliation-on-contact means concretely, and it suffices for correctness — a peer sees an update at the latest on its next read or interval tick. The cross-node push that prompts an out-of-schedule reconcile the moment a covered write lands is the deferred `reconcile-trigger` change; it lowers latency, never changes what a reconcile delivers. (The timer and the before-read hook live in the node runtime that drives reconciliation; subset-rbsr fixes the policy, not the scheduler.)

### D8. Rights come from the issuer's own records, not from wire presentation

The minimal grant has no signature and no token encoding (D3), so a grant "presented" by the caller could only be verified by comparing it against the serving node's own copy — presentation would add a wire-format change to the sync handshake without adding a bit of security. The serving node therefore evaluates rights from the grants its identity recorded: grants are published into the connection-metadata `own` stores, the issuer's devices replicate them, and at session accept the node reads the caller's effective grants from its own replica of that book. Nothing travels beyond what the transport already authenticates: the caller's node id (the QUIC handshake proves possession of the key) and the namespace named in the sync request — the fork's wire protocol is untouched. A device that has not yet caught up on a freshly issued grant serves less — fail-closed, healed by anti-entropy. Invariant 2's "can present a read capability" stays literally true: the audience holds its copy of the grant in its `peer` replica; the server just does not need the wire copy while both read one book. Presentation as a protocol arrives with UWill, together with the material that first makes it verifiable without trust — signed delegation chains the server cannot know in advance — and will be a wire change then in any case.

**The grant surface stops at the identity's own data.** Rights living in the issuer's own records draws a service boundary too: an identity can grant only the data it issues, because the book that would honor the grant lives with the data issuer's connections — a grant of a *foreign* issuer's data, recorded under the granting identity, is scanned by nobody and honored by nothing. Before the boundary the runtime published such grants successfully (its docblock even read as sanctioning it): the records replicated, the recipient read a live grant, enforcement denied every session — a silent no-op no layer reported. The connections service now refuses `identity != issuer` loudly with a typed error. This is an interim boundary, not a model decision: grants stay keyed by data issuer — exactly the shape delegation needs — and the boundary lifts when `UWill` chains make a foreign issuer's grant provable rather than merely asserted.

**One record per grant.** The grant book keys one record per (connection direction, granted issuer): `grants/<issuer-hex>`, its payload a width-tagged record — whole-store, or scoped with the capability inside. The two-slot layout it replaces (a ticket entry beside a capability entry) could not state its own consistency invariant: width was inferred from the capability's *absence*, so a capability whose blob had not yet replicated — or that a build could not decode — classified as whole-store, the exact opposite of the fail-closed rule above; a withdrawal was two tombstones whose replication order across devices was unconstrained; widening a scoped grant to whole-store left the stale capability masking the widening forever; and the two withdraw entry points could drift. One record makes those states unrepresentable: publishing either width replaces the record wholesale, withdrawing is one tombstone, and the classifier derives width only from a present, decoded record — absence, replication lag, and undecodable payloads all classify as *no grant*. The record's tag doubles as the structural format version: a future record kind reads as no grant on builds that predate it, which is the same fail-closed rule, not a special case.

### D9. Counterparty devices are resolvable through the connection metadata store

To classify a caller (D4) the serving node must resolve the caller's authenticated node id to "a device of identity X" — and nothing supports that today: a counterparty's directory is unreachable by Invariant 1, establishment records no peer node ids, and the calling device may never have been seen at all (pairing ran on the phones; the laptop calls). Each identity therefore publishes its device set into its own directional connection-metadata store: `devices/<node-id-hex>` records — the same shape and LWW/tombstone semantics as the directory's device records — written by the identity's devices next to the grants, read by the counterparty, exactly Invariant 3's audience. Publication is bilateral: each side publishes into its `own` store, so either side can classify the other's devices (the issuer classifies scoped callers; a scoped holder classifies the issuer's devices when they dial it back — D10). An identity is authoritative over its own device set — the same trust root as its directory; listing a foreign node id widens nothing, since an authorized audience can already leak what it received (Invariant 2's note). Linking a new device must propagate into every connection's `own` store, and revocation likewise — runtime orchestration over the directory's device records. KERI/UWill later makes the publication redundant (a PdnId resolves to its active keys); this is an interim with a clear sunset.

**Device-record revocation is an agreement, not an enforcement — deferred knowingly.** A tombstone cannot bind a device that still holds the store's write ticket: deletion in the fork is author-scoped and same-key conflicts resolve by wall clock, so a revoked-but-running device can always out-write the tombstone — and worse, the old machinery did it *deterministically*: every pair opening re-published the device record with a fresh timestamp, so revocation was undone by the next grant read on the revoked device. The deterministic half is closed: publication on pair opening is assert-once (a live record is untouched, a tombstone is never overwritten by opening; re-assertion is a deliberate act nothing calls today). The enforcement half is future work and stays named here: real device revocation is revoking write *authority* — namespace-secret rotation under UWill — and a per-identity author (narrowing the same-key race) rides that same change; until then no revocation surface is exposed, and the tombstone is a convention honest devices now keep by default.

### D10. Fail-closed serve model: no computable rights — no session

At accept, the node classifies the caller per replica (D4): a device of the replica's identity (its directory) → full view; the counterparty of a connection-metadata replica (D9) → full view of that replica; a counterparty device holding grants (D9 + the grant book, D8) → filtered session under the effective claim set; anything else → `Reject(NotFound)`, indistinguishable from the replica not being hosted here. Empty effective rights also answer `NotFound` — uniform with the true not-found case, so an unauthorized holder of a leaked ticket learns nothing, not even that the node holds the replica (the refusal philosophy of Invariant 3 and of the pairing dialogue's uniform refusal, carried to sync). A granted peer whose claims have no entries yet gets an honest empty filtered session — it is entitled to the namespace's existence. A node id published by several identities (one device hosting two of the caller's identities) resolves to all of them, and its effective rights are the union of those identities' grants — the consequence of Invariant 2 being deliberately node-scoped: isolation is per node, and any per-persona narrowing on the consuming node is that node's own concern, not the server's. Consequence: a scoped peer never re-serves its slice — it cannot compute anyone else's rights over foreign data (the grant book lives with the issuer), so its node answers `NotFound` for foreign replicas; re-serving returns with UWill delegation, when rights become presentable. The one exception falls out of the same rule: the issuing identity's own devices dialing a scoped holder back are classified through D9 and served in full — they are entitled to the whole replica anyway.

Three implementation realities, discovered while landing the change and kept deliberately. **Role-aware classification:** the access provider is told which end of the session it is judging. A scoped holder refuses callers it cannot resolve (`NotFound`, per this decision) but may still dial out with a *closed egress* — serving no entry of its slice while receiving whatever the callee's own filter admits; without the distinction a scoped node whose issuer never published a device set could neither serve nor pull. **Incremental arming:** enforcement is armed per identity by registration (`host_identity` / `host_connection`) and per replica by the scoped import; a replica the node's book knows nothing about stays in the legacy ticket-bounded mode. The pdn-node runtime registers everything it hosts, so product nodes are always armed — and ordering is part of that contract: device linking arms the identity the moment its directory is imported, *before* the data namespace is, and disarms on rollback — so the data binding never exists ahead of the book that judges its sessions, at the bounded fail-closed cost of refusing callers the still-converging directory cannot yet resolve. Bare data-layer assemblies that never register keep the pre-change behaviour — which is exactly what the same-identity suites exercise. Directory and connection-metadata replicas are never classified at all: they stay ticket-gated (Invariants 1 and 3, D4) — classifying them against their own, possibly not-yet-converged device records would deadlock the bootstrap that delivers those records. **The interim whole-store grant classifies as full:** a grant record naming whole-store width (the pre-scoped grant surface) is still a grant the issuer recorded (D8), of whole-replica width — so a resolved counterparty holding one gets the full view, while an out-of-band ticket with no recorded grant behind it now delivers nothing from an armed issuer: the first enforcement landing is exactly the death of bare-ticket handover. Width comes only from the decoded record (one record per grant — D8): a record still replicating, or one this build cannot read, classifies as no grant, so the whole-store view arms only once the record's payload has landed.

### D11. The grant's ticket carries exactly the granted authority: read → Read, write → Write

A scoped peer still needs the replica's ticket — the namespace id to name in the sync request and the contacts to dial — so the grant record carries the ticket alongside the capability; its `ShareMode` follows the grant's commands. A read-only grant ships `ShareMode::Read`: the holder cannot produce a valid entry at all (the fork's `Capability::Read` carries no namespace secret; local inserts fail with `ReadOnly`), so "cannot write" holds by construction, and read revocation is real — withdrawing the grant stops the filter admitting on the next session. A grant carrying `write` ships `ShareMode::Write`: the namespace secret is the interim carrier of write authority — the scenario "the issuer shares a claim for writing, the audience writes it" stays reachable, and the audience's writes travel back over the same bidirectional reconciliation it initiates (the writer stays outside the swarm, D5). Two interim facts are inherited knowingly from the write-tickets decision that preceded this change: until the ingest hook lands (ADR-0008), a write grant is effectively whole-store on the write side (the secret does not scope to the granted claims), and write authority is not revocable (a secret, once known, is known). Both now attach only to audiences the issuer deliberately granted `write` — read-only audiences no longer carry them. The ingest hook later narrows writes to the granted claims and makes write revocation effective, consuming the same grant; the type does not change. Once the ingest hook is the enforcing mechanism, degrading the record's ticket to "always a write ticket" becomes acceptable if it simplifies anything: the secret stops being the write authority — the hook is — so the mode distinction stops carrying security. Until then the mode split stands: it is what keeps read-only audiences unable to write at all.

## Risks / Trade-offs

- **[Consistency discipline]** The filter must touch fingerprints + boundaries + offers + sends uniformly; any path over the unfiltered set leaks. Test the existence-hiding property explicitly.
- **[Side channels]** Timing and message sizes can leak the replica's total claim count (the server scans every entry to filter). Minor; note, don't block.
- **[Efficiency]** A filtered session may cost time linear in the number of entries rather than logarithmic — accepted; performance is not a goal here.
- **[Enforcement boundary: gossip join — closed for data namespaces, open for directory and connection-metadata replicas]** A replica's gossip topic id equals its namespace id, and iroh-gossip does not authorize topic joins — any holder of the namespace id (every ticket carries it; every synced entry reveals it) can subscribe to the topic. Two things used to leak to such a subscriber: the swarm's full-entry broadcasts, and — for a directory or connection-metadata replica — the content a follow-up reconciliation serves (those replicas classify `Full` for anyone who can name them, D10). The **content-free swarm** now closes the first for *every* replica: the fork broadcasts a content-free author-head announce (`Op::SyncReport`) on a local insert instead of the entry (`Op::Put`), and drops `Op::Put` on receipt, so the topic carries only "I have news" digests and the content flows solely over the classified reconciliation the announce triggers (each hop re-announces after it pulls — the existing sync-report cascade). For a **data namespace** this shuts the subscriber out: the reconciliation is gated (D10 answers `NotFound` to an unresolvable caller), so a topic subscriber now gets only activity metadata (author heads, timing), never keys, hashes, or values. For **directory and connection-metadata** replicas the announce still triggers a reconciliation that classifies `Full`, so their content still flows to any id-holder over sync — the content-free swarm removed the broadcast half but not the sync half. Identity-bound session authorization on those channels — deferred to UWill (D8/D9) — is what closes them; until then their confidentiality rests on namespace-id secrecy (the ticket-possession posture, D4), honest-stack discipline of the same category as this note. Two residuals stay named: the activity-metadata a topic subscriber still sees, and `Op::ContentReady` — a bare content hash still broadcast as a fetch hint, leading to the ungated blob provider (the blob-egress-by-hash gap, deferred), left untouched here by decision.
