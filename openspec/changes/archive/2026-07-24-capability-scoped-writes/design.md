# Design: capability-scoped-writes

## Context

Write authority over a granted data namespace is the namespace secret: a grant carrying write ships a `ShareMode::Write` ticket, so the audience can produce valid entries for every claim of the store, and the authority survives withdrawal — a secret, once known, is known. This is the accepted interim recorded in subset-rbsr D3/D11, and the data-layer scenario `write_grant_round_trips_while_reads_stay_scoped` pins it: an assertion deliberately states that an out-of-scope write is accepted, with instructions to flip it when the gap closes. The fork's ingest hook (ADR-0008) — the one chokepoint both ingest paths call — is available and uninstalled, and today it receives the entry alone: the session peer stops one call frame above it. The read side is already enforced per session by the egress filter; the classifier resolves the caller's node id to an identity through published device sets and reads the effective grant from its own records. Two further fork facts shape this design: an entry rejected at ingest is dropped and never remembered, so the sender's reconciliation re-offers it every session; and local inserts skip the hook entirely, so a grantee holding the secret can always populate its own replica.

## Goals / Non-Goals

**Goals:**

- One connection can carry mixed rights: a claim granted read-only next to a claim granted read-write, in one grant record.
- The issuer's devices admit a granted counterparty's writes exactly on the granted claims; everything else is turned away before persisting, and withdrawal makes the refusal effective from the next session.
- A writer whose entry is not accepted — malice, a withdrawal race — is not broken forever: the issuer's gate signals the refusal back to the writer, which retracts the entry at once, the replica returns to the issuer's accepted state, and the outcome is observable (log and event), never silent.
- A minimal, deliberate fork wire change: the issuer's ingest refusal rides back to the sender on the reconciliation reply (an in-band rejection), beside the local hook signature and physical retract operation. The earlier goal of a wire-frozen fork is lifted on purpose — both ends are our own build, and the fork is a bounded, replaceable dependency rather than a fixed substrate.

**Non-Goals:**

- Cryptographic write scoping. Producing a valid entry keeps requiring the namespace secret — the accepted stance since the fork was chosen; author-delegated entries are UWill's question (proof-of-authorship placement, open in uwill.md).
- Per-identity authors. Author keys stay node-local; the gate judges by session peer precisely so no author-to-identity mapping is needed (subset-rbsr D9 defers that mapping to UWill).
- Secret rotation after withdrawal, the recovery surface for retracted payloads (the marker is its seed), and any tightening of the fork's timestamp window (a recorded knob, off).

## Decisions

**D1 — Per-claim commands inside the one grant record.** The capability's claim set becomes a list of pairs — claim id plus whether write is granted alongside read — keeping read always granted per claim, mirroring UWill's per-claim command list (one delegation per claim, `cmd` beside it). The one-record-per-issuer keying and the one-tombstone withdrawal are untouched (subset-rbsr D8): mixed rights live inside the record, so no ordering of separate read and write records can ever be observed half-withdrawn. The ticket mode follows the record as a whole: any write in the record ships a write ticket, none ships a read ticket. The alternative — a second record for write — was rejected for exactly the consistency argument that produced the single record. The payload shape change is fail-closed by construction: the tagged decoder reads unknown shapes as no grant, so live grants are republished rather than migrated.

**D2 — The gate is peer-keyed, not author-keyed.** The fork's ingest validator learns the session origin (the transport-authenticated peer already present at the chokepoint) and stays a local, synchronous predicate. Judging by entry author instead was rejected: author keys are node-local, one runtime author writes for every identity the node hosts, no author-to-identity resolution exists anywhere, and publishing one would pull per-identity authors forward against subset-rbsr D9. The session peer is the same signal the read side already resolves through published device sets — the two directions of enforcement key on the same identity evidence.

**D3 — The write set is a per-session snapshot deposited by the classifier.** The validator runs synchronously inside the insert path; grant reads are asynchronous store reads. The session classifier — already asynchronous, already consulted for both session roles before any entry flows — computes the caller's write set alongside its read set and deposits it keyed by replica and peer; the validator consults the snapshot. Rights are thereby frozen per session for writes exactly as they are for reads — one semantics, one window.

**D4 — What the gate admits, and where it is armed.** On a replica data-bound to a hosted identity: a peer resolving as the issuer's own device is admitted in full; a peer resolving as a granted audience device is admitted exactly on entries whose derived claim identity is in the session's write set; every other peer's entries are turned away. The gate arms only there. Directories and connection metadata stores stay ungated (ticket routing is their mechanism, Invariants 1 and 3). A grantee's own replica of a foreign namespace is not write-gated — its inbound entries are already bounded by the serving side's egress filter, and gating them by write set would reject the read slice a sibling legitimately relays — but it does refuse entries named by a retraction marker (D6), the narrow second duty of the same validator. An unregistered replica admits as it serves: whole, bounded by ticket possession — the read side's existing stance for a node that registers nothing.

**D5 — A foreign write is provisional until the issuer keeps it; refusal is signalled, not inferred.** Acceptance is locally unobservable — an accepted and a refused write leave the writer's replica identical — so the issuer's gate says so: when it refuses an entry at ingest for lack of a write capability, it returns the entry's identity (author, path, timestamp) to the sending peer on the same reconciliation reply, an in-band rejection carried by the minimal fork wire addition. Only that one reason is signalled, so the injected gate is three-valued: accept, refuse silently, refuse and signal. A signature or timestamp-window failure is transient and self-heals, and a refusal that is the receiving node's own state — a live retraction marker, a peer whose session it cannot resolve, records it cannot read — says nothing about the sender's authority; signalling either would make an honest writer destroy an entry it holds legitimately. The gate signals only an entry its own replica does not hold, so a rejection means "the issuer lacks this entry" rather than "the issuer dislikes it": an entry admitted in an earlier session stays, refused silently however the grant reads now. Narrowing a grant is the case that makes this bite — the narrowed egress hides the already-accepted entry from the session's view, so the audience re-offers what the issuer keeps, and signalling there would destroy the audience's copy of data both sides hold. The writer, receiving a rejection from a peer that resolves as the issuer's own device (the same published-device-set resolution the read side uses) for one of its own authored entries, retracts that entry at once — deterministic, one session, no counting. A rejection from any other peer, or for an entry the writer did not author, is ignored: a forged rejection cannot make a writer discard data it holds legitimately. The rejection's fields are the refusing peer's word, and retraction is irreversible, so the writer confirms the name against its own replica before judging — author, path, timestamp and content hash must match a record it holds at that moment. A fabricated timestamp thus addresses nothing (it cannot arm a removal for every future write at that path), and a version already replaced by a newer own write is not the one the rejection judged. A lost rejection self-heals: the refused entry stays in the set difference and is re-offered next session, carrying the rejection again — re-offering is the transport's own retry, never a signal the writer counts. The rejected alternative — inferring the verdict by counting re-offers to a threshold — was dropped: it mis-fires on a multi-device issuer (an accepted write propagating once to each of several devices reaches the count with no refusal at all) and keeps a per-write accounting that never fully drains.

**D6 — Retraction is physical removal plus a replicated marker, alive only while its entry can be.** A tombstone is not a retraction: it is one more entry the gate refuses, and it shadows the issuer's truth locally — a newer empty entry wins last-write-wins — instead of restoring it. The refused entry is physically removed from the local replica — a new local fork operation — after which the set difference disappears and the issuer's entry is the latest for the path again. Removal alone does not stop a sibling that still holds the entry from re-offering it, so the verdict replicates as a marker in the identity's directory (the private metadata store): key `retractions/<issuer-hex>/<author-hex>/<path>`, bounding timestamp inside, addressing that author at that path up to the bound — one live entry per author and path exists at a time, so the bound also covers a value rewritten while the marker travelled, and a newer own write dated above the bound is never matched. Each device acts on the marker: remove locally, refuse re-ingest of matching entries. With the issuer's rejection signalled (D5) the marker is an accelerator and a durability aid, not a correctness requirement — every device that reaches the issuer earns its own rejection, and the marker only compresses the window for a sibling that holds the entry but has not itself reached the issuer (catch-up while the issuer is offline). The node id, content hash, and timestamp the marker carries are provenance for the event and a future recovery surface, never matching material. A marker is dropped once the entry it addresses is provably dead — superseded by a newer entry at that author and path, or aged out by a retention window (a coarse proxy for the same) — and in bulk when the granted namespace is forgotten. Restoring write on the claim does not drop the marker: a re-grant does not retroactively validate the old refused entry, and it removes the issuer-gate backstop — the issuer would now accept that entry if a sibling flapped it back — so until the entry is superseded or aged out the marker is the only thing keeping a believed-dead value from resurrecting on both sides. Two cases pin the rule. Partial withdrawal: the issuer narrows a claim from read-write to read-only, a racing write is refused, retracted, and marked, then the issuer writes that path itself — because the marker addresses only the writer's author, the issuer's entry (another author, a newer timestamp) reaches the audience unaffected and is read; the marker is not reaped by forgetting, since the namespace is still granted for read, and ages out by the retention window. Re-grant: the issuer restores write on the claim and the marker still does not drop — only a later legitimate write that supersedes the old entry, or the retention window, drops it.

**D7 — The verdict is loud.** Retraction emits a `tracing` warning and a runtime event — a subscription stream in the style of the existing change streams — carrying issuer, path, author, timestamp, content hash, and the deciding device. The marker is the durable half of the same record. The payload blob itself is not copied anywhere: it remains in the blob store as long as the store lives, and a recovery surface over marker plus blob is deliberately left to the retention work.

**D8 — The writing surface refuses out-of-scope writes up front.** A write addressed at a granted (audience-postured) namespace is checked against the local grant record's write set and refused before touching the replica when the claim is not covered. This is a courtesy to honest writers — the error arrives at the call site, not as a rejection round-trip later — and it is not the enforcement: the gate at the issuer is, and the scenario tests probe the bypass explicitly.

**D9 — The last-write-wins window is documented, not narrowed.** An admitted write competes with the issuer's own entries by per-path last-write-wins, and the fork admits entries dated up to 10 minutes ahead of the receiving clock, so a write-granted audience can date an entry forward and hold the path against the issuer's same-clock writes for up to 10 minutes, repeatably. Recourse today: withdraw the grant and outwait or outwrite the pinned timestamp. A stricter bound for gated foreign writes is a one-line policy in the same validator — recorded as a knob and left off: no data on honest clock skew, and retraction makes a future tighter bound survivable (a bounced honest write self-heals observably instead of wedging).

**D10 — The pinned scenario flips, and the target scenario lands at the runtime surface.** The data-layer scenario that asserts the out-of-scope acceptance becomes the write-denial pair it stands in for. A runtime scenario exercises the shape the change exists for — one claim read-only beside one claim read-write over one connection: the read-write claim round-trips through the audience's write, the read-only claim refuses at the audience's API, the forced bypass never reaches the issuer and is retracted at the writer on the issuer's rejection — its event observed — and the read denials stay with the existing scenarios per access-control-tests.md.

## Risks / Trade-offs

- [A rejected entry re-offers until the writer retracts] → the issuer's in-band rejection retracts it in one session; re-offering persists only as the transport's own retry when a rejection is lost, and self-heals on the next session; a hostile writer can mint fresh entries and re-trigger a rejection each time, so the noise is bounded per entry, not per actor — session-level rate limiting is separate work.
- [Retraction discards honest input, a withdrawal race being the honest path into it] → accepted and stated: the event and marker carry the full address of what was lost, the application layer decides whether to re-offer it to the user; the store itself returns to the issuer's accepted state.
- [A false verdict when the issuer restores from backup and genuinely lost an accepted write] → the writer retracts and both sides converge on the issuer's restored state — consistent with the rule the mechanism enforces: in a namespace issued by X, X's kept state wins.
- [Per-session write-set snapshot goes stale within a session] → the same per-session freezing the read side already accepts; the window closes at the next session setup.
- [The secret stays known after withdrawal] → the gate refuses the withdrawn audience's next session, so new writes stop landing; the residual authority is inert against armed issuer devices and dies for good with secret rotation under UWill.
- [Gating could break device bootstrap or sibling catch-up] → the gate arms only on replicas data-bound to a hosted identity (D4); directories, connection metadata stores, and grantee-held replicas keep their existing admission, so linking and sibling serving are untouched.
- [Marker matching could suppress a legitimate entry] → a marker addresses one author at one path up to a timestamp, written only by the identity's own devices into its own directory (Invariant 1); the issuer's entries carry other authors and never match, and the marked entry is one the issuer does not hold, since a rejection names only an entry the refusing replica would newly store.

## Open Questions

- None blocking. The marker retention window is a constant with the same injection posture as the reconcile interval, and the marker drop rule — superseded, aged out, or the namespace forgotten, never a bare re-grant — is decided above; both are values a later change can revisit without shape changes.
