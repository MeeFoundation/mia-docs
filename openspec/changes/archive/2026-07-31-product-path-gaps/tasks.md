## 2. Issuer contacts for granted replicas (`pdn-node`)

- [x] 2.1 `connections.rs`: the grant sweep adds the counterparty's published devices to the granted replica's contacts, beside the audience siblings it already adds; the read of that set is the one the retraction tracker already performs, so no second read of the pair (D1)
- [x] 2.2 Re-derived per sweep, never stored; a withdrawn device drops out because the published-device read excludes tombstones — asserted, not assumed
- [x] 2.3 Scoped to the pair the grant came through: a second counterparty's devices never reach this replica's contacts
- [x] 2.4 The issuer's device set unioned across every pair whose grant binds this issuer, as the siblings already are — and fed to the retraction tracker from the same read, since its set is keyed by the same shared replica

**The union covers both sides of the shared replica, not only the siblings (2.4).** The several-identities walk caught the sibling half first and left the issuer half reading one pair — the one whose binder woke — and replacing the whole list with it. Since the pairs replicate on their own, their views of the issuer's device set differ while one lags, so each binder's sweep undid what the other established. The same read feeds the retraction tracker, which is keyed by the replica too, so the shrunken set there left a rejection unhonored and a provisional write standing. Both now derive from one union over every pair bound to this issuer. The consequence is stated in the delta rather than left implicit: a device leaves the contact set once no bound pair publishes it, not at the first withdrawal — the replica is one, and while any bound pair still names the device it is a live route to the same bytes. Pinned by `an_issuer_device_leaves_only_when_no_bound_pair_publishes_it`, which withdraws in one audience's pair and requires the device to stay, then withdraws in the other and requires it to go; with the single-pair read restored it fails on the first of those and the other seven reachability scenarios still pass.

**Deviation from the Impact section: `data-layer` is touched after all.** "A withdrawn device drops out" is not expressible over the add-only contact surface — a contact once added never left — so `add_namespace_contacts` became `set_namespace_contacts` (its only caller was this sweep): the sweep derives the whole set — the grant ticket's addressing for devices the issuer still publishes, the issuer's published devices, the audience siblings — and replaces the tracked list with it. Observation for scenarios rides a new `test-util` feature (`SyncNode::namespace_contacts`, surfaced as `RuntimeDataService::contacts_of`), absent from product builds; it hands back device ids rather than the tracked addresses, so what the observation returns is nameable through `pdn-node`'s own re-exports and a host needs no `data-layer` dependency of its own to hold it. Walking `code-practices/operating-conditions.md` also caught the several-identities-on-one-node case: two hosted audiences granted by one issuer bind one replica, so the derived set unions every bound audience's siblings — a per-identity set would have each binder's sweep strip the other's. The engine-side residue is recorded in the delta: the sync engine's own record of once-useful peers may redial a withdrawn device until it ages out, so the guarantee is "leaves the contact set", not "never dialed again".

The unreachable-inviter probes dial a live bare node rather than the address of a node that is gone: a bare node accepts neither ceremony ALPN, so the handshake is rejected in about 2 milliseconds and the marker's absence is asserted outright. The address of a departed node costs the transport's whole connect timeout — measured at 30 seconds on loopback — so a probe that bounds its wait below that never reaches its assertion at all, and asserts nothing while appearing to. The timeout-is-not-the-refusal probe lives in the rollback test, which owns the dead-ticket harness.

## 5. Arrange by the product path (`pdn-node` tests)

The rule these apply: an arrange or act step reaches a namespace the way the product reaches it. A hand-made ticket handover is admissible only where the out-of-band path is the subject of the test, or where it is the negative control the access-control practice requires — never as a shortcut to a state a grant would have produced (D5).

- [x] 5.1 [establishment.rs:83](../../../../crates/pdn-node/tests/establishment.rs#L83): drop the manual `import` after the grant is read — the binder imports what the grant names, so the assertion that follows becomes a test of the grant path instead of the import route
- [x] 5.2 [scoped_grants.rs:118](../../../../crates/pdn-node/tests/scoped_grants.rs#L118): the same for the scoped grant; the leaked-ticket import at line 134 stays — it is the ticket-holder-without-a-grant control
- [x] 5.3 [linking.rs:571](../../../../crates/pdn-node/tests/linking.rs#L571): the rollback test's premise — a granted namespace present on the laptop — set through the grant instead of a hand-made import, so what the rollback must not destroy is what the product would have created
- [x] 5.4 [linking.rs:804-805](../../../../crates/pdn-node/tests/linking.rs#L804-L805): now expressible — the grantee arranged through its recorded grant, and the serving device isolated by taking the other one offline, as [sibling_serving.rs](../../../../crates/pdn-node/tests/sibling_serving.rs) isolates its own. The outsider's ticket at 806-807 stays as the control. If something still pins it to a hand-made ticket, keep the ticket and name the reason in the test's docs — an admitted instrument, not a silent shortcut
- [x] 5.5 [data.rs:81-82](../../../../crates/pdn-node/tests/data.rs#L81-L82) untouched: the bare out-of-band ticket is that test's subject, and the core spec's out-of-band scenarios rest on it
- [x] 5.6 Every rewrite checked against a deliberately broken binder and confirmed to fail there
- [x] 5.7 The rule written as a new entry in `openspec/specs/code-practices/` — arrange through the product path, hand-made setup only as subject or control, `sibling_serving` as the worked example

5.4 resolved the design's open question: nothing pins the sibling-serving variant to a hand-made ticket for the grantee. Bob rides his binder-imported grant; the serving device is isolated by shutting the phone down and probing an update written on the laptop alone; Carol's laptop-minted ticket stays as the one admitted instrument (the outsider control needs addressing to the serving device and has no grant to carry it), named in the test's docs. Broken-binder check: with the binder's import disabled, all four rewritten scenarios fail (0 of 4 pass); restored, all pass. ## 7. Gates

- [x] 7.1 `just check` and `just test` green
- [x] 7.2 Stress pass per [flaky-tests](../../specs/code-practices/flaky-tests.md): the reachability scenarios and the rewritten suites under `--stress-count`, sized by the rule of three. - [x] 7.3 `openspec validate --all --strict` before archiving

**Stress finding (30-Jul-2026, first pool).** 1 failure in 50 iterations of the five affected binaries: `a_regrant_after_withdrawal_rebuilds_the_contact_set`, final wait starved — the audience never converged after the publisher shut down. Localized: the serving laptop classifies by the grant record in its own replica of the pair store; the re-grant was published on the phone moments before the shutdown, and the record's broadcast is best-effort, so about 2% of runs killed the phone before the record crossed — after which the laptop refuses the audience fail-closed and no reconcile contact backstops the pair store (its tracked contacts name the establishing devices alone; the gap is now named in the proposal's out-of-scope list). Fix in the arrangement, not a stretched wait: the undetermined premise — "the surviving device holds the record it will serve by" — became an explicit wait on a new `test-util` observation (`RuntimeConnectionsService::grant_visible`), added to every scenario that kills the publisher after granting (four in `reachability.rs`, one in `linking.rs`).

**Those scenarios carry the feature as a whole, not only the wait.** `reachability.rs` is `#![cfg(feature = "test-util")]` for its contact observation already; the one in `linking.rs` shuts the publishing device down either way, so a build without the feature would keep the killing and drop the wait that closes its premise — the arrangement measured at about 2% flaky. It is therefore gated at the test itself: the scenario runs where its premise can be pinned, and the lane without the feature runs neither it nor the reachability set. The `just` recipes enable the feature.

**Issuer-device union, after the fix (31-Jul-2026).** 60 of 60 stress iterations over `reachability`, `scoped_writes`, and `sibling_serving` — 13 tests an iteration, 0 failures, about 18 minutes. This is a regression pass, not a rule-of-three run against a measured rate: the union widens a derived set rather than moving a timing window, and no failure rate was in hand to size against. What it does establish is that the scenario the first pool caught — `a_regrant_after_withdrawal_rebuilds_the_contact_set` — stays green under the new derivation, and that the two withdrawal scenarios do not race each other.

**Unreachable-inviter probes, after the rewrite (30-Jul-2026).** 200 of 200 stress iterations of the two, 0 failures, at 0.83 seconds per iteration for both together — the earlier shape spent 5 seconds per test waiting out a bound it could never beat. Each was also run against a deliberately broken mechanism (the dial failure given the refusal marker) and failed there, so the assertion is known to discriminate rather than merely to pass.

**Second pool, verdict (30-Jul-2026).** Broad: 74 of 100 iterations over the five binaries, 0 failures, cut short by decision — its full-picture job was done. Deep, on the caught scenario alone: 476 of 600 iterations, 0 failures, cut short by decision at 3 of 476 ≈ 0.63% — three times below the 2% baseline, which satisfies the rule-of-three sizing. Final `just check`, the full 97-test suite, and `openspec validate --all --strict` are green after the fix.
