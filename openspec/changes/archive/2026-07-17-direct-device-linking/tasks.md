## 2. The data-layer surface the ceremony stands on (`data-layer`, D8)

- [x] 2.1 `PrivateMetadataStore` gains a bounded wait for the first successful sync session of its replica started after a given instant — today's `confirm_registration` semantics (`events()` + the fork's sync-finished event, `result.is_ok()` and `started >= instant`), lifted into the store as its own property. `events()` stays `pub(crate)` behind it and the fork's event type stays unexported, so `pdn-node` still needs no dependency on the fork. No trigger is carried over: `import_doc` starts the first session and enrols the replica in the periodic reconcile pass with the ticket's contacts, so a failed first exchange is re-dialed inside the wait's own budget
- [x] 2.2 `PrivateMetadataStore::namespace()`, mirroring `ConnectionMetadataStore`'s — so an imported directory can be named to `forget_doc` it
- [x] 2.3 `SyncNode::forget_namespace(issuer)` as the counterpart of `import_namespace(issuer, ticket)`: untrack, drop the replica, and unregister the issuer as one act (`Registry` gains the unregister). Dropping without unregistering is the trap this closes — the issuer would keep resolving to a dropped replica and fail as a storage error instead of the unknown-issuer refusal
- [x] 2.4 data-layer tests for the three: the wait returns on a successful session started after the instant and not on content alone, and times out distinguishably when no peer is reachable; forgetting a namespace makes its issuer unknown again while a co-hosted issuer stays addressable

## 3. The linking ceremony (`pdn-node`)

- [x] 3.1 Linking module next to `pairing.rs`: `LinkingPayload` (format version, inviter device address, one-time secret, identity `PdnId` — no tickets, no proof), the dedicated `/pdn/linking/0` ALPN, a second `PendingInvites` instance in runtime state for linking secrets (the struct is reused unchanged — it binds a 32-byte secret to an identity with lazy expiry, which is what a linking secret binds too; placement is the design's open question), the two length-prefixed postcard messages: request `{version, secret}`, response `{directory ticket, data ticket}` (D2)
- [x] 3.2 Accept side (the protocol handler): read the request → version check → under the runtime lock: atomic verify-and-burn before any state, write the newcomer's device record into the inviter's directory replica using the connection's authenticated peer id (never a claimed field — this is new ground: pairing reads a claimed `scanner` field, so there is no precedent to copy, only the transport's guarantee that the accepted connection carries the remote endpoint's authenticated id), mint fresh write tickets for the directory and the identity's data namespace from local replicas → unlock → reply; commit precedes the reply; refusals uniform (close without a distinguishing answer); a wrong secret burns nothing; late-bound state slot and pairing's lock discipline — request read before the lock, answer written after it, local store writes and mints under it, and no wait on delivery to another device ever under it (D3, D4)
- [x] 3.3 Dial side (`link`): version refusal before dialing; already-hosted refusal before dialing; dial through the data-layer dial handle on the linking ALPN → exchange → import the directory (inviter's live address appended to the ticket's contacts) → import the data namespace registered under the payload's identity → one bounded wait (2.1) for the first successful directory sync started after the import, within the caller's timeout → on any failure after import, roll back both replicas: `forget_doc(directory.namespace())` and `forget_namespace(identity)` (2.2, 2.3), so the dialing node keeps no residue. Note the shape being copied, not the code: establishment's rollback fires only on a failed ticket mint and leaves an orphan behind a failed assembly — linking's covers the whole path after the import (D5)
- [x] 3.4 `Runtime::spawn` registers both handlers — pairing and linking — through the spawn-time protocol slot; each handler gets its own state slot (the existing `set` is per-handler and errors on a second fill)
- [x] 3.5 `IdentityService` reshaped (**BREAKING**): `create` additionally publishes the data-namespace ticket under `tickets/data` (D4); `linking_invite(identity, lifetime) -> LinkingPayload` and `link(payload, timeout)` replace `linking_seed` / the identity-argument `link` (D7); service and runtime docs updated — the `State` doc's standing exception ("The exception is linking, which holds the lock for its whole wait") is removed, since `link` no longer holds the lock across its wait
- [x] 3.6 Delete data-layer `linking.rs`: provisioning folds into `create` (directory + device record + data namespace + `tickets/data`), `link_device` / `confirm_registration` / `PrivateMetadataStore::sync_with` / `CONTACT_RETRY_INTERVAL` / `IdentityStores` all gone; `events()` is not dead code — group 2's wait is its caller now; the runtime keeps its own hosted-identity value (D6); data-layer `lib.rs` / `node.rs` / `registry.rs` docs swept

## 4. Linking scenario tests (`pdn-node`)

- [x] 4.1 Positive ceremony (scenarios "Linking completes between two runtimes", "The newcomer is registered on the inviting device", "Success implies the directory is caught up", "The newcomer comes up with the full store set"): create on A, invite on A, link on B; B reads the device set including A's device, hosts the data namespace, and an entry written under the identity on either runtime becomes readable on the other; the payload carries no bearer material; distinct secrets per invite
- [x] 4.2 Non-founder chain (scenario "Linking through a non-founder device"): three devices, device 3 links from an invite minted on device 2; device sets converge to three; transitive data catch-up. Covers the induction D4 rests on — device 2 can mint a *write* ticket for the data namespace only because its own linking reply imported one
- [x] 4.3 Refusal pairs (verify-and-burn scenarios, per the access-control-tests practice — the boundary the QR model never had): a replayed secret after a completed link; an expired secret (tiny invite-time lifetime); a wrong secret that burns nothing (the real secret still links afterwards); an unknown payload version refused before dialing; linking into an already-hosted identity refused before dialing; a linking invite for an unhosted identity refused — each refusal probed for no observable state (device set, directory kinds, hosted replicas on both sides unchanged)
- [x] 4.4 Lost-reply convergence (scenario "A dialogue lost after commit converges on a fresh invite"): a raw dialer presents a live secret and drops the connection without reading the reply; the inviter holds the registration; a fresh invite links the same device cleanly, one device record
- [x] 4.5 Rollback (scenario "A timed-out link leaves nothing behind on the dialing node"): a link whose directory cannot catch up within the timeout fails, and the dialing runtime afterwards hosts neither the directory nor the data namespace — the identity's reads refuse as unknown, not as storage errors (the assertion that 2.3 exists to make true)
- [x] 4.6 Multi-identity linking re-targeted (delta scenario "Second identity requires its own linking"): two identities linked onto one runtime by two invites, nothing of one visible under the other; data-service scenarios drop manual same-identity ticket handover (share/import remains for cross-identity namespaces only)
