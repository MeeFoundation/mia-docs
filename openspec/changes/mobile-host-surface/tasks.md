# Tasks: mobile-host-surface

Start after `own-grant-read` has landed: the facade exports that read, and nothing here adds it.

Group 1 is a gate, not a warm-up: nothing below the facade has ever been compiled for either mobile target, and 2 devices have never paired over a real network with no relay configured. Its outcomes are not one outcome, and 1.1 sorts them — a missing feature flag is proceeded through, a needed fork stops the change, and an endpoint that cannot survive a platform suspension changes this specification rather than the schedule.

## 1. Portability spike (gate)

- [x] 1.1 Build the runtime's dependency graph for `aarch64-apple-ios` and `aarch64-linux-android`: iroh, quinn, the TLS provider, the docs engine, the address-watching and port-mapping crates. Sort what is found into the 3 outcomes — a feature or configuration change, which is proceeded through and recorded; a dependency needing a fork, which stops the change; and a platform behaviour that contradicts a requirement below, which amends it before anything is built
  - Outcome: (a) for both targets, throughout. `cargo check -p pdn-node --target <target>` (which covers `data-layer` and the whole iroh graph underneath) typechecks clean on both, and no dependency needed a fork.
  - iroh 1.0.2 no longer depends on `quinn` at all: it carries its own QUIC implementation, `noq-proto`/`noq-udp`. The task's and design.md's "quinn" naming is stale as of this version; nothing in the graph is named `quinn`.
  - `aarch64-apple-ios`: no configuration needed. `ring` (the crypto provider — confirmed by its compiled artifacts, not just a clean log) builds its assembly through Xcode's `clang` via `xcrun`, found automatically. `netwatch`, `portmapper`, `iroh-relay`, `rustls`, `rustls-platform-verifier` all typecheck with no changes.
  - `aarch64-linux-android`: one configuration gap. `ring`'s build script needs a target C compiler; `cc-rs` looks for a bare `aarch64-linux-android-clang`, but NDK 28 only ships API-level-suffixed wrappers (`aarch64-linux-android24-clang`, `...30-clang`, etc.). Setting `CC_aarch64_linux_android` / `AR_aarch64_linux_android` to a chosen API level's wrapper (tried API 24) is enough — after that the graph typechecks clean, `ring` included. This is exactly what task 5.2's recipe and `cargo-ndk` (not yet installed) exist to automate; nothing here needs one.
  - Noted for 2.2 (bring-up), confirmed on-device under 1.2: `iroh_dns`'s Android system-DNS reader (not `rustls-platform-verifier` — that was a guess before 1.2 ran, corrected here) uses `ndk_context` to read `LinkProperties` over JNI, and this runs unconditionally the first time a `DnsResolver` is built — inside `SyncNode::spawn_with`, on every bring-up, even under `presets::Minimal` with no relay or discovery configured. Without an initialized `ndk_context`, the JNI call panics; `iroh_dns` catches that panic internally (`catch_unwind`) and falls back to public DNS servers, so bring-up still succeeds — confirmed on the Android emulator in 1.2, where the panic printed but node id and identity still came back. Two consequences for the facade: (1) its Android bring-up should call `iroh_dns::install_android_jni_context` (re-exported as `iroh::install_android_jni_context`) once at startup with the JavaVM/Context obtained from `JNI_OnLoad`, so the DNS reader gets the real system config instead of silently falling back; (2) the facade's Android build must never set `panic = "abort"` unless that call is guaranteed to run first — `iroh_dns`'s own docs state that combination aborts the process on first DNS lookup instead of falling back.
  - Local note, not a repo finding: the active rustup toolchain here was 1.89.0, below iroh 1.0.2's own MSRV of 1.91; `rustup update stable` (now 1.97.1) fixed it. CI is unaffected — `ci.yml`/`nightly.yml` install `dtolnay/rust-toolchain@stable`, always current.
- [~] 1.2 A throwaway host on each platform that brings a runtime up, creates an identity, and reports the node id — the smallest proof the endpoint binds and the identity's stores come up on the device
  - Android, done: a throwaway binary (`Runtime::spawn`, `identity().create()`, print node id and identity) built for `aarch64-linux-android`, pushed to a Pixel 6a emulator (API 34) over `adb`, and run. Reported a node id and identity, and a bound UDP socket was visible in `/proc/net/udp` while the process slept. The `ndk-context`/DNS panic noted under 1.1 fired here too, on the main thread inside `SyncNode::spawn_with` — but see 1.1's corrected note below, it is caught internally and harmless.
  - iOS Simulator, done: the same logic as a `staticlib` (`pdn_spike_run` FFI entry point) linked into a minimal SwiftUI app (generated with `xcodegen`, no signing needed for Simulator) and run on an iPhone 17 (iOS 26) simulator. Reported node id and identity on screen. One linker gap found and fixed: `netwatch`'s iOS backend (`netdev`, via `nw_path_monitor_*`) calls `Network.framework` directly, and Xcode does not auto-link a framework only referenced from an opaque static lib — needed `-framework Network -framework SystemConfiguration` in `OTHER_LDFLAGS`. Outcome (a); the eventual `pdn-mobile` build recipe (task 5.2/5.3) needs to link both frameworks for iOS.
  - iOS physical device: pending, needs the interactive signing step below.

## 2. The facade (`crates/pdn-mobile`)

- [ ] 2.1 The crate: depends on `pdn-node` only, no `data-layer` dependency, built as a static library for both mobile targets beside the workspace's own (D1)
- [ ] 2.2 Bring-up and stop on a handle: one runtime per handle, an explicitly configured reconcile interval, stop safe to repeat, a second bring-up of the same handle refused (D2, D5)
- [ ] 2.3 Exported calls, one per service call: identities (create, list hosted), linking (mint, consume), invites (mint, consume), connections (list), grants (publish, read a peer's, read own, withdraw), entries (write, read, list), node id
- [ ] 2.4 The claim derivation, in both directions and stated on the surface: a grant names claim identities derived from the issuer and an entry path, so publication takes paths and derives, and a grant read reports the derived identities. The facade exports the derivation so a caller can join a read against paths it knows or has listed (D8)
- [ ] 2.5 Exported types: entry listing, connection list, grant publication, and both grant reads carrying the capability alone — issuer, claims, commands, no ticket, and no exported call accepting one (D3)
- [ ] 2.6 Ceremony payloads: exported in the runtime type's own serde encoding, so any host over the same runtime consumes what this one produced, with a textual form a screen can draw as a code and rebuild from a scan. The facade names none of the payload's fields, and the live-secret exposure is stated in the crate's docs (D6)
- [ ] 2.7 The error table, written out rather than referenced: the runtime's refusals separated by kind — an ungranted write, unsupported delegation, a refused ceremony — an unhosted identity or issuer, a peer not connected, an act already committed or in flight, a counterparty never reached, a dialogue that timed out, a catch-up that timed out, an unsupported payload version, and an unrecognized failure whose cause chain stays in the log. The divergence from `pdn-node-http`'s table is stated in the crate's docs with its reason (D4)
- [ ] 2.8 The host's own pre-validation, named as the host's rather than the runtime's: an empty entry payload, a malformed entry path, and a grant naming no claim at all (D4)
- [ ] 2.9 Entry payloads as raw bytes both ways with no framing of the facade's own, bounded by a stated ceiling per payload, and entry paths in the runtime's own form (D9)
- [ ] 2.10 The read that answers nothing: one reported absence covering both no entry and a record whose payload has not arrived, stated in the crate's docs as the thing a caller must not conclude from
- [ ] 2.11 Listing: issuer, path and payload length with no payloads fetched, an optional prefix matching whole path components, and an issuer this node holds nothing of reported as the unknown-issuer refusal rather than an empty list
- [ ] 2.12 Grants: publication naming the issuer and the claims with a per-claim write flag, republication replacing the previous record, withdrawal as one act naming peer and issuer, a foreign issuer's refusal passed through, and both reads reporting what is readable now without waiting
- [ ] 2.13 Ceremonies bounded: every exported ceremony call reaches an outcome within a bound, and the linking consume takes the caller's bound for the whole act — the dialogue spending from it first, the catch-up taking the remainder — reporting its own failure after rolling back
- [ ] 2.14 Asynchronous across the boundary, with the asynchronous runtime owned by the facade and no exported call requiring the caller to hold a lock across it. Where a caller's continuation resumes is the caller's, and no requirement here claims it
- [ ] 2.15 The facade authorizes nothing: no credential, token or permission of its own on any exported call, stated in the crate's docs beside the fact that reaching it is reaching the node
- [ ] 2.16 Volatility and the keyless identity stated in the crate's docs, as context quoted from the runtime's own specs rather than as this surface's own claims: what a stop loses, and that a connection is evidence 2 devices ran a ceremony with one secret and nothing more

## 3. The facade's tests

- [ ] 3.1 Two handles against two runtimes in one test binary, driven through exported calls alone: create identities, invite, establish, publish a grant, write an entry, read it back through the grantee, withdraw and watch access close — no ticket in the test body, no direct service call, waiting done by repeating the read
- [ ] 3.2 The paired denial of that positive, in the same place: a third handle whose identity is connected to neither side obtains nothing of the granting identity's data, probed after the grantee demonstrably read it ([access-control-tests](../../specs/code-practices/access-control-tests.md)). The second read negative that rule names — a ticket without a capability — cannot be staged here, because no ticket crosses the facade; it stays with the runtime's own suites, and the test's docs say so
- [ ] 3.3 The error table asserted directly, each kind to its own and an unmapped error to the unrecognized one — the table is what every paired denial rests on, so it is tested as a table rather than only through calls. The 3 ceremony outcomes are asserted at whatever granularity the runtime actually separates them at, which 1.5 and the linking budget's own behaviour settle
- [ ] 3.4 The host's own pre-validation asserted beside the well-formed call it is the near miss of: an empty payload, a malformed path, a grant with no claim
- [ ] 3.5 Bytes in, bytes out for an arbitrary payload up to the ceiling and refused above it; a prefix matching components rather than characters; an unknown issuer refused rather than answered empty; a claim identity derived from a path matching the one a grant read reports
- [ ] 3.6 A ceremony payload minted through the facade parsed by `pdn-node-http`'s own decoding, and the reverse — the interop 2.6 exists for, and the only assertion that catches a divergence before a person meets it in a room
- [ ] 3.7 Each scenario above proven to fail with its mechanism deliberately broken — a test that passes either way asserts nothing. The absences of 4.1 are excluded: an absence cannot be broken, which is why it is not a test
