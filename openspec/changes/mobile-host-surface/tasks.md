# Tasks: mobile-host-surface

Start after `own-grant-read` has landed: the facade exports that read, and nothing here adds it.

Group 1 is a gate, not a warm-up: nothing below the facade has ever been compiled for either mobile target, and 2 devices have never paired over a real network with no relay configured. Its outcomes are not one outcome, and 1.1 sorts them — a missing feature flag is proceeded through, a needed fork stops the change, and an endpoint that cannot survive a platform suspension changes this specification rather than the schedule.

## 1. Portability spike (gate)

- [x] 1.1 Build the runtime's dependency graph for `aarch64-apple-ios` and `aarch64-linux-android`: iroh, quinn, the TLS provider, the docs engine, the address-watching and port-mapping crates. Sort what is found into the 3 outcomes — a feature or configuration change, which is proceeded through and recorded; a dependency needing a fork, which stops the change; and a platform behaviour that contradicts a requirement below, which amends it before anything is built
  - Outcome: (a) for both targets, throughout. `cargo check -p pdn-node --target <target>` (which covers `data-layer` and the whole iroh graph underneath) typechecks clean on both, and no dependency needed a fork.
  - iroh 1.0.2 no longer depends on `quinn` at all: it carries its own QUIC implementation, `noq-proto`/`noq-udp`. The task's and design.md's "quinn" naming is stale as of this version; nothing in the graph is named `quinn`.
  - `aarch64-apple-ios`: no configuration needed. `ring` (the crypto provider — confirmed by its compiled artifacts, not just a clean log) builds its assembly through Xcode's `clang` via `xcrun`, found automatically. `netwatch`, `portmapper`, `iroh-relay`, `rustls`, `rustls-platform-verifier` all typecheck with no changes.
  - `aarch64-linux-android`: one configuration gap. `ring`'s build script needs a target C compiler; `cc-rs` looks for a bare `aarch64-linux-android-clang`, but NDK 28 only ships API-level-suffixed wrappers (`aarch64-linux-android24-clang`, `...30-clang`, etc.). Setting `CC_aarch64_linux_android` / `AR_aarch64_linux_android` to a chosen API level's wrapper (tried API 24) is enough — after that the graph typechecks clean, `ring` included. This is exactly what the recipes of tasks 5.3 and 5.7 and `cargo-ndk` (not yet installed) exist to automate; nothing here needs one.
  - Noted for 2.2 (bring-up), confirmed on-device under 1.2: `iroh_dns`'s Android system-DNS reader (not `rustls-platform-verifier` — that was a guess before 1.2 ran, corrected here) uses `ndk_context` to read `LinkProperties` over JNI, and this runs unconditionally the first time a `DnsResolver` is built — inside `SyncNode::spawn_with`, on every bring-up, even under `presets::Minimal` with no relay or discovery configured. Without an initialized `ndk_context`, the JNI call panics; `iroh_dns` catches that panic internally (`catch_unwind`) and falls back to public DNS servers, so bring-up still succeeds — confirmed on the Android emulator in 1.2, where the panic printed but node id and identity still came back. Two consequences for the facade: (1) its Android bring-up should call `iroh_dns::install_android_jni_context` (re-exported as `iroh::install_android_jni_context`) once at startup with the JavaVM/Context obtained from `JNI_OnLoad`, so the DNS reader gets the real system config instead of silently falling back; (2) the facade's Android build must never set `panic = "abort"` unless that call is guaranteed to run first — `iroh_dns`'s own docs state that combination aborts the process on first DNS lookup instead of falling back.
  - Local note, not a repo finding: the active rustup toolchain here was 1.89.0, below iroh 1.0.2's own MSRV of 1.91; `rustup update stable` (now 1.97.1) fixed it. CI is unaffected — `ci.yml`/`nightly.yml` install `dtolnay/rust-toolchain@stable`, always current.
- [x] 1.2 A throwaway host on each platform that brings a runtime up, creates an identity, and reports the node id — the smallest proof the endpoint binds and the identity's stores come up on the device
  - Android, done: a throwaway binary (`Runtime::spawn`, `identity().create()`, print node id and identity) built for `aarch64-linux-android`, pushed to a Pixel 6a emulator (API 34) over `adb`, and run. Reported a node id and identity, and a bound UDP socket was visible in `/proc/net/udp` while the process slept. The `ndk-context`/DNS panic noted under 1.1 fired here too, on the main thread inside `SyncNode::spawn_with` — but see 1.1's corrected note below, it is caught internally and harmless.
  - iOS Simulator, done: the same logic as a `staticlib` (`pdn_spike_run` FFI entry point) linked into a minimal SwiftUI app (generated with `xcodegen`, no signing needed for Simulator) and run on an iPhone 17 (iOS 26) simulator. Reported node id and identity on screen. One linker gap found and fixed: `netwatch`'s iOS backend (`netdev`, via `nw_path_monitor_*`) calls `Network.framework` directly, and Xcode does not auto-link a framework only referenced from an opaque static lib — needed `-framework Network -framework SystemConfiguration` in `OTHER_LDFLAGS`. Outcome (a); the eventual `pdn-mobile` build recipe (tasks 5.3 and 5.7) needs to link both frameworks for iOS.
  - iOS physical device, done: an iPhone 15 Pro Max (iOS 26), and through the facade itself rather than a throwaway entry point — the `PdnMobile.xcframework` of task 5.2 linked into a minimal SwiftUI application generated with `xcodegen`, calling the exported `bringUp`, `nodeId`, `createIdentity` and `hostedIdentities`. The signing this task waited on needed no interactive step in the end: `xcodebuild -allowProvisioningUpdates` minted the team provisioning profile itself from the development certificate already on the machine. Bring-up on the application's own `Documents/pdn` reported a node id and created an identity; a relaunch on that container reported the same node id and the same hosted identity, which is the restart behaviour of 2.16 observed on a device rather than read from the code. Both `-framework Network` and `-framework SystemConfiguration` were needed, as the Simulator run found.
- [~] 1.3 Two physical devices in one local network: mint an invite on one, consume it on the other, publish a grant on one claim, read it on the other. This is the whole change's premise (D7)
  - Done between an iPhone 15 Pro Max and a `pdn-node-http` process on a Mac, over the room's own network with no relay configured: the host minted an invite naming its own subnet address, the phone consumed it by camera through the facade, and both sides then listed the other. The host wrote `contact/email`, published a read-only grant over that one claim, and the phone's connection screen showed the path and the value — joined from the listing of the received namespace, since a grant reports claim identities and no path comes back out of one.
  - What this settles is the premise: 2 nodes over 2 processes on 2 machines reach each other at a published subnet address, and a payload minted by one host is consumed by the other. What it does not settle is the phone-to-phone case, which needs the second device, and 1.6, which needs the declaration observed as the thing the traffic depends on.
  - The withdrawal exposed a defect of the screens rather than of the runtime: the memory of which issuers a connection had shown lived inside one mounting, so leaving the screen and returning made a withdrawn grant indistinguishable from one never made, and the screen named it as a device that may be unreachable — the network-problem framing its own requirement forbids. Fixed by holding that memory outside the screen, and confirmed on the device: after a withdrawal and a return to the screen it now names the issuer and says the peer no longer shares its data, with no banner of any kind. The memory records an observation rather than a grant, and a restart forgets it, after which an ended grant reads as no grant.
  - The whole path the operating conditions single out ran on the device: granted, read, withdrawn, and granted again over the same claim, the second time with write.
  - A restart of a node breaks its connections, and neither side can tell. A node keeps its id across a restart, because its key is in its directory, but not its address: the endpoint binds on an ephemeral port — `PDN_BIND_ADDR` names an IP and binds port 0, and no spawn option names a port — so a restarted node comes back reachable at an address nobody it had spoken to knows. With no relay and no discovery configured there is nothing to learn the new one from. Observed here: after the host was restarted, 2 values it wrote never reached the phone, whose screen went on showing the last value that had arrived, since a replica holds what it holds and no read reports how old it is.
  - This is not the facade's to fix and this change adds nothing for it. What it bears on is the staging of the demonstration, where restarting any node silently ends its connections.
  - A connection to a node that will never answer is retried for as long as the identity holds it, and nothing removes it: 1.5 recorded the phone still dialling an erased node hours later. A demonstration that has paired and re-paired during rehearsal therefore carries that traffic into the run.
- [x] 1.4 What a platform suspension does to a bound endpoint: suspend the application mid-session and record whether the node is reachable afterwards. If it is not, the single-bring-up requirement is the thing that changes — a host whose endpoint dies on suspension needs a re-bring-up act, which the requirement as written refuses (D2)
  - Outcome: the endpoint survives, and D2 stands. On an iPhone 15 Pro Max the application was backgrounded mid-session for about 20 minutes while a `pdn-node-http` peer wrote a new value to a granted claim; on return the node answered, the value was there, and no re-bring-up was needed. The single-bring-up requirement therefore needs no amendment, and neither shell delta changes.
  - What the suspension does break is the application's own reading, and it broke it silently — the worse of the two failures. 2 defects of the screens, both fixed there and neither the runtime's:
  - The periodic read is a `setInterval`, and a suspension stops it without the platform starting it again: after the return the screen sat for 20 seconds, 4 intervals, showing the value from before the suspension as though it were current. A screen that says it is waiting is honest; one that shows a stale value as fresh is not. The interval is now re-established on every return to the foreground, and the listing screens re-read there too, since a navigation gives a focus and a return from suspension does not.
  - The waiting banner counts from when the screen was opened, so after a long suspension it reported the sleep of the application as "longer than the cadence explains — the other device may be unreachable", blaming the peer for this side's own absence. The clock is restarted on the return.
  - Both belong to `operating-conditions`' warning about steps scheduled for the way out: a timer the system may stop is not something correctness may rest on.
  - Both fixes confirmed on the device: after a 2-minute suspension the value written meanwhile appeared as the application came back, with no banner blaming the peer for the sleep. Before them the same suspension left the screen showing the previous value for as long as it was watched.
- [x] 1.5 The failure a dial into one's own endpoint produces, on the 2 Android emulators that cannot reach each other: whether it arrives as unreachable or as a refusal. A permanent specification names this, so it is observed rather than reasoned about (D7)
  - Observed on iOS instead, and no emulator was needed: an identity with a single device dials its own endpoint continuously, because a connection's metadata pair names that identity's devices and the only one is this node. It arrives as a named condition of the runtime rather than as unreachability — `Failed to establish connection`, caused by `Connecting to ourself is not supported` — once per namespace per reconcile interval, 16 of them in one short window.
  - The distinction was only visible once the facade logged causes. Read from the failure alone, without its cause, the same lines look like an unreachable peer, which is what a reader would otherwise have concluded.
  - Nothing above sees it: the sync pass logs and carries on, and no exported call reports it. The cost is noise rather than a broken act, but it is continuous and it scales with the namespaces the identity holds.
  - A dead peer produces the same failure and never stops: the phone was still dialling a node whose directory had been erased hours earlier, `MultipathNotNegotiated` and then the same connect failure. Of the 3 peers it was polling, 2 were unreachable for good and the runtime had no way to learn it.
- [~] 1.6 On iOS, confirm the local-network declaration is what the traffic depends on: with it, the pairing of 1.3; without it, the silent drop — and whether a refused consent is observable at all, which the shells will need
  - The half with the declaration is done: 1.3 paired and exchanged data over the subnet with it in place.
  - The half without it is not, and the reason is worth writing down because it will catch the next person: the platform remembers the grant against the application's identifier, so a build that drops the declaration keeps the access an earlier build was granted. Two builds without the key both synced normally, and the runtime's log showed `sync finished` against the peer throughout. Removing the key from the generated `Info.plist` does not revoke anything.
  - What the log did show, once at start-up, is that the denial has a name when it happens: `session denied by the local access provider`, as the cause under a failed sync. Whether that name reaches an exported call, or arrives as an ordinary unreachable peer, is exactly what stays unanswered.
  - Answered by reinstalling, which is what revokes the grant along with the node's directory and its key. On a build carrying no declaration and an application with no prior grant, the pairing ran and the sync went on running: a connection was established and the peer's namespaces synced, with no denial logged at all.
  - The reason it ran: the platform asked for the access anyway and the person allowed it. The declaration is not what gates the traffic on this version — the grant is, and the system requests the grant whether or not the application declares anything. What the declaration supplies is the sentence in that request.
  - So the premise this task was written on — "without it, the silent drop" — does not hold. What is true is worse for a person and better for the specification: without the declaration the request still appears, and it appears with no reason in it. Somebody is asked to let an application reach the devices around them and is told nothing about why.
  - One explanation was tried and refuted before this one was found, and is kept here so it is not tried again: that the runtime's globally routable IPv6 addresses carried the traffic around the gate, since those are ordinary internet rather than local network. Handing the phone an invite naming the subnet address alone still paired, which ruled it out.
  - This settles what the declaration is for, and therefore what `ios-app-shell` should require of it: the reason text, not the access.
  - The other half of the question — whether a refused consent is observable at all — is answered, and the answer is no. With the grant revoked from the platform's settings the ceremony ran its bound and failed, and what reached the surface named the peer: `CounterpartyUnreachable` in the run that was logged, and reported as the unrecognized failure in an earlier unlogged one. Either way the application cannot say what happened, because it is not told: the denial belongs to the platform and the runtime sees only a dial that went nowhere.
  - So the person is shown a peer that could not be reached, or a fault inside the node, for a condition they created themselves in the settings and could undo in seconds. `ios-app-shell`'s requirement of a legible state when local-network consent is absent or refused cannot be met by the shell as things stand, and no scenario for it should be invented; what it would take is the runtime distinguishing a denied local-network session, which it does not.
  - The runtime does have the words for it — `session denied by the local access provider` appears in its own log — so the distinction exists below and is lost on the way up. This change adds nothing for it; it is recorded so that whoever widens the table knows what to key on.
- [ ] 1.7 On Android, determine what the target platform level requires for local-subnet traffic and whether a declaration is needed at that level. Nothing here depends on the answer; the shells do, so it is recorded
- [x] 1.8 Record what the generated bindings do about async: futures or callbacks, whether an opaque type crosses at all, and which shape is pleasant to call from a screen
  - uniffi 0.32 generates each asynchronous exported call as the language's own asynchronous form, with no callback anywhere: Swift gets `func bringUp(storageDir: String, reconcileIntervalSecs: UInt64) async throws`, Kotlin gets `suspend fun bringUp(...)`. A screen therefore awaits a call the way it awaits any other, and a refusal arrives as a thrown error of the generated error type rather than as a result to inspect.
  - The handle crosses as an object (Swift `open class PdnNode`, Kotlin `class PdnNode : Disposable, AutoCloseable`), and the records cross as generated data types — `GrantCapability`, `GrantedPath`, `GrantedClaimId`, `EntryListing`. An entry payload crosses as `Data` on Swift and `ByteArray` on Kotlin. Nothing opaque crosses.

## 2. The facade (`crates/pdn-mobile`)

- [x] 2.1 The crate: depends on `pdn-node` only, no `data-layer` dependency, built as a static library for both mobile targets beside the workspace's own (D1)
  - `crate-type = ["lib", "staticlib", "cdylib"]` — the static library iOS links, the shared library Android loads, and the `lib` the crate's own tests drive. The 2 target builds run in the pipeline (5.7); the development container has neither the NDK nor Xcode, so neither ran here.
- [x] 2.2 Bring-up and stop on a handle: one runtime per handle, an explicitly configured reconcile interval, stop safe to repeat, a second bring-up of the same handle refused (D2, D5)
  - Bring-up also names the directory the node's state lives in, because the runtime's spawn requires a storage choice and the embedder is the one that knows its sandbox — see the note under 2.16, which is where that decision leaves this change's spec.
  - The 2 races between bring-up and stop are handled where the state lives rather than in the caller, and both are asserted: the node is installed by the spawn's own task, so a cancelled call — a coroutine cancelled as a shell leaves the foreground — cannot strand the handle between its states; and a stop that overtakes a bring-up shuts the new node down and leaves the bring-up reporting the node as not up, rather than handing back a node its caller has already stopped and a directory nobody holds.
- [x] 2.3 Exported calls, one per service call: identities (create, list hosted), linking (mint, consume), invites (mint, consume), connections (list), grants (publish, read a peer's, read own, withdraw), entries (write, read, list), node id
- [x] 2.4 The claim derivation, in both directions and stated on the surface: a grant names claim identities derived from the issuer and an entry path, so publication takes paths and derives, and a grant read reports the derived identities. The facade exports the derivation so a caller can join a read against paths it knows or has listed (D8)
- [x] 2.5 Exported types: entry listing, connection list, grant publication, and both grant reads carrying the capability alone — issuer, claims, commands, no ticket, and no exported call accepting one (D3)
- [x] 2.6 Ceremony payloads: exported in the runtime type's own serde encoding, so any host over the same runtime consumes what this one produced, with a textual form a screen can draw as a code and rebuild from a scan. The facade names none of the payload's fields, and the live-secret exposure is stated in the crate's docs (D6)
  - The textual form is that encoding in a base64 alphabet, wrapped in nothing else, so what a scan recovers unwraps to the bytes the other host takes as a body.
- [x] 2.7 The error table, written out rather than referenced: the runtime's refusals separated by kind — an ungranted write, unsupported delegation, a refused ceremony — an unhosted identity or issuer, a peer not connected, an act already committed or in flight, a counterparty never reached, a dialogue that timed out, a catch-up that timed out, an unsupported payload version, and an unrecognized failure whose cause chain stays in the log. The divergence from `pdn-node-http`'s table is stated in the crate's docs with its reason (D4)
  - 3 kinds of the host's own sit beside those: a directory another running node holds, a call with no node up, and a second bring-up.
- [x] 2.8 The host's own pre-validation, named as the host's rather than the runtime's: an empty entry payload, a malformed entry path, and a grant naming no claim at all (D4)
- [x] 2.9 Entry payloads as raw bytes both ways with no framing of the facade's own, bounded by a stated ceiling per payload, and entry paths in the runtime's own form (D9)
  - The ceiling is 1 MiB, against the HTTP host's 64 MB: the same buffer on a device that is killed for memory rather than asked to swap. It bounds the write and not the read, which the requirement now says outright with its reason — an entry a peer wrote through the other host is in the replica whatever its size, and refusing to hand it over would make a granted claim unreadable instead of making the device safer.
- [x] 2.10 The read that answers nothing: one reported absence covering both no entry and a record whose payload has not arrived, stated in the crate's docs as the thing a caller must not conclude from
- [x] 2.11 Listing: issuer, path and payload length with no payloads fetched, an optional prefix matching whole path components, and an issuer this node holds nothing of reported as the unknown-issuer refusal rather than an empty list
- [x] 2.12 Grants: publication naming the issuer and the claims with a per-claim write flag, republication replacing the previous record, withdrawal as one act naming peer and issuer, a foreign issuer's refusal passed through, and both reads reporting what is readable now without waiting
- [~] 2.13 Ceremonies bounded: every exported ceremony call reaches an outcome within a bound, and the linking consume takes the caller's bound for the whole act — the dialogue spending from it first, the catch-up taking the remainder — reporting its own failure after rolling back
  - The linking consume takes the caller's bound and passes it through as the budget of the whole act. What is not asserted here is the rollback and the catch-up's own failure, which the runtime's suites hold; the facade adds nothing to either.
- [x] 2.14 Asynchronous across the boundary, with the asynchronous runtime owned by the facade and no exported call requiring the caller to hold a lock across it. Where a caller's continuation resumes is the caller's, and no requirement here claims it
  - The handle owns a tokio runtime, every call runs on it, and the state lock is taken and released without an await in between. A handle released without a stop shuts its tasks down in the background rather than blocking the thread that let it go.
- [x] 2.15 The facade authorizes nothing: no credential, token or permission of its own on any exported call, stated in the crate's docs beside the fact that reaching it is reaching the node
- [x] 2.16 What a node keeps and the keyless identity stated in the crate's docs, as context quoted from the runtime's own specs rather than as this surface's own claims: what a stop loses, and that a connection is evidence 2 devices ran a ceremony with one secret and nothing more
  - The facade now installs a `tracing` subscriber writing to the platform's log, once, at handle construction, with an embedder's own subscriber keeping precedence. Without it the requirement that an unrecognized failure keeps its cause chain in the log was unmet on the platform it was written for: nothing routed the runtime's diagnostics anywhere, so the one refusal a person cannot act on was also the one nobody could diagnose. It is the logging alone; no exported call and no behaviour changed.
  - The keyless identity is stated as written. Volatility is not, because the runtime is no longer volatile: `SpawnOptions` requires a storage choice, `pdn-node` re-hosts what its `hosted-identities.json` record names, and `pdn-node-http` has required a directory for as long as it has existed. The crate's docs and `tests/surface.rs` therefore say what the runtime does — a node comes back on its directory as itself, under the same node id, and what does not come back is work in flight. The delta's requirement "The host repeats what the runtime says about its state", the proposal's deferred "On-disk persistence" and the design's restart and disk conditions are rewritten against the runtime as it stands, citing `durable-storage.md` and `restart-recovery.md` rather than asserting. `mobile-demo-app` carried the same claim in its proposal, its design D10, both its deltas and its own tasks, and is rewritten with them. The facade was not what changed.

## 3. The facade's tests

- [x] 3.1 Two handles against two runtimes in one test binary, driven through exported calls alone: create identities, invite, establish, publish a grant, write an entry, read it back through the grantee, withdraw and watch access close — no ticket in the test body, no direct service call, waiting done by repeating the read
  - `tests/surface.rs`, one scenario: 3 handles, the connection established from a minted payload, the grant published and read from both halves, the value read through the grantee, the republication replacing rather than accumulating, the withdrawal closing the access and a re-grant reopening it.
- [x] 3.2 The paired denial of that positive, in the same place: a third handle whose identity is connected to neither side obtains nothing of the granting identity's data, probed after the grantee demonstrably read it ([access-control-tests](../../specs/code-practices/access-control-tests.md)). The second read negative that rule names — a ticket without a capability — cannot be staged here, because no ticket crosses the facade; it stays with the runtime's own suites, and the test's docs say so
  - The read-only claim's refused write sits beside it, with the previous value asserted to stand.
- [x] 3.3 The error table asserted directly, each kind to its own and an unmapped error to the unrecognized one — the table is what every paired denial rests on, so it is tested as a table rather than only through calls. The 3 ceremony outcomes are asserted at whatever granularity the runtime actually separates them at, which 1.5 and the linking budget's own behaviour settle
- [x] 3.4 The host's own pre-validation asserted beside the well-formed call it is the near miss of: an empty payload, a malformed path, a grant with no claim
- [x] 3.5 Bytes in, bytes out for an arbitrary payload up to the ceiling and refused above it; a prefix matching components rather than characters; an unknown issuer refused rather than answered empty; a claim identity derived from a path matching the one a grant read reports
- [x] 3.6 A ceremony payload minted through the facade parsed by `pdn-node-http`'s own decoding, and the reverse — the interop 2.6 exists for, and the only assertion that catches a divergence before a person meets it in a room
  - The decoding asserted against is `serde_json` over the runtime's own payload type, which is what that host's body parsing is; the round trip ends in a consumed invite rather than a parse alone, so a divergence fails the establishment and not only the assertion.
- [~] 3.7 Each scenario above proven to fail with its mechanism deliberately broken — a test that passes either way asserts nothing. The absences of 4.1 are excluded: an absence cannot be broken, which is why it is not a test
  - 2 of the headline scenario's mechanisms were broken and the test failed on each, at the assertion that names it: with the grant publication turned into a no-op it fails on the own-grant read finding nothing published, and with the withdrawal turned into a no-op it fails on the access it should have closed staying open. Both mutations were reverted and the suite re-run green.
  - A third: with the install's stop-overtook check removed, the scenario that covers a stop racing a bring-up fails on the node still answering after the stop.
  - What is not yet done this way: the ceremony's own path (a payload minted but not delivered), the claim derivation, the listing's prefix, and the bounds of the host's pre-validation.

## 5. Binding artifacts and recipes

The generation and the packaging live in `pdn-sdk`, the crate and its target builds stay here (D10).

- [x] 5.1 `pdn-sdk` exists as its own git repository, gitignored by `mee-pdn` and present in the workspace file, carrying its README and CLAUDE.md: what it packages, what it decides nothing about, and that a screen needing something the facade does not export is a change to this capability rather than anything of its own
- [~] 5.2 In `pdn-sdk`: generate Swift bindings and package them with the static library as an XCFramework; generate Kotlin bindings and package them with the shared libraries for the Android architectures in use
  - Both generations run and are asserted by `just check` there. The Apple packaging has now run on a Mac outside the development container: `just package-apple` built both Apple targets, generated the Swift, and wrote a `PdnMobile.xcframework` carrying the `ios-arm64` and `ios-arm64-simulator` slices, which task 1.2's device run then linked. The Android archive still needs the NDK the development container does not carry. The Android half currently covers `arm64-v8a` alone, which 5.5 is where the architecture set is decided.
- [x] 5.3 In `pdn-sdk`: recipes for both, reading the crate from the `mee-pdn` checkout it is cloned inside, with the toolchains each needs; the generated sources are build artifacts and are committed nowhere
  - The generation reads the crate's metadata out of a host build of the shared library, which is why it runs on a machine that cannot build for a phone. `MEE_PDN` names another checkout. Everything a recipe writes lands under `build/`, which that repository's `.gitignore` covers.
- [x] 5.4 In `pdn-sdk`: a release names the commit of `mee-pdn` it packages and builds both halves from that one commit, so an application built against a facade older than the runtime it is used against is diagnosable from the release rather than from a refusal on a phone (D10)

- [~] 5.5 In `pdn-sdk`: a release built in the configuration a device installs — the runtime's test-only feature off — covering the architectures the targeted devices need, and the packaging failing rather than publishing a release short of one
  - The feature is off by default and no recipe turns it on, and the recipes stop on a failed target build rather than packaging what succeeded. What is undecided is the architecture set: the Android half packages `arm64-v8a`, and whether a demonstration device needs `x86_64` for an emulator is a question the run-through answers.
- [ ] 5.6 In `pdn-sdk`: the release consumable by naming a version, proven by building the application on a machine holding neither a Rust toolchain nor a `mee-pdn` checkout
- [x] 5.7 A recipe building the facade for a mobile target, and a pipeline job running it, here; the 2 mobile targets added to `just setup-tooling`. `just check` already builds the workspace with `pdn-node/test-util` off — it runs clippy in both configurations, the product one first — so what this recipe adds is the target, not the feature configuration
