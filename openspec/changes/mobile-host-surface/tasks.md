# Tasks: mobile-host-surface

Start after `own-grant-read` has landed: the facade exports that read, and nothing here adds it.

Group 1 is a gate, not a warm-up: nothing below the facade has ever been compiled for either mobile target, and 2 devices have never paired over a real network with no relay configured. Its outcomes are not one outcome, and 1.1 sorts them — a missing feature flag is proceeded through, a needed fork stops the change, and an endpoint that cannot survive a platform suspension changes this specification rather than the schedule.

## 1. Portability spike (gate)

- [x] 1.1 Build the runtime's dependency graph for `aarch64-apple-ios` and `aarch64-linux-android`: iroh, quinn, the TLS provider, the docs engine, the address-watching and port-mapping crates. Sort what is found into the 3 outcomes — a feature or configuration change, which is proceeded through and recorded; a dependency needing a fork, which stops the change; and a platform behaviour that contradicts a requirement below, which amends it before anything is built
  - Outcome: (a) for both targets, throughout. `cargo check -p pdn-node --target <target>` (which covers `data-layer` and the whole iroh graph underneath) typechecks clean on both, and no dependency needed a fork.
  - iroh 1.0.2 no longer depends on `quinn` at all: it carries its own QUIC implementation, `noq-proto`/`noq-udp`. The task's and design.md's "quinn" naming is stale as of this version; nothing in the graph is named `quinn`.
  - `aarch64-apple-ios`: no configuration needed. `ring` (the crypto provider — confirmed by its compiled artifacts, not just a clean log) builds its assembly through Xcode's `clang` via `xcrun`, found automatically. `netwatch`, `portmapper`, `iroh-relay`, `rustls`, `rustls-platform-verifier` all typecheck with no changes.
  - `aarch64-linux-android`: one configuration gap. `ring`'s build script needs a target C compiler; `cc-rs` looks for a bare `aarch64-linux-android-clang`, but NDK 28 only ships API-level-suffixed wrappers (`aarch64-linux-android24-clang`, `...30-clang`, etc.). Setting `CC_aarch64_linux_android` / `AR_aarch64_linux_android` to a chosen API level's wrapper (tried API 24) is enough — after that the graph typechecks clean, `ring` included. This is exactly what the recipes of tasks 5.3 and 5.7 and `cargo-ndk` (not yet installed) exist to automate; nothing here needs one.
  - Noted for 2.2 (bring-up), confirmed on-device under 1.2: `iroh_dns`'s Android system-DNS reader (not `rustls-platform-verifier` — that was a guess before 1.2 ran, corrected here) uses `ndk_context` to read `LinkProperties` over JNI, and this runs unconditionally the first time a `DnsResolver` is built — inside `SyncNode::spawn_with`, on every bring-up, even under `presets::Minimal` with no relay or discovery configured. Without an initialized `ndk_context`, the JNI call panics; `iroh_dns` catches that panic internally (`catch_unwind`) and falls back to public DNS servers, so bring-up still succeeds — confirmed on the Android emulator in 1.2, where the panic printed but node id and identity still came back. Two consequences for the facade: (1) its Android bring-up should call `iroh_dns::install_android_jni_context` (re-exported as `iroh::install_android_jni_context`) once at startup with the JavaVM/Context obtained from `JNI_OnLoad`, so the DNS reader gets the real system config instead of silently falling back; (2) the facade's Android build must never set `panic = "abort"` unless that call is guaranteed to run first — `iroh_dns`'s own docs state that combination aborts the process on first DNS lookup instead of falling back.
  - Local note, not a repo finding: the active rustup toolchain here was 1.89.0, below iroh 1.0.2's own MSRV of 1.91; `rustup update stable` (now 1.97.1) fixed it. CI is unaffected — `ci.yml`/`nightly.yml` install `dtolnay/rust-toolchain@stable`, always current.
- [~] 1.2 A throwaway host on each platform that brings a runtime up, creates an identity, and reports the node id — the smallest proof the endpoint binds and the identity's stores come up on the device
  - Android, done: a throwaway binary (`Runtime::spawn`, `identity().create()`, print node id and identity) built for `aarch64-linux-android`, pushed to a Pixel 6a emulator (API 34) over `adb`, and run. Reported a node id and identity, and a bound UDP socket was visible in `/proc/net/udp` while the process slept. The `ndk-context`/DNS panic noted under 1.1 fired here too, on the main thread inside `SyncNode::spawn_with` — but see 1.1's corrected note below, it is caught internally and harmless.
  - iOS Simulator, done: the same logic as a `staticlib` (`pdn_spike_run` FFI entry point) linked into a minimal SwiftUI app (generated with `xcodegen`, no signing needed for Simulator) and run on an iPhone 17 (iOS 26) simulator. Reported node id and identity on screen. One linker gap found and fixed: `netwatch`'s iOS backend (`netdev`, via `nw_path_monitor_*`) calls `Network.framework` directly, and Xcode does not auto-link a framework only referenced from an opaque static lib — needed `-framework Network -framework SystemConfiguration` in `OTHER_LDFLAGS`. Outcome (a); the eventual `pdn-mobile` build recipe (tasks 5.3 and 5.7) needs to link both frameworks for iOS.
  - iOS physical device: pending, needs the interactive signing step below.
- [ ] 1.3 Two physical devices in one local network: mint an invite on one, consume it on the other, publish a grant on one claim, read it on the other. This is the whole change's premise (D7)
- [ ] 1.4 What a platform suspension does to a bound endpoint: suspend the application mid-session and record whether the node is reachable afterwards. If it is not, the single-bring-up requirement is the thing that changes — a host whose endpoint dies on suspension needs a re-bring-up act, which the requirement as written refuses (D2)
- [ ] 1.5 The failure a dial into one's own endpoint produces, on the 2 Android emulators that cannot reach each other: whether it arrives as unreachable or as a refusal. A permanent specification names this, so it is observed rather than reasoned about (D7)
- [ ] 1.6 On iOS, confirm the local-network declaration is what the traffic depends on: with it, the pairing of 1.3; without it, the silent drop — and whether a refused consent is observable at all, which the shells will need
- [ ] 1.7 On Android, determine what the target platform level requires for local-subnet traffic and whether a declaration is needed at that level. Nothing here depends on the answer; the shells do, so it is recorded
- [x] 1.8 Record what the generated bindings do about async: futures or callbacks, whether an opaque type crosses at all, and which shape is pleasant to call from a screen
  - uniffi 0.32 generates each asynchronous exported call as the language's own asynchronous form, with no callback anywhere: Swift gets `func bringUp(storageDir: String, reconcileIntervalSecs: UInt64) async throws`, Kotlin gets `suspend fun bringUp(...)`. A screen therefore awaits a call the way it awaits any other, and a refusal arrives as a thrown error of the generated error type rather than as a result to inspect.
  - The handle crosses as an object (Swift `open class PdnNode`, Kotlin `class PdnNode : Disposable, AutoCloseable`), and the records cross as generated data types — `GrantCapability`, `GrantedPath`, `GrantedClaimId`, `EntryListing`. An entry payload crosses as `Data` on Swift and `ByteArray` on Kotlin. Nothing opaque crosses.

## 2. The facade (`crates/pdn-mobile`)

- [x] 2.1 The crate: depends on `pdn-node` only, no `data-layer` dependency, built as a static library for both mobile targets beside the workspace's own (D1)
  - `crate-type = ["lib", "staticlib", "cdylib"]` — the static library iOS links, the shared library Android loads, and the `lib` the crate's own tests drive. The 2 target builds run in the pipeline (5.7); the development container has neither the NDK nor Xcode, so neither ran here.
- [x] 2.2 Bring-up and stop on a handle: one runtime per handle, an explicitly configured reconcile interval, stop safe to repeat, a second bring-up of the same handle refused (D2, D5)
  - Bring-up also names the directory the node's state lives in, because the runtime's spawn requires a storage choice and the embedder is the one that knows its sandbox — see the note under 2.16, which is where that decision leaves this change's spec.
  - The 2 races between bring-up and stop are handled where the state lives rather than in the caller, and both are asserted: the node is installed by the spawn's own task, so a cancelled call — a coroutine cancelled as a shell leaves the foreground — cannot strand the handle between its states; and a stop that overtakes a bring-up shuts the new node down and leaves the bring-up reporting the node as not up, rather than handing back a node its caller has already stopped and a directory nobody holds.
- [x] 2.3 Exported calls, one per service call: identities (create, list hosted), linking (mint, consume), invites (mint, consume), connections (list), grants (publish, read a peer's, read own, withdraw), entries (write, read, list), node id
- [x] 2.4 The claim derivation, in both directions and stated on the surface: a grant names claim identities derived from the issuer and an entry path, so publication takes paths and derives, and a grant read reports the derived identities. The facade exports the derivation so a caller can join a read against paths it knows or has listed (D8)
- [x] 2.5 Exported types: entry listing, connection list, grant publication, and both grant reads carrying the capability alone — issuer, claims, commands, no ticket, and no exported call accepting one (D3)
- [x] 2.6 Ceremony payloads: exported in the runtime type's own serde encoding, so any host over the same runtime consumes what this one produced, with a textual form a screen can draw as a code and rebuild from a scan. The facade names none of the payload's fields, and the live-secret exposure is stated in the crate's docs (D6)
  - The textual form is that encoding in a base64 alphabet, wrapped in nothing else, so what a scan recovers unwraps to the bytes the other host takes as a body.
- [x] 2.7 The error table, written out rather than referenced: the runtime's refusals separated by kind — an ungranted write, unsupported delegation, a refused ceremony — an unhosted identity or issuer, a peer not connected, an act already committed or in flight, a counterparty never reached, a dialogue that timed out, a catch-up that timed out, an unsupported payload version, and an unrecognized failure whose cause chain stays in the log. The divergence from `pdn-node-http`'s table is stated in the crate's docs with its reason (D4)
  - 3 kinds of the host's own sit beside those: a directory another running node holds, a call with no node up, and a second bring-up.
- [x] 2.8 The host's own pre-validation, named as the host's rather than the runtime's: an empty entry payload, a malformed entry path, and a grant naming no claim at all (D4)
- [x] 2.9 Entry payloads as raw bytes both ways with no framing of the facade's own, bounded by a stated ceiling per payload, and entry paths in the runtime's own form (D9)
  - The ceiling is 1 MiB, against the HTTP host's 64 MB: the same buffer on a device that is killed for memory rather than asked to swap. It bounds the write and not the read, which the requirement now says outright with its reason — an entry a peer wrote through the other host is in the replica whatever its size, and refusing to hand it over would make a granted claim unreadable instead of making the device safer.
- [x] 2.10 The read that answers nothing: one reported absence covering both no entry and a record whose payload has not arrived, stated in the crate's docs as the thing a caller must not conclude from
- [x] 2.11 Listing: issuer, path and payload length with no payloads fetched, an optional prefix matching whole path components, and an issuer this node holds nothing of reported as the unknown-issuer refusal rather than an empty list
- [x] 2.12 Grants: publication naming the issuer and the claims with a per-claim write flag, republication replacing the previous record, withdrawal as one act naming peer and issuer, a foreign issuer's refusal passed through, and both reads reporting what is readable now without waiting
- [~] 2.13 Ceremonies bounded: every exported ceremony call reaches an outcome within a bound, and the linking consume takes the caller's bound for the whole act — the dialogue spending from it first, the catch-up taking the remainder — reporting its own failure after rolling back
  - The linking consume takes the caller's bound and passes it through as the budget of the whole act. What is not asserted here is the rollback and the catch-up's own failure, which the runtime's suites hold; the facade adds nothing to either.
- [x] 2.14 Asynchronous across the boundary, with the asynchronous runtime owned by the facade and no exported call requiring the caller to hold a lock across it. Where a caller's continuation resumes is the caller's, and no requirement here claims it
  - The handle owns a tokio runtime, every call runs on it, and the state lock is taken and released without an await in between. A handle released without a stop shuts its tasks down in the background rather than blocking the thread that let it go.
- [x] 2.15 The facade authorizes nothing: no credential, token or permission of its own on any exported call, stated in the crate's docs beside the fact that reaching it is reaching the node
- [~] 2.16 Volatility and the keyless identity stated in the crate's docs, as context quoted from the runtime's own specs rather than as this surface's own claims: what a stop loses, and that a connection is evidence 2 devices ran a ceremony with one secret and nothing more
  - The keyless identity is stated as written. Volatility is not, because the runtime is no longer volatile: `SpawnOptions` requires a storage choice, `pdn-node` re-hosts what its `hosted-identities.json` record names, and `pdn-node-http` has required a directory for as long as it has existed. The crate's docs and `tests/surface.rs` therefore say what the runtime does — a node comes back on its directory as itself, under the same node id, and what does not come back is work in flight. This contradicts this change's own delta, whose requirement "The host repeats what the runtime says about its state" carries the scenario "A restart is a new node", and the proposal's deferred "On-disk persistence". Those 3 places need rewriting against the runtime as it stands; the facade is not what should change.

## 3. The facade's tests

- [x] 3.1 Two handles against two runtimes in one test binary, driven through exported calls alone: create identities, invite, establish, publish a grant, write an entry, read it back through the grantee, withdraw and watch access close — no ticket in the test body, no direct service call, waiting done by repeating the read
  - `tests/surface.rs`, one scenario: 3 handles, the connection established from a minted payload, the grant published and read from both halves, the value read through the grantee, the republication replacing rather than accumulating, the withdrawal closing the access and a re-grant reopening it.
- [x] 3.2 The paired denial of that positive, in the same place: a third handle whose identity is connected to neither side obtains nothing of the granting identity's data, probed after the grantee demonstrably read it ([access-control-tests](../../specs/code-practices/access-control-tests.md)). The second read negative that rule names — a ticket without a capability — cannot be staged here, because no ticket crosses the facade; it stays with the runtime's own suites, and the test's docs say so
  - The read-only claim's refused write sits beside it, with the previous value asserted to stand.
- [x] 3.3 The error table asserted directly, each kind to its own and an unmapped error to the unrecognized one — the table is what every paired denial rests on, so it is tested as a table rather than only through calls. The 3 ceremony outcomes are asserted at whatever granularity the runtime actually separates them at, which 1.5 and the linking budget's own behaviour settle
- [x] 3.4 The host's own pre-validation asserted beside the well-formed call it is the near miss of: an empty payload, a malformed path, a grant with no claim
- [x] 3.5 Bytes in, bytes out for an arbitrary payload up to the ceiling and refused above it; a prefix matching components rather than characters; an unknown issuer refused rather than answered empty; a claim identity derived from a path matching the one a grant read reports
- [x] 3.6 A ceremony payload minted through the facade parsed by `pdn-node-http`'s own decoding, and the reverse — the interop 2.6 exists for, and the only assertion that catches a divergence before a person meets it in a room
  - The decoding asserted against is `serde_json` over the runtime's own payload type, which is what that host's body parsing is; the round trip ends in a consumed invite rather than a parse alone, so a divergence fails the establishment and not only the assertion.
- [~] 3.7 Each scenario above proven to fail with its mechanism deliberately broken — a test that passes either way asserts nothing. The absences of 4.1 are excluded: an absence cannot be broken, which is why it is not a test
  - 2 of the headline scenario's mechanisms were broken and the test failed on each, at the assertion that names it: with the grant publication turned into a no-op it fails on the own-grant read finding nothing published, and with the withdrawal turned into a no-op it fails on the access it should have closed staying open. Both mutations were reverted and the suite re-run green.
  - A third: with the install's stop-overtook check removed, the scenario that covers a stop racing a bring-up fails on the node still answering after the stop.
  - What is not yet done this way: the ceremony's own path (a payload minted but not delivered), the claim derivation, the listing's prefix, and the bounds of the host's pre-validation.
