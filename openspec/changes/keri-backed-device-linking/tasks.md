- [ ] 1.1 Validate, implement, and land `durable-runtime-storage`: persistent documents/blobs, protected endpoint/runtime-author/generic secret records, prepared-replica handles, successor runtime-security records, conditional batches/intents, and reopen tests. This is a hard dependency; no implementation task below begins before it lands.
- [ ] 1.2 Implement the selected narrow 3-event KERI profile over the workspace's Apache/MIT-compatible BLAKE3 and Ed25519 primitives; do not link `keriox`. Incept a root, incept a delegate, anchor it, verify the chain, and cross-check the exact bytes with pinned `keripy` as an external oracle.
- [ ] 1.3 Implement the exact normative `pdn-node-keri-wire-profile`: KERI 1.0 compact JSON field order and size bytes, canonical `u64` sequence domain, the fixed full-qb64 CESR prepad encodings for `D`/`E`/index-0 `A`, the BLAKE3 digest of the exact 44-byte qualified next key, BLAKE3-256/Ed25519 algorithms, thresholds, di-only delegation, indexed signature bytes, and store-commitment construction. Reproduce the included root/founder/anchor golden vector byte-for-byte with both our implementation and pinned `keripy` `v1.0.0` commit `6478fee8688a0a3e978827d5327f8fd05e3d3737` before protocol code is accepted; do not strip visible CESR characters before base64 decoding or choose alternate encodings.
- [ ] 1.4 Implement the selected tree topology from design D2: any device may invite; no operation in this change acts on another device; a device identifier is not a permanent domain name; and a later re-inception/recovery change owns migration after delegator loss.
- [ ] 1.5 Implement the wire profile as the sole owner of the shared bounds: complete `PDL1` body 65,536 bytes and signed-event material — exact event JSON plus 88-byte indexed signature — 61,440 bytes. Apply the latter identically to request inception, reply event, `KEL1`, and accepted-head reconstruction producers/readers; no stored accepted event may be unreplayable. Enforce reply bundle 1,968 events — the largest flat inventory whose `572 + 33 * N` manifest fits one body — and 16,777,216 body bytes, depth 32, and 1,024 events per identifier. Reserve 1 level, 1 inviter event, the maximum anchor-frame contribution, and 33 manifest-inventory bytes; size the prospective manifest before anchoring. Use 1 absolute caller deadline with remaining-time semantics across all phases.
- [ ] 1.6 Implement the exact canonical transcripts, signed-object digest, `KEL1`, `PDO1` offer, `PDR1` timestamp wrapper, both `PDB1` proof variants, and the manual frame bodies. `Linked` has 3 signatures; `Created` has founder and root. Reproduce the normative length/digest/signature vectors for every transcript and container plus the complete `KEL1` and `0x02` hex, body, and inventory; reject trailing/non-canonical encodings and permit no serializer-selected alternative. Reconstruct request bytes from authenticated endpoint identities; never decode a request-preimage or claimed `NodeId` from the request frame.
- [ ] 1.7 Keep existing `PdnOp::{AddDevice, RevokeDevice, RotateKey, ActiveDevices}` reserved: do not emit, accept, or map them to this service's create/link/forget paths, update their current source comments so they describe reserved placeholders rather than working authorization/revocation/recovery operations, and add boundary tests proving the deferral.
- [ ] 1.8 Keep implementation and documentation aligned with accepted ADR-0003; when this change lands, update ADR-0012 to point at the version-1 replacement without rewriting its historical version-0 rationale.
- [ ] 1.9 Fix the wording of the threat model the specs are read against: the chain as authorization, the inviter's signature over the nonce as the challenge and its response, the anchor as reusable authorization with no freshness, the manifest as an inventory that cannot reveal events omitted from both inventory and stream, and what a substituted payload, photographed secret, unseen fork, linkability, and leaked directory ticket leave open. State only the implemented local rule that a pinned accepted prefix is not silently rewritten. Do not claim KERI accountability or the direct-mode threshold of 1 without a validator-signed receipt. Retain the separate whitepaper fact that a superseding rotation higher in a delegation chain can recover keys at lower levels, which this change neither implements nor rules out.

## 2. Types and key material

- [ ] 2.1 Give `Aid` its qualified form in `pdn-types`, correct its doc comment — it is the digest of an inception event under the pinned derivation, not an inception public key — and add the canonical mapping to and from the 32-byte `PdnId`, with round-trip tests against the golden vectors.
- [ ] 2.2 Add the key store through the durable profile's protected versioned secret records: current and pre-rotated device keys per identity and root keys. Enforce owner-only permissions where supported, exclude all key bytes from catalog/diagnostics/errors, and fail reopen on missing, malformed, unreadable, or permission-invalid records without generating replacements. No exported recovery copy.
- [ ] 2.3 Remove the empty `PdnIdentityProof` type and `Claim::proof_of_issued_by` field. Treat `issued_by` as attribution only, reject the old serialized claim shape rather than silently accepting an empty proof, regenerate fixtures, and leave a future counterparty-proof change to add a new versioned proof type with actual verification semantics.
- [ ] 2.4 Before creating any root/device key record, persist the identity-creation outer intent with every preallocated secret handle/type and non-secret recovery input. Activate the creation record only after all handles are registered; otherwise recovery completes that exact owner or deletes all its handles. The active record then carries opaque prepared-replica handles, role-tagged commitments, inception configuration, founder `dip`, root seal, and current boundary, keeping all 3 events deterministic without raw namespace identifiers above `data-layer`.
- [ ] 2.5 Before creating attempt keys, persist the linking-attempt outer intent with its preallocated handles, identity, inviter AID, and exact local `NodeId`. Activate the attempt record only after all key handles are registered, and test every registration/activation crash boundary. Add the read path a same-endpoint retry resumes from and discard superseded attempts plus their owned keys. If an explicit endpoint reset changes the local node id, discard that endpoint-specific attempt, its device keys, and local proof before dialing, assemble a new inception, and preserve pinned identity heads.
- [ ] 2.6 Resume every unfinished creation at startup before the service accepts a new `create`, publish recovered identities through `hosted_identities`, and preserve the existing call's non-idempotent meaning: every admitted call starts another identity. Test that an uncertain caller retry creates a second identity rather than consuming an uncorrelated record; caller-idempotent creation requires a later API change with an idempotency key.
- [ ] 2.7 Add the explicit forget operation to the identity service — the only path that removes pinned heads, ceremony record, and key material — with the displaced-binding care the linking rollback already has, and distinguishable in the surface from that rollback.
- [ ] 2.8 Keep key material, creation records, and attempt state separate per identity.
- [ ] 2.9 Register KERI security-state schema `1` in the durable catalog and implement the exact `accepted-head`, `ceremony`, `pending-observation` plus active index, and `kel-problem` families. Every accepted head retains an ordered, content-digested set of exact canonical `KEL1` event/signature bytes from inception through head plus the delegation seal's event location and list index; an advancing head preserves the former reconstruction as a byte-identical prefix. Ceremony snapshots store `{aid, sequence, SAID}` and use generation only as a commit guard, so startup validates old ceremonies against prefixes of current heads rather than requiring obsolete generations. Startup re-verifies without directory payloads before identity/session admission. Replay all intents; forget removes the whole identity prefix through its outer intent.

## 3. Key events in the directory

- [ ] 3.1 Add `kel/<aid-hex>/<sn-16hex>/<event-content-digest-64hex>` where the storage digest is BLAKE3-256 over exact final event bytes and is explicitly distinct from the event's dummy-serialization `d` SAID. Store only the wire-profile-defined canonical `KEL1`, enforce its shared 61,440-byte signed-event-material limit before allocation/admission, reject alternate tags, lengths, attachments, and trailing bytes, and check identifier, padded sequence, content digest, and SAIDification independently.
- [ ] 3.2 Enforce the authorship rule: a device writes the events it controls — its own, and the root's while it holds the root's keys — and never re-authors another device's event.
- [ ] 3.3 Build the runtime-owned validated view, the sole normative implementation of accepted-head, awaiting-delegation, gap, and discrepancy semantics. First decode exact `KEL1`, recompute the final-byte event-content digest for the entry key and independently reconstruct the dummy-serialization `d` SAID, then check identifier and sequence before signatures, chaining, and external authorization prerequisites. On every head change conditionally persist the complete reconstruction set and seal index with the head before admission. Keep `data-layer` limited to candidate enumeration, payload integrity/readability, and payload-arrival notification. A delegated inception or rotation stays awaiting until the accepted branch of its fixed delegator carries the matching seal; an out-of-order event stays pending until its gap closes; a contradicting event stays retained and reported.
- [ ] 3.4 Persist key-event problems in the versioned `kel-problem` family and expose them through the runtime: durable across reopen, enumerable per identity, typed as competing event or malformed content address, and atomically created/cleared with any accepted-head verdict based on the same evaluated input.
- [ ] 3.5 Test that two events at one position coexist as separate entries and neither displaces the other, that two authors writing identical bytes are two records, that alternate/trailing `KEL1` payloads and a payload whose identifier, sequence number, or recomputed digest does not match its entry key never enter the accepted view, that an out-of-order event is not mistaken for a discrepancy, and that a delegated inception received before its seal establishes no head but is re-evaluated after the seal reaches the delegator's accepted branch.
- [ ] 3.6 Test that a device's own writes are checked on the view's path — the ingest hook never sees them.
- [ ] 3.7 Replace the record-only `SessionAccess::Full` probe with the runtime-only, whole-identity `IdentityAccessProjection` API. Make `data-layer` generation-count every relevant device-record/payload-state input, synchronously close and notify `pdn-node` on change, and reject projections over stale input. Make `pdn-node` produce monotonically generated decisions bound to that input generation, exact proof digests, and `{aid, sequence, SAID}` head snapshots; make `AccessBook` consume them opaquely and host identities closed by default. Grant only after durable KERI commit. For any possibly revoking update, use a cross-backend intent to close first, invalidate deposited write admissions, terminate active Full-authorized sync sessions, atomically replace the whole projection, and remain closed across crashes. For `Linked`, require request + manifest + newcomer confirmation, exact path/peer endpoint, commitments, and accepted chain; for `Created`, require founder + root signatures and direct root delegation. Preserve listing and independent grant access; fail closed on conflicts without waiting for reconciliation.

## 5. The `/pdn/linking/1` exchange

- [ ] 5.1 Implement the request and reply frames from the normative profile: signed request, inventoried signed-event frames, signed manifest, and tickets. Both readers reject an announced body over 65,536 before allocation/read; the request carries no preimage or claimed NodeId and is reconstructed from authenticated endpoints. Request and manifest bind both endpoints and ceremony values; newcomer confirmation is created locally after verification. Step ALPN and payload version to 1.
- [ ] 5.2 Implement the inviter's checks of the presented inception: delegator is this device, identifier is the event's digest, signatures verify at the declared threshold, pre-rotation commitment non-empty.
- [ ] 5.3 Implement the inviter's critical section in design D6, with the log locked across uniqueness lookup, snapshot, anchor, manifest signature, and pending-offer write. Same-endpoint retry is idempotent; another endpoint is refused; no second seal is written over an already sealed inception.
- [ ] 5.4 Implement the streamed reply and `PendingRecord`: preserve the signed request, sign the exact manifest, and wrap those exact 2 objects as `PDO1` with inviter creation time in `PDR1`. Create first-observed state only after canonical wrapper, path/endpoint, signatures, anchor, chain, subject AID, hosted identity root, and accepted inviter membership verify. Maintain one active digest per subject. Unreadable input creates no new state; temporary unreadability preserves any prior verified observation/index, makes lookup and expiry indeterminate, and cannot refresh its time. Delete stale observations only for readable proven-invalid/cross-directory payloads or authoritative removal, confirmation, or tombstone. Same-endpoint supersession uses a cross-backend intent so recovery retains exactly the observation matching the pending payload and removes the old one. Do not construct `DeviceBindingProof` on the inviter.
- [ ] 5.5 Check the bounds at all three points, with the reservation of task 1.5 at invite time, and refuse minting an invite for a device whose own bundle is already over one or has no room for what redemption adds. Under the KEL lock, compute the exact post-anchor snapshot and `572 + 33 * N` manifest body before writing the anchor.
- [ ] 5.6 Extend `LinkingLocalFailure` with the anchor-write and bound-exceeded variants, so a post-burn failure is diagnosable rather than only refused.
- [ ] 5.7 Implement the newcomer's verification: every event's signatures under the key state its own log establishes at that point; the chain from the payload's identity to the payload's inviting device; each delegation's seal; the internal consistency of every log in the reply; the anchor over its own inception; the manifest against the frames received and against the nonce it sent.
- [ ] 5.8 Hand both canonical ticket blobs, both sealed commitments, and the authenticated inviter fallback to `data-layer` together. Require the opaque `VerifiedBootstrapPair` and import only by consuming it; never decode or mutate tickets in `pdn-node`. Test that substituted bytes, swapped roles, another fallback, handle reuse, and restart from remembered verdicts cannot import. Leave grant paths unchanged.
- [ ] 5.9 Enforce the byte and event bounds while reading the reply — stop and refuse on the frame that crosses one, rather than after the stream ends.
- [ ] 5.10 Through one conditional runtime-security batch, commit every accepted head with its complete exact `KEL1` reconstruction set and seal index plus the exact signed request, signed manifest, anchor, and `{aid, sequence, SAID}` accepted-head snapshot before imports; recorded generations are commit guards, not permanent references. Reopen MUST re-verify each snapshot as a byte-identical prefix of the current reconstruction set even after a legitimate head advance. After consuming the verified ticket pair, atomically extend that ceremony record with canonical newcomer confirmation, documented as a signed assertion of successful local pair verification/import rather than reproducible proof of ticket bytes or capability verdicts. Use owner intents for confirmed/pending directory writes. Reduced fields are forbidden; rollback keeps the verified offer and pins while removing replicas, bindings, and hosted entry.
- [ ] 5.11 Build the local device-identifier lookup over verified pending and confirmed proofs. Treat the same identifier and node id idempotently, refuse another node id in either state before anchoring, and make an unavailable payload indeterminate without waiting in the critical section. Detect several valid confirmed node ids for one identifier as an observable conflict that denies full access to all of them.
- [ ] 5.12 Write the newcomer's inception, verify the exact pending offer and successful consuming import of the byte-bound bootstrap pair, sign and durably record the canonical newcomer confirmation, then write the resulting 3-signature `Linked` proof to confirmed — confirmed first, pending tombstone second, both idempotent. This adds no round trip. After the commit point, resume only tombstone cleanup.
- [ ] 5.13 Surface a reply cut off mid-stream as its own typed outcome within the caller's budget.
- [ ] 5.14 Add the closed typed verification outcome. A bootstrap failure is a nonempty list of every failed role, ordered directory then data, with the total mapping `CommitmentMismatch` → `StoreCommitmentMismatch`, `InsufficientCapability` → `BootstrapTicketInsufficientCapability`, and `MalformedTicket` → `BootstrapTicketMalformed`; no successful role appears and no simultaneous failure is discarded. Thread it through `link` and map it in the host's error table without exposing the reason remotely.
- [ ] 5.15 Add the host route for the forget operation, under the surface requirement that admits it.

## 6. Tests

- [ ] 6.1 Positive: linking completes, the newcomer's chain reaches the identity, the 2-store set comes up, and device sets converge — including a third device linked from a non-founder. After the second device joins, it accepts the founder's `Created` proof and data replicates in both directions between founder and newcomer.
- [ ] 6.2 Substituted identity: the inviter answers with valid tickets and a chain rooted elsewhere; the link fails, nothing is imported, no identity is hosted.
- [ ] 6.3 Anchor negatives: an unanchored inception, and an anchor over another inception.
- [ ] 6.4 Inception negatives on the inviter's side: a foreign delegator, an identifier that is not the event's digest, a bad or under-threshold signature, an empty pre-rotation commitment.
- [ ] 6.5 Replay consistency negatives: two events at one position, a broken prior-digest chain, and a chain ending at a device other than the payload's.
- [ ] 6.6 Signature negatives on the replay: an event whose signature does not verify under the key state its log establishes, and the attack the structural checks alone would admit — a genuine identity's real inception followed by a delegating interaction event signed with the attacker's keys.
- [ ] 6.7 Store-set negatives: a verifying chain with another identity's commitment, a forked pair, a role swap, a matching read-only ticket, malformed ticket text, simultaneous unlike failures in both roles, substitution after verification, another fallback address, and reuse of a consumed pair. Assert the total typed directory-then-data mapping to every applicable `StoreCommitmentMismatch`, `BootstrapTicketInsufficientCapability`, or `BootstrapTicketMalformed`; only the exact verified pair imports, its raw capabilities appear only in the temporary protected secret record and never catalog/diagnostics, `pdn-node` never receives either namespace identifier or decoded ticket, pairing metadata does not extend the set, and a valid grant import remains allowed.
- [ ] 6.8 Nonce negatives: a reply whose manifest signature covers a different nonce is refused, and a reply captured from an earlier successful ceremony is refused when presented in a new one.
- [ ] 6.9 Manifest negatives: refuse when an inventoried frame is missing, changed, extra, reordered, or the stream ends before the signed inventory is satisfied. Do not assert detection of valid events omitted from both stream and manifest when no prior pin or witness exposes them.
- [ ] 6.10 Transcript and binding negatives: cross-connection replay; wrong domain; copied complete proof under another path; request/manifest endpoint mismatch; a pending offer copied into confirmed under the same path; missing or forged newcomer confirmation; and any non-canonical/trailing transcript bytes.
- [ ] 6.11 One test per bound at each applicable checkpoint: inviter and newcomer reject a body prefix over the same profile limit before allocation/read; inviter request inception, newcomer reply event, stored `KEL1`, and accepted-head reconstruction all reject the same signed-event material at 61,441 while accepting 61,440; a 1,968-event inventory yields a 65,516-byte manifest body and is accepted while 1,969 would yield 65,549 and is refused at minting and under the pre-anchor snapshot check; an event admitted to storage round-trips into a valid `PDL1/0x02`; and a hostile inviter is cut off while reading rather than after the stream ends.
- [ ] 6.12 Uniformity: every refusal above is indistinguishable to the dialer.
- [ ] 6.13 Residue before confirmation commit: after a failed or cancelled link the runtime holds no replica, binding, confirmed record, or hosted entry, and still holds the attempt, the pinned heads, and the ceremony record; the reservation is released once rollback completes. After confirmation commit, cancellation does not roll the identity back and only pending-record cleanup may remain.
- [ ] 6.14 Idempotency and endpoint binding: 3 interrupted same-endpoint attempts against 1 inviting device leave 1 device identifier and 1 seal; a retry after restart likewise; another inviter starts a new attempt; and an explicit local node-id change discards the endpoint-specific attempt and keys before dialing, creates a fresh inception, and preserves pinned heads.
- [ ] 6.15 Pinning: a retry presenting a different history for the same identity is refused; a legitimate anchor written when the next device links advances the head instead of registering as a discrepancy; after B is confirmed and B anchors C, restart validates B's older ceremony snapshot as an exact prefix of B's advanced reconstruction set without requiring its old catalog generation; pinning survives restart.
- [ ] 6.16 Forgetting: it removes pinned heads, ceremony record, and key material where a rollback does not; a later link into the same identity starts unpinned; a namespace of the same issuer reached through a peer's grant survives.
- [ ] 6.17 Crash points from design D11: creation around replica preparation/recording, root `icp`, founder `dip`, root `ixn`, issuer bind, founder proof, and hosting; 2 interrupted creations; a linking crash before the confirmed-record write rolls back; a crash after it preserves the hosted link and resumes only the pending tombstone; and a failure between directory import and the pre-confirmation hosted entry.
- [ ] 6.18 Operating conditions: a full disk on the inviter's anchor write after the burn refuses uniformly with a local diagnostic; a full disk while the newcomer commits pinned heads or the ceremony record fails before import without weakening prior pins; two linkings against one inviting device do not interleave; one runtime's identities do not share ceremony state.
- [ ] 6.19 Access-control pairing and projection: chain without confirmed proof receives only grant access; copied `Linked`/`Created` proof receives no Full. Positive `Linked` requires 3 signatures and `Created` 2, joined with path, peer, and accepted chain. Start hosted identities closed; reject stale/partial/skipped projection generations. After an endpoint already has Full and a conflicting proof appears, assert that conflict processing synchronously closes both endpoints, removes deposited write admissions, terminates active Full-authorized sync sessions, and denies further reads/writes without waiting for reconciliation; crash at every close/install boundary remains closed while independent grant access survives.
- [ ] 6.20 Golden vectors: our events validate under `keripy`, deliberately corrupted `keripy` events are rejected by us, the root-`ixn` `KEL1` matches its normative 410-byte hex and BLAKE3 digest, and those exact container bytes round-trip to and from the fixture's `PDL1/0x02` body without changing event or indexed-signature bytes.
- [ ] 6.21 Protocol version: a payload of an unsupported version is refused before a connection opens, and a dial on the previous ALPN gets no ceremony.
- [ ] 6.22 Root authority: a device that holds no root keys cannot anchor a delegate of the root — the negative that survives the root-export decision, since it depends on no export at all.
- [ ] 6.23 Device-identifier uniqueness: a same-endpoint retry is idempotent; the same inception from another node id is refused while pending and while confirmed; 2 concurrent endpoints cannot both pass the locked lookup; an old endpoint cannot confirm a second binding after another endpoint's refused presentation; several conflicting confirmed proofs injected as replicated state fail closed for every endpoint; and an unavailable payload is indeterminate rather than absence.
- [ ] 6.24 Runtime-security durability: stop before/after atomic head+ceremony batches, confirmation extension, KEL problem create/clear, every access-projection close/install boundary, and every pending-supersession intent/directory/batch boundary. Also stop after reply acceptance but before any corresponding KEL entry payload replicates: reopen re-verifies exact durable reconstruction sets and seal indexes without arrival-order inference. Reopen exposes all old or all new generations, validates older ceremony snapshots as exact prefixes of advanced heads, keeps device-derived access closed until KERI state and one complete projection agree, retains the original observation while a formerly verified payload is unreadable, creates no state for arbitrary invalid writer payloads or a valid offer copied from another identity's directory, performs no expiry/tombstone action from either, and admits no identity service before intent replay.
- [ ] 6.25 Startup creation recovery and replicas: a prepared replica whose opaque handle never reached the creation record is not adopted; recovery uses the recorded handles and commitments, exposes the identity through `hosted_identities`, and never surfaces namespace identifiers above `data-layer`; a subsequent `create` produces a distinct identity; 2 interrupted records recover independently.
- [ ] 6.26 Confirmed endpoint loss: missing endpoint secret fails reopen without replacement; a replacement node id receives no access from an old proof; a linked device can only forget and re-link through another inviter; and a founder is not silently forgotten, re-incepted, or root-signed as an implicit repair.
