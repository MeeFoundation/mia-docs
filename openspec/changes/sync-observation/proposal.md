# Proposal: sync-observation

## Why

Two tests measure sync in a [pod](../../specs/architecture/language/pod.md) from outside the nodes, and neither can read what it measures. The load tests (`mee-pdn/sync-test/load.md`) ask how CPU and sync speed grow with the number of member nodes and the volume a pod holds, once with every node on the laptop and once with the phone as the measured node, and whether the laptop-only run is honest for each number. The reliability test (`mee-pdn/sync-test/design.md`) decides whether an entry was lost by comparing what a reader holds against the sessions that should have carried it. Both read the same event record and the same run directory, fixed in `mee-pdn/sync-test/plan.md` ("Shared interfaces"), and both measure release builds only, since a debug build of the store is several times slower.

Nothing they need exists. No host exposes the engine's events: `pdn-node` has no subscription to a pod's stores, `pdn-node-http` has no route for one, and the mobile facade has none. The events the engine does produce cannot carry the reliability test's rule: `Engine::subscribe` in `crates/pdn-store/src/engine.rs` merges two channels with `or`, so a session's `SyncFinished` can reach a subscriber before the entries that session inserted, and both channels drop events past 256 (`SUBSCRIBE_CHANNEL_CAP`), so a session of 1,000 entries overflows them. A session event names no counterpart session, says nothing about the stage a failure happened at, and loses its counts when the teardown fails. The record view with each entry's verdict exists only as `pod_record_view_for_test` in `crates/pdn-node/src/runtime.rs`, which no host serves, and its entries carry a content hash only once the payload has arrived. A joiner's first sessions cannot be observed at all: `join` in `crates/pdn-node/src/pods.rs` starts both stores' sync inside the import and waits for their first sessions before it returns, so whatever they carry is inserted before any subscription to the pod can exist. The facade's runtime names none of its threads, so a sampler on the phone cannot tell the node's CPU from the rest of the application's. `pdn-node-http` brings the runtime up at the default pod interval of 300 seconds (`POD_RECONCILE_INTERVAL` in `crates/data-layer/src/node.rs`) with no way to set another, while the reliability test sizes its stall deadline from an interval it chooses. Neither host says whether it is a release build.

This change adds an observation surface for tests, from the store up to the two hosts and the application's test build, and nothing else. It is test instrumentation in the sense of [product-path-arrangement](../../specs/code-practices/product-path-arrangement.md): it observes, never arranges, and it is absent from every build that ships.

**Example:** record `by/<w3>/immutable-document/<id>/1` placed by writer w3, read by the phone. What the phone's subscription to the pod yields for the record-store session that carried it, in `seq` order:

| `seq` | `kind` | `store` | fields |
|---|---|---|---|
| 8,204 | `sync_finished` | `membership` | `origin` `connect`, `peer` w5's node, `ok`, `session` `51c0…` |
| 8,211 | `insert_remote` | `records` | `key` `by/<w3>/immutable-document/<id>/1`, `entry_ts` 41.203 on w3's clock, `from` w5's node |
| 8,212 | `content_ready` | `records` | the payload's hash |
| 8,219 | `sync_finished` | `records` | `origin` `connect`, `peer` w5's node, `ok`, `received` 12, `session` `9f3a…` |

w5's own subscription yields a record-store `sync_finished` with `origin` `accept`, `sent` 12 and the same `session`, so the test pairs the two sides by that value, and seeing 8,211 before 8,219 on the phone proves the entry arrived within that session. The load test reads the same records for other numbers: 8,212's `t`, corrected by the phone's clock offset, minus 41.203 is the record's latency on the phone, and the number of distinct record-store `session` ids with `received` above 0 across all nodes during the steady workload, divided by the records placed, is the sessions per record: the phone's `9f3a…` counts once though w5 reports it too, and a session that carried nothing does not count.

## What Changes

- **An ordered subscription in the store.** `pdn-store` gains a subscription to one replica whose events all come from the live actor, which already sees every insert before the result of the session that made it. A session's inserts are then reported before that session's `SyncFinished`, and a content download's `ContentReady` after the insert it belongs to. The product's existing subscription is unchanged.
- **A bound on loss that a 1,000-entry session fits.** The ordered subscription names its capacity, 4,096 events for observation; past it, events are dropped behind one lag notice, as every subscription outside the store already is, and nothing waits on the subscriber. A replica dropped under the subscription ends it.
- **A session event that pairs and explains itself.** Each session event over a connection carries a session id both sides derive from the connection's keying material (nothing new crosses the wire), the stage a failure happened at (`connect`, `remote_abort`, `sync`, `close`), and the counts of entries sent and received whenever the exchange completed, a failed teardown included.
- **The runtime's observation calls, behind `test-util`.** `pdn-node` offers one subscription per hosted identity and pod covering both of the pod's stores, numbered as one stream in the shape `plan.md` fixes, each record naming its store, with `closed` when the record store is forgotten on a removal or a leave; a task of the runtime's own takes the stores' events as they come, stamps and numbers them whatever the consumer's pace, and holds the records for the consumer behind a second bound of 262,144, past which a `lagged` record says what was lost; an observed join that opens that subscription before either store's sync starts, so a joiner's catch-up is observed from its first insert; and the record listing — per record-store entry its key, author, hash, length, payload presence, payload and verdict — built on the existing record view.
- **The laptop host.** `pdn-node-http` gains a cargo feature `observation`, off by default, that adds 3 debug routes delegating to those 3 calls; the event route, and the observed join route once its join has answered, stream JSON Lines over one long response, hold no admission permit, and open streams have a bound of their own. `PDN_POD_RECONCILE_INTERVAL_SECS` sets the pod interval in every build, and 2 more settings of every build arrive with it: `PDN_CONNECTIVITY` chooses direct paths, relays, or the relays and address lookup a device runs with, and `PDN_ANY_ORIGIN` opens the debug subtree's answers to a browser page of any origin for the demo's screens. The status route reports the build profile and whether the observation surface is compiled in. The observation build compiles and is checked as a release build. The container stand's default image builds without the feature and a build argument makes a second image with it.
- **The product live actor's held dials.** A fix of the product path, found as the root of the observation scenarios' flakiness and kept in `crates/pdn-store/src/engine/live.rs` for every build: a dial of a pod's membership store refused as already syncing no longer releases the record store's dials held behind it; they are released when that exchange ends, when the redials are exhausted, by the resync an exchange is queued behind, or by the drop of an in-process request. The record store is then judged on the membership the running exchange brings, which is the order the pod-store spec requires.
- **A join after a departure starts the record store once the membership view shows the join.** A fix of the product path in `crates/data-layer/src/node.rs`, for every build, the second root of the same flakiness: on a device holding the pod's tombstone, the record store's sync starts once the view lists the identity as a member again, at most 5 seconds after the membership store's start, so its first session is judged by the join and `join` returns with the records placed in the member's absence.
- **A pod's stores are first started by the start that registers them.** In `crates/data-layer/src/node.rs`, for every build: the periodic pass, the dials of the identity's own devices and the membership store's watcher leave a pod alone while its start is in flight, so a subscription the start attaches sees the first session whole, and the record store's dial queues behind the membership store's as the pod-store spec requires, instead of by the timing of the pass.
- **The phone.** `pdn-mobile` gains a feature `observation` that serves the laptop host's debug and observation routes on the phone's loopback, beside a reset that brings a node up at the pod interval and the connectivity it names, the device's samples and the device's clock, and names its runtime's threads in every build; `pdn-sdk` packages a test build with it, in the release configuration, that no release carries. `pdn-app` gains a test build, in its release configuration, holding an agent: a screen of its own; a native module that reads the launch environment and starts the surface, keeps the idle timer off while the launch lasts, and samples once a second the CPU of the node's threads and of the whole process, the resident memory, the thermal state, Low Power Mode, the battery and the application's state, and every change of that state, so a window in which the application was not active is told apart as invalid. The test's coordinator reaches the surface over the phone's cable through usbmux, so nothing on the phone listens on the local network, and no record crosses the Wi-Fi the measured sync uses or JavaScript.

## Out of Scope

- **The coordinator, the load runner and the classifier.** They live in `mee-pdn/sync-test/`, with the phone's build and checks in `pdn-app/sync-test/`, and read the records this change defines; how they measure and classify is `load.md`'s, `design.md`'s and `plan.md`'s.
- **Whether a failed teardown fails a session, and the dialer's `Abort`.** That is the `session-outcome` change; this change reports what the session reports.
- **Download failures.** No event reports a failed download; a payload that never arrives shows at the final record listing as an entry whose payload is absent.
- **Whether a connection is direct or relayed.** Both tests use direct paths; the report per connection belongs to a relay variant.
- **The counterpart's member in a session event.** A session event names the counterpart node. The accepting side knows which member the caller acts as only from the caller's own first message, so it is not reported as fact; both tests host one identity per node, which makes the node name the member.
- **CPU and memory of laptop nodes.** The load runner reads them with `ps`; nothing in the host reports them.
- **Stores outside pods.** The subscription addresses a pod's two stores; the private metadata store (PMS), the connection metadata store and a data namespace received under a grant keep the product subscription alone.
- **Operating conditions left out:** a device linking before, during or after is not a condition of this surface — a sibling's session appears with the sibling's node as its peer and changes nothing here; a member promoted or demoted changes what the membership fold counts, which is the subject the tests measure, not a property of the observation; a write to several places at once does not occur, since the journal is one append-only file and the observation writes nothing else.

## Relation to active changes

- **`mobile-host-surface`** states that the facade "SHALL build with that feature disabled" and exports nothing test-only ("The exported surface is exactly this set"), and that no call offers a convenience the product lacks. This change keeps both for every build that ships and adds a test build that exports the observation calls, a bring-up with a pod interval and the build profile. The two texts contradict each other as written. This change archives after `mobile-host-surface`, and before it archives, those two requirements gain the qualifier "in a build a device installs" — in `mobile-host-surface` before it archives, or as MODIFIED deltas here once it has. The same holds for its `pdn-sdk` requirement "A release is built in the configuration a device installs", which this change keeps and supplements. `mobile-host-surface` carries its `pdn-sdk` delta twice (`specs/sdk-artifacts/spec.md` and `specs/components/pdn-sdk/artifacts/spec.md`); this change targets the second. `mobile-host-surface` predates pods and names none of the facade's pod calls. Those calls — `create_pod`, `pods`, `pod_members`, `mint_pod_invite`, `join_pod`, `pod_act`, `put_record`, `append_op`, `read_record`, `read_ops`, `list_records` — are written in `crates/pdn-mobile` and specified by no change. They are no prerequisite of group 3: the phone's test surface drives the runtime through the laptop host's router, not through them.
- **`session-outcome`** decides what a session reports when its dialer fails or its teardown fails, and names the counts and the event record as this change's. The two touch `net.rs` and `codec.rs` in different places (the dialer's `Abort` there, the session id and the counts on a close error here) and can land in either order.
- **`pods-removed-member-access`** changes how honest member devices refuse a removed member's devices the record store. Either way a refused session reaches the removaled dialer as `remote_abort` and the refusing side reports nothing; its record-store stream still ends in `closed` once the removaled member folds its own departure.
- **`pods-scale-and-storage`** may bound what one session or one device holds. The store's capacity here is sized for a 1,000-entry session and the runtime's buffer for a 100,000-record catch-up's first session (design, D2 and D5), whatever that change decides.
- **`pods-record-deletion`** and **`pods-mergeable-document-merge`** change which entries the record store holds and how operations are keyed; the record listing reports whatever entries the record view holds, and its verdicts are the record view's own, so neither changes this surface.
- **`pods-anchored-history`**, **`pods-listed-node-consent`**, **`pods-name`** and **`pods-versioning-and-migration`** change the membership fold, device statements, how a pod is named and how a build reads entries; the subscription reports the membership store's entries and sessions whatever they mean, and none of them touches what this change adds.
- **`reconcile-trigger`** adds sessions prompted by a trigger on stores received under a grant, which this subscription does not address.
- **`live-actor-loop-priority`** reorders the live actor's loop. The ordered subscription's guarantee that a session's inserts precede its end rests on that loop taking replica events before finished sessions (design, D1), and that change's proposal names it among what every option keeps.

## Impact

- **`crates/pdn-store`**: behind its `observation` feature, the ordered subscription (the live actor forwards `LocalInsert` and `RemoteInsert` to it), taken alone or with the start of a replica's sync, its capacity, its end when the replica is dropped, the session id on `SyncFinished` and `SyncEvent`, the stage of a failure, counts on a close error; in every build, the live actor's release of held dials. A divergence from upstream iroh-docs, recorded in the crate's `CLAUDE.md` and `UPSTREAM.md`.
- **`crates/data-layer`**, behind `test-util`: the ordered subscription of each store of a pod an identity holds, and an import of a pod that starts both stores with it; `RecordEntry` carries the entry's content hash and length whether or not the payload has arrived.
- **`crates/pdn-node`**, behind `test-util`: the numbered record, the pod subscription with its stamping task and buffer, the observed join and the record listing.
- **`crates/pdn-node-http`**: the `observation` feature and its 3 routes, the stream bound, `PDN_POD_RECONCILE_INTERVAL_SECS`, `PDN_CONNECTIVITY` and `PDN_ANY_ORIGIN`, the status lines; `ops/Dockerfile` gains a `FEATURES` build argument; `scripts/test-features.sh` and `just check` cover both builds and the release build of the observation feature; the container suite builds both images.
- **`crates/pdn-mobile`**, **`pdn-sdk`**, **`pdn-app`**: the test build, in the release configuration, with `pdn-mobile`'s test artifact linking `pdn-node-http`'s router; `pdn-mobile` names its runtime's threads in every build. Built after the network spike (`plan.md` step 1, task 3.1): a phone on direct paths joins a pod on the invite of a `pdn-node-http` on `PDN_CONNECTIVITY=direct` across the local network, and a usbmux tunnel reaches a server bound to the phone's loopback.
