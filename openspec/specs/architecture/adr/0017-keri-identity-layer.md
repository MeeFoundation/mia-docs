# KERI identity layer — architectural decisions

Draft for review. Each numbered decision record (DR), such as DR-1 or DR-5, states one decision and why it was taken, and it usually gives an example. A "To verify" line marks a point that still has to be checked against the KERI specification, against a platform or against the sync engine. The numbers run through the whole document, and the headings only group related decisions. The questions that are still open or deferred are listed at the end.

## Terms

- **PDN** — Private Data Network: the platform. Data moves between devices over iroh, the peer-to-peer network library that the platform uses.
- **Tellipod** — the product: the PDN together with the Android, iOS and desktop apps.
- **Pod** — a shared space with many members. A pod is usually about one topic, such as "planning a trip to Tokyo".
- **Identity** — a person, known to others by one KERI identifier.
- **KERI and keripy** — KERI (Key Event Receipt Infrastructure) is a system of self-certifying identifiers whose keys change through a signed log of key events. keripy is KERI's reference implementation.
- **AID** — KERI's autonomic identifier: a self-certifying identifier that is bound to a key event log.
- **KEL** — key event log: the signed, hash-chained sequence of an AID's key events.
- **Establishment event** — an inception event or a rotation. An establishment event sets the current keys and commits to the digests of the next keys. This commitment in advance is called pre-rotation.
- **Interaction event** — a KEL event that changes no keys and anchors data, such as a digest.
- **Current keys and next keys** — the current keys of an establishment event are the keys that sign it. Its next keys are the keys that may sign the next rotation, and the event holds only their digests. A key is a next key in one event and, once it signs, a current key in the next one. A device therefore holds a new key of the identity after each rotation that it signs. For example, "phone key 1" and "phone key 2" name 2 keys of one device, one after the other (DR-11).
- **Weight and threshold** — each key carries a weight. An event is valid when the weights of the keys that signed it add up to at least the threshold. In this design the threshold is 1.
- **Partial rotation** — a rotation that uses some of the committed next keys, and carries the commitments to the other next keys forward unchanged.
- **Digest seal** — a digest of some data, carried inside a KEL event. The event is signed, so the seal fixes the data without putting the data itself in the KEL. An event that carries a digest seal of some data is said to anchor that data.
- **Domain tag** — a fixed label at the start of signed or digested data that names what the data is for, so that data made for one purpose never counts for another (DR-1).
- **Escrow** — a place where a validator holds an event that it cannot validate yet, such as an event that arrived before the event that precedes it.
- **Delegation** — a relation between 2 AIDs, a delegator and a delegated AID. The inception and the rotations of the delegated AID are valid only when the delegator anchors them in the delegator's own KEL.
- **Fork** — 2 different items, both validly signed, at the same position of one sequence that a single party signs. The 2 items are either 2 events of one KEL, or 2 records of one device's chain in a pod. From that position on, the sequence has 2 branches.
- **Duplicity** — KERI's name for a fork of a KEL. KERI treats duplicity as the mark of a compromised key.
- **Superseding recovery** — KERI's mechanism by which a rotation replaces the interaction events that came after the last establishment event. This design does not use superseding recovery (DR-3).
- **Witness** — a server that receipts an AID's events: it signs a receipt for each of them. A witness refuses to receipt a second event at a position where it has already receipted one. In this design, a witness also signs key state statements, from which stamps are made. An AID's witnesses are the ones that the AID's inception event lists, and a later establishment event can change that list. A validator accepts an event of the AID only once enough of the AID's witnesses have receipted it. The witness threshold in the KEL sets how many witnesses are enough. In this design, that threshold is a majority of the identity's witnesses (DR-15).
- **Merkle tree and Merkle root** — a tree of digests in which each inner node is the digest of the nodes below it. The root is the single digest at the top. A short path of digests from a leaf to the root proves that the leaf belongs under that root (DR-20).
- **Key state statement and stamp** — a key state statement is the one kind of statement that a witness signs for an identity. It carries a domain tag, the identity's AID, the latest position of the identity's KEL that the witness has receipted, the digest of the event at that position, and the date on which the witness signed it. When one of the identity's own devices supplied a Merkle root, the statement carries that root too. The nearest counterpart in keripy is its key state notice, a reply that carries the whole key state and a date but no domain tag, as the section on departures from KERI explains. Anyone may pass key state statements on. Statements from a majority of the identity's witnesses can make a device's copy of the KEL fresh. They do so when each is dated no earlier than 24 hours before the device's witness time, and the copy reaches the newest position that they give (DR-15). A stamp is a set of key state statements from a majority of the identity's witnesses that give the same position, the same event digest and the same root. Each statement of a stamp keeps its own date, and the dates may differ. The root covers some records of the identity's devices: either the requesting device's own records, or, before a revocation, the revoked device's records (DR-20). Whatever a stamp covers existed before any event after the stamp's position was accepted (DR-20). A stamp travels in each pod whose records it covers. In such a pod, the stamp is pod data that no device signs, so a stamp is not a record.
- **Own fetch** — a device's fetch of its own identity's KEL from the identity's witnesses. Every own fetch is also a stamp request for the device's own records (DR-15, DR-20).
- **Witness time** — the time by which a device measures every period that decides something. It is read from the device's witnesses, never from a clock of the device. It is the newest date that a majority of the witnesses of the device's own identity have each signed. Each witness counts with its newest key state statement that the device holds, whoever passed that statement on. A device that hosts several identities takes the newest witness time among them. Witness time advances only when such statements arrive, is stored durably, and never moves backward. For example, the newest statements of Alice's 3 witnesses that her phone holds are dated 9:02, 9:00 and 8:40. Her phone's witness time is 9:00: 2 of the 3 witnesses have signed a statement dated 9:00 or later, and only one has signed a later one (DR-15).
- **Watcher** — a party that collects copies of other AIDs' KELs from several sources, keeps the first accepted event that it sees at each position, and reports when 2 copies disagree. In this design, every member's device is a watcher for the KELs of the members of its pods (DR-15).
- **Keys of a device** — for each identity that it hosts, a device has 4 kinds of keys:
  - Its key in the identity's key set. It is a P-256 key, kept in hardware, and it signs rotations.
  - Its record key. It is a P-256 key, kept in hardware, and it signs records and the device's endpoint binding.
  - Its iroh endpoint key, which names the device on the network. It is an Ed25519 key, held in memory while the node runs. It is stored wrapped, which means encrypted under the wrapping key.
  - A wrapping key, kept in hardware. Its type follows the platform. Its only job is to encrypt, while they are stored, the secrets that the device keeps in software: the iroh endpoint key, a new recovery key until that key is enrolled or committed (DR-28), and the device's replicas where they are stored encrypted (DR-7).
- **Record key** — the key with which a device signs its records and its endpoint binding. The identity's role statement lists it in the device's entry, next to the device's key in the key set. A device has a separate record key for each identity that it hosts, and a device id's record key never changes (DR-6).
- **Device id** — the name of one device within one identity: a digest over a domain tag, the identity's AID and the device's record key. Every rule about one device, such as a fork or a removal, refers to the device by its device id (DR-6).
- **Sibling** — another device of the same identity.
- **Endpoint binding** — a statement, signed by a device's record key and by its iroh endpoint key, that ties the endpoint key to the device id. It is not a KEL event. It travels with the identity's KEL among pod peers, and it is valid while the identity's role statement lists its device id (DR-7).
- **Record** — an item of a pod's store. One device signs each record in the name of the device's identity. A record is pod data, never a KEL event.
- **Second party** — whoever signs a rotation together with a device: another device of the user, or the external co-signer.
- **External co-signer** — a party that is not a device of the user and that holds a key of weight 1/2 in the identity's key set. An external co-signer is either the Tellipod co-signer or a co-signer node that the user hosts. In this document, "the co-signer" always means the external co-signer.
- **Recovery key** — a key of weight 1, held by the Tellipod recovery service or written on a paper sheet.
- **PIN** — a short secret number that the user chooses. In this document, "the PIN" is the one that the Tellipod co-signer and the recovery service share and check in an enclave (DR-31). A self-hosted co-signer checks a separate PIN of its own.
- **Role statement** — a public statement, anchored in every establishment event, that gives the role of each key: recovery, external co-signer or device. Each device entry also gives the device's record key (DR-6, DR-14).
- **ACDC and TEL** — ACDC (Authentic Chained Data Container) is KERI's format for verifiable credentials. A TEL (Transaction Event Log) is the log that tracks whether each credential is issued or withdrawn, which ACDC calls revoked.
- **History of a record** — the record itself, together with every earlier record of the same device in the same pod that the record's hash chain leads back to.
- **Replica** — a device's copy of a pod's store.
- **Interval** — a span during which an identity is a member of a pod. A removal or a leave ends it, and the member's next join, which only a device of hers writes, starts the next one (DR-40).
- **Sync session** — an exchange of records between 2 devices. A sync session is different from a signing session, which is a period during which the user's presence lets a device sign records (DR-23).
- **Enclave** — a hardware-protected area of a server's processor. The server's operator cannot read or change the enclave's memory and code. The trust that remains lies with the chip vendor and with the machine's physical security.

## KERI and its implementation

### DR-1. KERI is the identity layer, in its standard encoding

**Decision.** Every identity is a KERI AID. The identity's KEL uses KERI's standard encoding, CESR (Composable Event Streaming Representation), so that existing KERI implementations can verify it. For P-256 signatures, the implementations that can verify them are the ones that follow keripy (DR-2). Each addition of this design is one of 3 things: data carried inside conformant events, a rule applied on top of those events, or a message outside the KEL. Role statements are data of the first kind. A stamp and an endpoint binding are messages of the third kind (DR-7, DR-20). No addition changes the encoding of a KEL. Every signature on a message of this design's own covers a domain tag that names the message's purpose. Signatures on KERI events and receipts cover KERI's own serialization. So a record never parses as a KERI event, and a key state statement never verifies as a receipt. A request to the recovery service or to the co-signer carries its purpose and a nonce, a single-use value that the receiving party issued for that request, so that the request cannot be replayed. A nonce of the enclave is valid only on the channel for which the enclave issued it. That channel ends inside the enclave and gets new keys each time it is opened, so traffic recorded earlier cannot be replayed, not even to an enclave restored from older stored data. A request also names what it applies to. A request to the enclave names the enrolment identifier, which a recovering device learns from the email check before it knows the AID. A request to co-sign also carries the rotation, with its AID and its KEL position (DR-26).

**Why.** A self-certifying identifier makes an identity independent of any server. The standard encoding keeps every KEL checkable by tools that the project did not write.

**Example.** Given Alice's KEL, keripy computes the same current keys as Bob's phone does. keripy parses Alice's role statement as data and ignores what the statement means.

### DR-2. Hardware-bound keys on P-256

**Decision.** A device's key in the identity's key set and its record key are P-256 keys. They are bound to the device's hardware, and they are never exported from the device. A device without such hardware cannot be linked, which the open questions at the end discuss. The access rule of these keys survives changes to the fingerprints or faces that the user enrolls. On iOS and macOS, the keys ask for `userPresence`, never for `biometryCurrentSet`. On Android, the keys are created with `setInvalidatedByBiometricEnrollment(false)`. Recovery keys are software keys. For P-256 signatures, the implementation conforms to keripy. The CESR specification has a gap for these signatures, and that gap is tracked or pushed upstream. A virtual TPM (Trusted Platform Module), as a virtual machine provides it, counts as no hardware. The record key lives in the platform's trusted execution environment, not in StrongBox, Android's separate security chip. Where StrongBox exists, it holds only the device's key in the identity's key set.

**Why.** P-256 is the curve that the Secure Enclave of iOS and macOS, Android StrongBox and TPMs have in common. The Secure Enclave offers no Ed25519. The CESR specification defines P-256 keys and plain P-256 signatures. However, KERI controllers use indexed signatures, and the specification's table of indexed signatures lists no P-256 code. keripy, the reference implementation, defines indexed P-256 signatures. Binding keys to hardware outweighs conformance with the specification's table. A recovery key is typed into whichever device carries out the recovery, so a recovery key cannot be bound to one device. Suppose that a key's access rule depends on the enrolled fingerprints. When the user adds or deletes a fingerprint, that key becomes permanently unusable, and so does its pre-committed next key. The device would then have to be revoked and linked again. Enrolling a new fingerprint must never cost the user a linking. A snapshot of a virtual machine copies its virtual TPM, keys included. StrongBox takes about 100 to 500 ms for each signature, which is too slow for a burst of records but fine for a rare rotation.

**Example.** Alice's laptop keeps its P-256 keys in its TPM. The recovery key of Alice's paper sheet is derived from the sheet's 24 words, on the device that carries out the recovery.

**To verify.** The exact key-creation flags on each platform. That a Secure Enclave key with `userPresence` stays usable after the user adds or deletes a fingerprint or a face. That an Android key created with `setInvalidatedByBiometricEnrollment(false)` survives a new biometric enrollment. And what a TPM-backed Windows Hello key does when the user changes the enrolled fingerprints.

### DR-3. Our own KERI implementation, limited to the subset in use

**Decision.** The project writes its own KERI implementation, under the Apache 2.0 license. The implementation includes only what this design uses: inception and rotation with partial rotation, weighted thresholds, the digest seal of the role statement, the establishment-only configuration, witness receipts, changes of the witness list, this design's key state statements, and the escrows in which a device holds events that it cannot validate yet. It also includes the witness software. A witness checks every event of an identity against the same validator rules as a device, including the roles and weights of DR-9, the witness count and threshold, and the limits on device entries, and it receipts only an event that passes them. A witness receipts the identity's events and signs the key state statements, each with the Merkle root of a stamp request when a device supplies one (DR-15, DR-20). The witness orders every statement of an identity against that identity's receipts, so that no statement gives a position below an event that the witness has already receipted. The witness keeps its state durable and linearizable for each identity, which means that it handles each identity's requests in one single order. It never restores that state backward. It dates its statements from a clock that it keeps accurate against several independent time sources. It signs no statement while those sources disagree, and it never dates a statement for an identity earlier than its previous statement for that identity. Each witness uses time sources that are independent of the other witnesses' time sources. A deployment runs at least 3 witnesses (DR-15). They have separate keys, run on separate machines, and are never restored from backups together. Receipts never wait behind key state statements. The witness limits request rates for each connection, never for each identity. The design needs no interaction events, no delegation and no superseding recovery. ACDC registries (TELs) are out of scope. The implementation follows KERI 2.0 and CESR 2.0 only, as the current Trust over IP specifications define them, and it never produces or accepts KERI 1.0 events. Conformance is checked in both directions against test vectors generated with keripy, the reference implementation, which is also under Apache 2.0. keripy serves as an outside test oracle: the tests compare our implementation's results with keripy's results, and keripy's code never enters the product.

**Why.** keriox, an existing KERI implementation, is under the EUPL (European Union Public Licence), and an Apache 2.0 project cannot take in code under the EUPL. The design needs only the subset that the decision lists. A witness restored from an old backup would stamp a thief's later records at an old position. Witnesses that shared keys, machines or backups would fail together, and a majority of them could then stamp at an old position. A limit for each identity would let a flood of requests block other devices' stamps. Devices read time only from their witnesses' dates (DR-15). So a witness whose clock drifted would shift every period for the devices that rely on it. A time source that a majority of the witnesses shared would do the same through all of those witnesses at once. A date that ran backward would make a statement that gives a later position look older than one that gives an earlier position. A witness that receipted an event which devices reject would let that event take its position, and the honest event could then never be receipted there. For example, a thief with Alice's phone and laptop signs a rotation that lowers her paper key's weight to 1/2, which devices reject, and if her witnesses receipted it, her real revocation of the phone could never take that position, and only a new identity would get her out.

**Example.** A test feeds a KEL that keripy produced into our validator, and a KEL that our implementation produced into keripy. For both KELs, our validator and keripy must reach the same key state.

### DR-4. Every device does the full KERI work itself

**Decision.** Each device validates KELs completely. Complete validation includes the escrows for events that arrive out of order and for events that do not yet carry enough signatures. Each device is also reachable over iroh, and it checks the copies of KELs that it receives. There is no cloud agent of the kind that KERI's Signify client relies on. With Signify, the KERIA agent keeps the user's KELs and mailbox in the cloud. The escrow has an overall size limit. Inside it, each identity has a share, and inside an identity's share each sender has a part of its own, so that one sender's events never push out another sender's. The escrow takes only events that carry a valid receipt from a witness that the identity's latest validated event lists, and it indexes events by AID and position. Without these limits, events that cannot be validated until missing earlier events arrive could fill the device's storage. An event that the escrow drops comes back later, such as an event that follows a change of the witnesses and arrives before that change. Once the device has validated the events before the dropped event, the next key state statement that gives a later position makes the device fetch the KEL (DR-15).

**Why.** The platform is local-first, and KELs are small enough for a phone (DR-13). Doing all KERI work on the device costs a complete and correct KERI implementation there, not storage or computing power.

**Example.** Bob's phone receives Alice's rotation 7 before her rotation 6. The phone holds rotation 7 in an escrow until rotation 6 arrives, and then validates both. In another case, a pod member sends Bob's phone events for positions 900 to 5,000 of Alice's KEL. These events fill only that member's part of Alice's share, and Bob's phone drops the rest. A genuine event of Alice that Carol's phone sends out of order still finds room in Carol's part.

## Identity and devices

### DR-5. One identity across all of a person's devices

**Decision.** A person is one identity, with one AID on all of the person's devices. Linking a device, revoking a device and rotating keys never change the AID.

**Why.** Pod membership and records refer to the person, not to the hardware. A new phone must not turn Alice into a new member of every pod.

**Example.** Alice replaces her phone. Her pods still list the same AID for her, and Bob notices nothing.

### DR-6. Each device is an entry of the role statement

**Decision.**

- Each device of an identity is an entry of the identity's role statement (DR-14). The entry pairs one slot of the identity's key set with one record key. The slot holds the device's key in the key set, with weight 1/2, or 1 as a sole device (DR-10). The record key is a P-256 key bound to the device's hardware (DR-2). A role statement lists at most 32 device entries. No record key appears in 2 entries, and a record key that a rotation dropped is never listed again.
- A device's device id is a digest over a domain tag, the identity's AID and the device's record key. Every rule of this design about one device refers to the device by its device id within its identity. These rules cover forks and the limit of 2 branches (DR-22), the leaves of stamps (DR-20), removals (DR-40) and endpoint bindings (DR-7).
- A device creates a separate record key for each identity that it hosts. A phone that hosts 2 identities has 2 record keys and so 2 device ids.
- A device is linked from the first accepted establishment event whose role statement lists its entry, and revoked from the first later one that does not (DR-20). Linking a device is a rotation of the identity's KEL that adds the device's entry (DR-8). The identity's inception event lists the first device's entry, so the first device needs no rotation of its own. An identity with an external co-signer is incepted by its first device and the co-signer together (DR-11).
- The record key signs the device's records (DR-18) and its endpoint binding (DR-7).
- A device id's record key never changes. A new record key means a new device id. One rotation lists the new entry and drops the old one, and before that rotation is signed, a stamp covers the old device id's records (DR-20). This holds alike in 3 cases: a sole device, or a single device with an external co-signer, that replaces itself after a fork (DR-22), a record key that became unusable, and a change of the signature algorithm. After a fork, a device with siblings is instead revoked and linked again. The stamp before that revocation is the one that the revoking device requests (DR-20).
- Before the signers of a linking list a new device's record key, they check the new device's endpoint binding, which proves that the new device holds that record key. The linking ceremony sets the details.

**Why.**

- A device signs records all day, but its key in the identity's key set is single-use and changes at every rotation. The device therefore needs a key that it can use repeatedly. It also needs a name that stays the same across the identity's rotations, so that the device's records, its endpoint binding and its revocation can all refer to that name.
- Listing the record key in the role statement keeps every device's key in the identity's KEL, which the witnesses order (DR-15). One source then answers both whether a device is linked and which key signs its records, and a verifier needs no KEL other than the identity's.
- The device id covers the identity's AID. A record key is public, so Mallory can copy Bob's record key into her own role statement. Her entry then has a device id of its own, and no rule about her device, such as a fork or a removal, reaches Bob's phone.
- If a device id could take a new record key, any 2 parties could put a key of their own under another device's device id. A dishonest user could also disown a device's history by moving its device id to a new key. A new device id for each new key keeps every record tied to the key that signed it.
- With one record key on 2 identities, the 2 identities would share a public key, which would connect them for anyone who is in pods with both (DR-35).
- The check of the binding keeps a linking from listing a record key that the new device does not hold.

**Example.** Alice's rotation 3 lists the entry of her laptop: a key in her key set and the laptop's record key, whose device id is `D-laptop`. When the laptop next signs a rotation of Alice's KEL, the laptop's key in her key set changes. Its record key and `D-laptop` stay the same, and the laptop's records in the Hiking pod keep `D-laptop` as their author. In another case, the laptop's record key becomes unusable. The laptop creates a new record key, whose device id is `D-laptop-2`. Alice's phone requests a stamp for the records of `D-laptop` that it holds, and then the phone and the laptop sign a rotation that lists `D-laptop-2` and drops `D-laptop`.

### DR-7. The iroh endpoint key is separate and bound by a statement

**Decision.**

- A device's iroh endpoint key is an Ed25519 key, separate from the device's KERI keys. An endpoint binding ties the iroh endpoint key to the device id, and through the device id to the identity. The binding is a statement, not a KEL event.
- The body of a binding holds a domain tag, the identity's AID, the device id and the iroh endpoint key, and no time or nonce. The device's record key signs the body in the low-S form, which is the one of a P-256 signature's 2 valid forms that has the smaller S value. The iroh endpoint key signs the body too, so no device can bind another device's endpoint key. A binding is identified by the digest of its body, and 2 bindings are never compared by their bytes.
- A binding travels with the identity's KEL among pod peers, and it never goes to the witnesses. It is valid while the identity's KEL lists its device id. A peer drops a binding whose device id its copy of the identity's KEL does not list, and it holds no such binding in an escrow.
- A device signs one binding for life. 2 bindings with different bodies for one device id mark the device as compromised, as a fork does (DR-22). A device whose iroh endpoint secret is lost is linked again, with a new record key and so a new device id.
- A peer rejects an iroh endpoint key that bindings tie to 2 device ids that are listed at the same time, whether in one identity or in 2.
- The secret part of the iroh endpoint key is stored encrypted under a separate wrapping key in the device's hardware: the Secure Enclave, the Android Keystore or a TPM. The wrapping key cannot be exported, its type follows the platform, and it signs nothing. The device unwraps the secret into memory when the node starts. Where the platform allows, the stored secret is kept out of backups. The wrapping key asks for no user presence, since background sync runs without the user. The device's replicas of its pods are kept out of backups as well, or stored encrypted under the wrapping key.

**Why.**

- If the iroh endpoint key were a KERI key, every rotation would change the key that names the device on the network. The tickets and peers that refer to that key would then lose the device. A binding that the record key signs needs no second party and no event in the identity's KEL.
- A binding carries no time, so it needs no order from the witnesses. It is valid exactly while the role statement lists its device id, so a revocation ends it too.
- Pod sync authorizes a device by its iroh endpoint key. If the secret were a plain file in the app's data, the file would travel with every backup. Whoever stole a backup could then read every pod as that device, and nothing would signal that a second endpoint uses the same key. Without the endpoint key's own signature, a modified node could bind Bob's endpoint key to its own device id and so cut Bob's device off.
- One binding for life stops a thief who holds an unlocked phone and knows its passcode. Otherwise he would bind an iroh endpoint of his own on a server, throw the phone away, and keep reading pods from the server until the revocation. A second binding instead marks the device as compromised, and honest peers stop syncing with both endpoints.
- A P-256 signature can be altered so that it still verifies, so 2 copies of one binding can differ in their bytes. If bindings were compared by their bytes, any member could alter a signature on an honest device's binding and present the copy as a second binding. The digest of the body is the same for both copies.
- An iroh endpoint key that served 2 listed device ids would leave a peer unable to tell which device, and so which rules, a sync session belongs to.
- A peer that held bindings of device ids that it cannot check would let anyone fill its storage.

**Example.** Alice links her laptop as `D-laptop`. During the linking, the laptop signs its binding, which names Alice's AID, `D-laptop` and the laptop's iroh endpoint key. Alice's phone checks the binding before it signs the rotation. Bob's phone gets the binding together with Alice's KEL from Carol's phone, and it syncs with that endpoint while Alice's KEL lists `D-laptop`. Alice's later rotations do not change the binding. In another case, a thief takes Alice's unlocked phone and knows its passcode. He signs a second binding for an endpoint on his server. Bob's phone holds both bindings, marks Alice's phone as compromised, and syncs with neither endpoint. In a third case, Mallory obtains the Time Machine backup of Alice's Mac. The wrapped secret is kept out of the backup, so the backup does not hold it. Even a copy of the wrapped secret would be useless without the Mac's Secure Enclave.

## The identity's key event log

### DR-8. The identity's KEL holds rotations only

**Decision.** The identity's KEL uses KERI's establishment-only configuration. The configuration is set in the identity's inception event, as `"c":["EO"]`, and KERI allows this setting nowhere else. The identity's KEL therefore holds an inception event and rotations, and no interaction events. Linking a device is a rotation that adds the device's entry (DR-6). Revoking a device is a rotation that drops the device's entry. Each rotation is signed by any 2 parties, by a sole device (DR-10) or by a recovery key, and a rotation is final once it is accepted. While no second party is reachable, linking waits. Anything that has to be anchored in the identity's KEL costs a 2-party rotation. Records, including membership acts, are frequent, so they are never anchored in the identity's KEL.

**Why.** Apart from a sole device (DR-10), no single device writes to the identity's KEL. A thief who holds one of several devices therefore changes nothing in that KEL, and no single device can fork that KEL. KERI defines the configuration: "Only establishment events MUST appear in this KEL".

**Example.** Alice links a tablet from her phone. Her laptop shows "approve linking a tablet?" from her phone, and she approves. The rotation that adds the tablet's entry is final.

### DR-9. Any 2 parties can rotate

**Decision.** Every device carries weight 1/2. The external co-signer, whether it is Tellipod's or a self-hosted one, carries weight 1/2. Each recovery key carries weight 1. The threshold is 1. An identity without an external co-signer has no co-signer key in its key set, and a sole device of such an identity carries weight 1 (DR-10). Apart from that case, the weights do not depend on the number of devices. KERI expresses the weights as one clause of fractional weights, such as `["1/2","1/2","1/2","1","1"]`. The clause is satisfied when the weights of the signers add up to at least 1. No weight may exceed 1. Every validator and every second party enforces these weights, the recovery weight of 1 and the threshold of 1. Each of them also enforces 4 more rules (DR-6). A key's role never changes once a role statement gives it. A role statement lists at most 32 device entries. No record key appears in 2 entries. And a record key that a rotation dropped is never listed again. Every validator requires receipts from a majority of the witnesses that the previous establishment event lists. For the inception, these are the witnesses that the inception itself lists. A validator rejects an establishment event that lists fewer than 3 witnesses, or whose witness threshold is anything other than a majority of the witnesses that it lists, such as 2 of 3 or 3 of 5 (DR-15). With partial rotation, a validator matches each signature's key against the next-key digest of the previous establishment event at the signature's second index, which is the index into that list of digests. It then takes the weight of that slot. The current keys of a rotation are only its signers (DR-11), so the 2 indices of a signature usually differ, and every rotation signature carries both.

**Why.** No device is special. Any 2 parties together can agree on a change. With 3 or more parties, the other parties keep working after the loss of any one device. The external co-signer's operator alone, at weight 1/2, can never rotate an identity.

**Example.** Alice has a phone, a laptop, the Tellipod co-signer and a paper sheet. The phone and the laptop together reach 1, and so do the phone and the co-signer. The co-signer alone reaches only 1/2. The paper alone reaches 1.

**To verify.** Negative test vectors for each of these rules: a rotation that lowers the paper's weight, raises the threshold, relabels a role, lists a dropped record key, lists one record key in 2 entries, lists 33 device entries, or claims the recovery slot with a device's signature.

### DR-10. A sole device carries weight 1

**Decision.** While an identity has one device and no external co-signer, that device carries weight 1. The rotation that links a second device gives both devices weight 1/2. A revocation after which the identity has one device gives that device weight 1 again. Dropping the external co-signer from an identity with one device gives that device weight 1, and adding an external co-signer to such an identity gives the device 1/2 (DR-9). Identities with an external co-signer need no special case.

**Why.** Every user without an external co-signer links a second device at some point. If a sole device carried only 1/2, that routine act would need the recovery key, and without a recovery key it would be impossible. Linking would then cost a paper user a new sheet, and it would expose the recovery key on a device. The risk of giving a sole device weight 1 is that whoever holds the sole device and its unlock secret owns the identity. That risk is accepted (Risk 3). User presence for every rotation (DR-23) means that an unlocked phone lying on a table is not enough.

**Example.** Alice creates her identity on her phone, with a paper sheet and no external co-signer. The phone carries weight 1, and the paper carries weight 1. She then links her laptop: she scans the laptop's QR code and confirms on the phone. Now the phone carries 1/2, the laptop 1/2, and the paper 1.

### DR-11. The current keys of a rotation carry the weights committed for them

**Decision.**

- The identity's KEL commits to one key of each device at a time. The latest establishment event commits to that key as a next key, by its digest, with the weight of the device's role.
- A device that signs a rotation reveals that key, and the same rotation commits to a new key of the device. A device that does not sign the rotation keeps its commitment unchanged.
- The current keys of a rotation are exactly the keys that sign it. Each of them carries the weight that the previous establishment event committed for it, and the threshold of the current keys is 1.
- The next keys of a rotation carry the weights of the roles from that rotation on (DR-9, DR-10).
- In the inception event, each current key carries the weight of its role. An identity with an external co-signer is therefore incepted by its first device and the co-signer together.

**Why.**

- KERI requires the signatures of a rotation to satisfy 2 thresholds: "the set of signatures on a Rotation event MUST satisfy two thresholds. These are the newly current threshold and the old prior next threshold from the most recent prior Establishment event." The current keys of a rotation repeat the signers' entries in the previous next keys, with the same weights. Both checks therefore add up the same weights, and any set of signers that satisfies one threshold satisfies the other.
- A current weight is used once, to check the event that lists it. The identity's KEL holds no interaction events (DR-8), so its current keys sign nothing else. The next rotation is checked against the next keys, so the weights of the roles apply from the next rotation on.
- If the current keys carried the weights of the roles after the rotation instead, a sole device could not link a second one. Its key was committed at 1, but the linking rotation would list it at 1/2, short of the threshold.
- A key that signed a rotation gives its device no weight afterwards, since only the next keys of that rotation can sign the following one. After the linking of a second device, a sole device's new key carries 1/2, so from then on every rotation needs 2 parties (DR-9, DR-10).

**Example.** Alice creates her identity on her phone, with a paper sheet and no external co-signer. "Phone key 1" and "phone key 2" below are 2 keys of the same phone, one after the other, and not 2 devices.

| Event | Signed by | Current keys, with weights | Next keys, with weights |
|---|---|---|---|
| Inception | the phone | phone key 0: 1 | phone key 1: 1, paper: 1 |
| Rotation 1, which links the laptop | the phone | phone key 1: 1 | phone key 2: 1/2, laptop key 1: 1/2, paper: 1 |
| Rotation 2, which links a tablet | the phone and the laptop | phone key 2: 1/2, laptop key 1: 1/2 | phone key 3: 1/2, laptop key 2: 1/2, tablet key 1: 1/2, paper: 1 |

Phone key 1 was committed at 1 in the inception, and rotation 1 lists it at 1, so both checks reach 1, and the phone links the laptop alone. A thief who steals the phone after rotation 1 holds phone key 2, which carries 1/2, and cannot rotate without the laptop or the paper. Phone key 1 cannot sign rotation 2, since rotation 1 does not list it as a next key. In rotation 2, the phone and the laptop sign together, and each of their keys carries 1/2 in both checks. In another case, Alice's laptop and the Tellipod co-signer link her tablet, and the rotation lists the laptop's key and the co-signer's key as current keys, with weight 1/2 each. A recovery rotation signed with Alice's paper lists only the paper's key as a current key, with weight 1.

**To verify.** That keripy accepts a rotation whose current keys carry other weights than the next keys that the same rotation commits to.

### DR-12. An offline device stays in the key set

**Decision.** A rotation carries forward, unchanged, the next-key commitment of every device that stays in the key set but does not sign the rotation.

**Why.** A rotation must not need every device to be present, and a switched-off desktop has to stay usable. A device's key in the key set signs rotations only, so carrying the device's commitment forward is all that the device needs to stay usable. KERI allows such a partial rotation: "A Partial rotation operation on a set of pre-rotated keys MAY hold back some as unexposed while exposing others as needed".

**Example.** Alice's desktop is switched off while her phone and laptop link a tablet. The rotation repeats the desktop's commitment unchanged. Later, the desktop signs another rotation with the key that it committed to.

### DR-13. KELs stay small and are stored once per identity

**Decision.** The identity's KEL holds identity acts only. These acts are device links, device revocations, a device's replacement of its own record key (DR-6, DR-22), recovery rotations, replacements, additions and drops of a recovery key, and changes of the witnesses or of the external co-signer. The identity's KEL never holds pod membership, pod data or records. A device stores one copy of each KEL that it knows, together with the endpoint bindings of that identity's devices, and every pod that the device is in shares that copy. Every KEL has hard limits that are decided from its content alone. One is the limit of 32 device entries in a role statement (DR-6). The other is a limit on the size of the identity's KEL, and the role statements that its events anchor count toward that size. An identity whose KEL exceeds a limit is invalid. No device syncs with that identity's devices, and no device stores or serves its KEL beyond the limit. A device caches its verdicts on records, and on a first sync it checks the newest records first.

**Why.** The identity's KEL then grows with device changes, not with activity. A device's storage grows with the number of people that the device knows, not with the number of pods. The following estimate leaves out the role statements and is to be replaced by measurement. A KEL holds about 16 KB after 3 years of ordinary use, and 64 KB for a heavy user. The KELs of 100 pod members then come to about 2 MB to 6 MB, and a phone checks them for the first time in under a second. A heavy user who knows about 900 identities holds about 14 MB to 58 MB of KELs, and a new device needs about 10 seconds to check them. Without the limits, a member with witnesses of its own could make every member's device store and check millions of valid events.

**Example.** Bob is in 3 pods with Alice. His phone keeps one copy of Alice's KEL.

**To verify.** The value of the size limit. Proposed: 1 MB or 4,096 events for an identity's KEL, with its role statements counted. Also the size of a KEL with its role statements counted, since each establishment event anchors a role statement that lists up to 32 device entries, each with a record key. The estimates of about 16 KB and 64 KB, and the figures derived from them, are to be measured in this way.

### DR-14. Every establishment event states the role of each key

**Decision.** Every establishment event anchors a public role statement by a digest seal. The role statement gives the role of each key. The roles are recovery by paper, recovery by the service, external co-signer and device. Each device entry also gives the device's record key, and so its device id (DR-6). The role statement is KERI self-addressing data, which means that it is CESR-encoded and carries its own digest. The role statement travels with the KEL. Revoking a device is a rotation whose role statement no longer lists the device's entry (DR-20). Wherever a rule of this design depends on the roles of a rotation's signers, the rule reads those roles from the previous establishment event. The indices in a role statement count the next-key digests of the event that carries the role statement.

**Why.** KERI validation sees only the positions and weights of keys, and KERI defines no roles. The rules of this design need roles. Every validator enforces the recovery key's weight of 1 (DR-9). Every device acting as second party checks that a rotation commits to the recovery keys again, unless its own user chose to replace, add or drop one (DR-29). A sole device also carries weight 1, so a weight alone does not show which key is a recovery key. The roles are read from the previous establishment event, so that a thief cannot relabel a key as a recovery key in the same rotation that uses that key for recovery. The record keys in the role statement put every device's record key in the one KEL that the witnesses order, so a record is verified against that KEL alone (DR-18). The role statement reveals nothing new, since the number of devices is visible anyway, and every record names its device id (DR-37).

**Example.** Event 8 of Alice's KEL anchors the role statement "key 0: recovery (paper), key 1: recovery (service), key 2: external co-signer, keys 3 and 4: devices whose record keys give the device ids `D-phone` and `D-laptop`". When Bob's phone checks event 9, it gives the signatures of key 0 and key 1 weight 1, and the signatures of keys 3 and 4 weight 1/2.

## Witnesses

### DR-15. Every identity has witnesses, and a majority of them orders its KEL

**Decision.**

- Every identity has at least 3 witnesses, listed in the identity's KEL from the identity's inception event on. The witness threshold is a majority, which means more than half of the listed witnesses: 2 of 3, or 3 of 5. By default, an identity's witnesses are Tellipod's, and Tellipod runs at least 3 of them. Whoever runs an instance of the Tellipod infrastructure of their own also runs at least 3 witnesses. A user may add witnesses of her own on top of the ones that Tellipod or another operator provides. Every witness runs the same witness software. A stock KERI witness does not qualify. It puts no device's Merkle root into its statements, so its statements can form no stamp (DR-20).
- A witness is not the co-signer. It holds no key of the identity and cannot rotate anything. Its only jobs are to receipt events and to sign key state statements (DR-20).
- A rotation of the identity's KEL is accepted only after a majority of the identity's witnesses have receipted it. Each witness receipts only the first event that it sees at each position. Any 2 majorities of the same witnesses share at least one witness, so 2 different events at one position never both reach a majority, and a second event at a position is never accepted.
- Identities with different witnesses can share a pod. Changing the witnesses is itself a rotation (DR-16).
- Every member's device is a watcher for the KELs of the members of its pods. It gets those KELs from its pod peers, together with the receipts, and it checks the receipts itself, without contacting any witness. It stores those KELs, serves them to other devices, and compares the copies that it receives. Of 2 accepted events at one position, it keeps the one that it saw first. A device serves an identity's KEL, key state statements and endpoint bindings (DR-7) only to 2 kinds of devices: that identity's own devices, and devices of identities that share a pod with that identity. For example, Bob's phone gives Alice's KEL and bindings to Carol's phone, which is in the Tokyo pod with Alice. It does not give them to Dave's phone, which shares a pod with Bob and none with Alice.
- A device contacts the witnesses for 3 purposes: to send the rotations that it signs, to request the stamp that comes before a revocation or before a replacement of a device's own entry (DR-6, DR-20, DR-22), and during recovery. Apart from these, a device asks the witnesses for a KEL in the 3 cases below, and at once whenever it receives a key state statement that gives a position ahead of its copy of that KEL:
  - It fetches its own identity's KEL whenever its node starts or wakes, before it next syncs with another identity's devices. It also fetches that KEL before it writes (DR-21). It fetches it after it writes, as soon as it is online, so that its new records are stamped (DR-20, DR-22). It fetches it at each signing session and before it co-signs a rotation (DR-29). And it fetches it about once a day while it keeps running, on the platform's timer. The exact times of these fetches decide nothing that counts.
  - It asks for another identity's KEL when its copy of that KEL is not fresh. It sends such a query to the identity's witnesses directly.
  - While it holds a removal of its identity from a pod, or a leave written in its identity's name, it asks for the KEL of the identity that wrote the removal or the leave. It asks at most once in 24 hours of its witness time. With that KEL, it checks the removal or the leave again (DR-19).
- To fetch a KEL, a device asks a majority of the identity's witnesses. For an own fetch, which is a fetch of the device's own identity's KEL, it asks every witness. Either way, the device takes the newest accepted event among the answers of a majority. Every accepted event was receipted by a majority, and any 2 majorities share a witness, so at least one of the witnesses that answer holds the newest accepted event.
- Every own fetch is also a stamp request for the device's own records (DR-20). It carries the identity's AID and a Merkle root. The root is computed over the device's records that no stamp covers yet. When there are none, it is the root of a padded tree of random leaves. So an own fetch shows the witnesses no pod, and they cannot tell a fetch from a stamp request. An own fetch succeeds only when a majority of the identity's witnesses answer with statements that carry that root. A fetch that gets no such answer from a majority before a timeout of the platform's timer counts as failed. The timeout decides only when the device warns, never what counts. A fetch of another identity's KEL that gets no answer in that time fails in the same way. A fetch that the witnesses answer also counts as failed when it leaves the device's copy of the KEL still not fresh. That happens, for example, when the witnesses' statements are dated more than 24 hours before the device's witness time. No device asks for stamps for another identity's records.
- While its latest own fetch has failed, the device shows the user "can't reach your witnesses", keeps retrying and keeps syncing.
- Whenever its witness time advances, a device checks again whether its copy of each identity's KEL is fresh, for every identity whose devices it is in a sync session with. It pauses each sync session whose copy is no longer fresh, until a fetch of that identity's KEL succeeds or fails, as it does before a new sync session. If the fetch fails, the sync session resumes with the copy that the device holds, and the device shows that this identity's KEL has not been confirmed recently. A sync session that stays open therefore meets the same bound as a new one.
- A key state statement of any identity that is dated more than 24 hours after the device's witness time makes the device fetch the KEL of every identity that it hosts. If those fetches succeed without moving the witness time past that date, the device warns the user that its own witnesses lag behind. This also catches a daily fetch that the platform's timer never runs.
- A witness answers every query for a KEL at one endpoint, with a key state statement. An own fetch supplies a root and gets it back in the statement. A query for another identity's KEL supplies none, and its statement carries no root.
- A device's witness time is the newest date that a majority of the witnesses of its own identity have each signed. Each witness counts with its newest key state statement that the device holds, whoever passed that statement on. A device that hosts several identities takes the newest witness time among them. Its witness time then keeps moving while the witnesses of any of those identities answer, even when the witnesses of another of them vanish. Witness time advances only when such statements arrive, is stored durably, and never moves backward. A newly linked or recovered device takes its first witness time from the key state statements that the linking or the recovery passes to it. Before it has one, it judges nothing that depends on witness time. After every start, until its first own fetch succeeds, a device treats every copy of another identity's KEL as not fresh, shows the notice that the KEL has not been confirmed recently, and accepts no further records that no stamp covers from devices whose 7-day window it had stored. A whole-system image, such as a Windows system image, can bring back an old witness time with the rest of the disk, and this keeps such a device from judging by it. A device stores its witness time outside backups, beside the wrapped secret of its endpoint key (DR-7), so that a restore of the app's data does not bring back an older witness time.
- No rule that decides what counts reads a clock of the device: neither its wall clock nor a monotonic clock, which counts the time since the device started. This holds for whether a record, a stamp, a copy of a KEL or a rotation counts, and for when the 7-day window of DR-20 closes. The freshness of a copy, the 7-day window, the re-check of a removal or a leave, and every other period of this design run on witness time. Platform timers appear only where they decide nothing that counts. They end waits for answers, pace retries, run the daily own fetch above, end a signing session after a period without use, keep the record key's window (DR-23), and schedule reminders. Each timer changes only when a device acts or asks, never what counts.
- A device's copy of an identity's KEL is fresh when 2 conditions hold. The device holds key state statements from a majority of the identity's witnesses, each dated no earlier than 24 hours before the device's witness time. And its copy reaches the newest position that those statements give. A date later than the witness time qualifies. Nothing else makes a copy fresh, and in particular no peer's word does. A witness's answer to a query for a KEL carries the witness's key state statement. The statements of a stamp count like any others, so a stamp that a device publishes in a pod also makes the members' copies of its identity's KEL fresh. Every device keeps the newest key state statements that it holds for each identity, and passes them on to its pod peers together with the KEL.
- A key state statement that gives a position ahead of the device's copy of the KEL, alone or as part of a stamp, makes the device fetch the KEL at once.
- A device that cannot reach a majority of an identity's witnesses keeps syncing with the copy that it holds, shows the user that this identity's KEL has not been confirmed recently, and keeps retrying.

**Why.** Without a party that orders events, no rule for forks can both bring all devices to the same state and protect the events that were already accepted. Either every device falls back to the same state when it sees 2 rotations at one position, or each device keeps the event that it saw first. In the first case, a rival rotation that arrives late can undo events that were already accepted. It can do so even if it was signed a year later, by keys that were carried forward since then. In the second case, members disagree for good about which branch is valid. The witnesses provide the single order. A rival event is never accepted, and a thief cannot show different versions of the KEL to different members.

Stamps need the same majority as receipts. With 3 witnesses, a revocation is accepted once 2 of them have receipted it, and a stamp counts only with the statements of 2 of them. The 2 witnesses that sign a stamp and the 2 that receipted the revocation share at least one witness, and an honest witness signs no statement below a position that it has receipted. A stamp from a single witness of several would not do, since that witness might not yet have receipted the revocation. A majority rather than all of the witnesses keeps the identity working while 1 of 3 witnesses is down. It also keeps one lying witness, one witness restored from an old backup, or one leaked witness key from forging receipts or stamps alone. With fewer than 3 witnesses, any such failure of one witness would block or forge the identity's order. 3 witnesses of one operator protect against a failure of one witness, but not against the operator as a whole.

Witnesses that a user adds on top of an operator's protect her against that operator only when her own witnesses outnumber the operator's. With Tellipod's 3 witnesses and 2 of her own, a majority is 3, and Tellipod's witnesses still form it alone. With 4 of her own, a majority of the 7 is 4. Her witnesses then carry on without Tellipod's, and Tellipod's can no longer form a majority alone at any position after the change (Risk 17, Risk 18). An even number of witnesses tolerates no more failures than one witness fewer. For example, 4 witnesses need 3 receipts, so they tolerate 1 failure, as 3 witnesses do.

The pod members compare the copies of KELs, and no separate network of watchers does. The parties that rely on an identity's KEL are exactly the members of the identity's pods, and they sync with each other anyway. A separate network would only add a party that learns who checks whom. On duplicity, KERI's own answer is to stop trusting the AID. That answer suits a validator that decides alone, but a pod needs every member to reach the same verdict, and a user must keep her identity after a thief forks it.

Within 24 hours of witness time after a revocation, the revocation reaches every device that syncs with the identity's devices. This limit is called the freshness bound. A device's witness time moves forward at its own fetches, so the device notices that the bound has passed at its next own fetch. A peer can withhold events but cannot forge them, since the witnesses receipt only the first event at a position. The freshness bound limits what a peer can achieve by withholding events. The witnesses see the identity's KEL, and so they see the identity's device changes, but they never see pods. The design pays 2 costs. First, a user who wants no Tellipod infrastructure has to run at least 3 witnesses. Second, linking and revoking need a majority of the witnesses to be reachable, so 2 devices on a local network without internet access cannot link a third device. Records are unaffected.

A device's clock cannot be trusted. Its user can set it to any time, and so can a thief who holds it. Whoever runs its network can do the same, through a spoofed time server, a mobile network's time or a hotspot. So this design relies on time only where it cannot be avoided. Even then, it relies only on witness time, and only for periods that last days. Witnesses are expected to be close to always available, and an outage of several days is treated as force majeure (Risk 21). Witness time comes from a majority of the device's own witnesses, so neither a peer nor a single witness can move it. It never moves backward, so old statements that a peer passes on cannot set it back. The cost is that witness time stands still while a device cannot reach the witnesses of any identity that it hosts. That stretches every period that runs on witness time by the length of the outage, and the device shows the user the warning throughout.

Every own fetch carries a root of the device's own, and it succeeds only when a majority of the witnesses answer with statements that carry that root. Without the root, whoever controls a device's network could answer each fetch with statements that it collected earlier. The fetch would look successful, and the warning would never show. The device's witness time would stand still unseen, which would keep old copies of other identities' KELs fresh and keep the 7-day window of DR-20 open. A root that the device computed for this fetch, over fresh random salts, comes back only in statements signed after the fetch was sent. The root of a padded tree of random leaves looks like any other root, so the witnesses cannot tell a fetch from a stamp request. A device that returns after days offline gets its offline records stamped at its first fetch. The fetch at every start and wake comes before the next sync with another identity's devices. So witness time is up to date before the device judges anyone's records after a pause.

If a device asked the witnesses before every sync session, the witnesses would learn who checks whom. Taking KELs from peers keeps the witnesses from learning this. A revoked device is itself a peer, and it can serve an old KEL that is still validly signed. The freshness bound keeps such a device from delaying a revocation for more than 24 hours of witness time.

Only the witnesses' dated statements make a copy fresh, because a peer's word can always be turned against the check. A stolen phone that hosts 2 identities would confirm each identity's old KEL as a source other than that identity. 2 devices with old copies would confirm each other. A dated statement goes out of date as the receiving device's witness time moves on, whoever passes it on. A stamp is made of such statements, so a stamp counts toward freshness for as long as the dates of its statements allow. The identity's own devices fetch their KEL at every signing session and about once a day while they run, and each such fetch is a stamp request. They publish a stamp in each pod in which they wrote (DR-20), and they pass the statements on. So in the normal case, members rarely need to ask the witnesses. A device that cannot reach the witnesses keeps syncing, since stopping would turn every outage of the witnesses into an outage of every pod. Whoever can cut a device off from the witnesses, such as the operator of its network, keeps the device on an old copy for as long as the cut-off lasts. The device shows the warning throughout (Risk 21). Setting the device's clock changes nothing that counts, since no rule reads it. At worst it breaks connections whose certificates the device checks against its clock. That looks like being cut off, and the device shows the warning.

**Example.** Alice's phone and the co-signer link a tablet. At the same time, her laptop and her desktop revoke an old phone that she no longer uses. Both rotations are at position 9 of Alice's KEL. Each of Alice's 3 witnesses receipts only the rotation that reaches it first. One of the 2 rotations gets at least 2 receipts and is accepted, and the other is never accepted. In a second case, Alice's phone starts a signing session at 9:00 and publishes a stamp in the Tokyo pod. The stamp's statements from 2 of her 3 witnesses are dated 9:00 and 9:01. Until Bob's witness time passes 9:00 the next day, those statements keep Bob's copy of Alice's KEL fresh, and Bob's phone does not ask her witnesses. In a third case, Alice's phone is stolen. On Tuesday at 10:00, her laptop and the co-signer revoke the stolen phone. Then the laptop goes offline, and so does Carol. Bob's phone keeps syncing the Tokyo pod with the stolen phone. The newest key state statements for Alice that Bob's phone holds are dated Monday at 14:00. The stolen phone passes on newer ones, dated Tuesday at 9:55, which it fetched just before the revocation. Bob's own fetches move his witness time forward. On Wednesday at 11:30, Bob opens the app, and the answers to his own fetch move his witness time to 11:30. That is more than 24 hours after the statements of Tuesday at 9:55, so Bob's copy of Alice's KEL is no longer fresh. Before his phone next syncs with the stolen phone, it asks Alice's witnesses, learns of the revocation, and stops syncing with the stolen phone. Had the stolen phone passed on no newer statements, this would have happened at Bob's first own fetch that moved his witness time past Tuesday at 14:00. Suppose that the stolen phone also hosts Alice's second identity, "Alice-work". Nothing changes, since that identity's devices cannot make Bob's copy of Alice's KEL fresh. In a fourth case, Dave uses Tellipod's 3 witnesses, and one of them is down for a week. The other 2 still receipt his rotations and sign the key state statements of his stamps. In a fifth case, Erin does not want to depend on Tellipod, and she adds 4 witnesses of her own to Tellipod's 3. If all of Tellipod's witnesses refuse her, her own 4 still form a majority of the 7. In a sixth case, Bob's phone joins a hotspot in a café, and the hotspot belongs to the thief who holds Alice's stolen phone. The hotspot sets the phone's clock a year back, which changes nothing, since no rule reads it. It then blocks Bob's queries to his witnesses, or answers his own fetches with statements that it collected earlier. Those statements carry none of the roots of Bob's fetches. So each fetch fails, Bob's witness time stands still, and his phone shows "can't reach your witnesses" until Bob leaves the hotspot.

### DR-16. Changing witnesses, planned rotation and witnesses that misbehave or disappear

**Decision.**

- A rotation that changes the identity's witnesses needs receipts from a majority of the old witnesses and from a majority of the new witnesses, without exception. The old witnesses are the ones that the previous establishment event lists. The rotation goes to the new witnesses first and to the departing witnesses last. The receipt that completes the majority of the old witnesses is the point at which the change takes effect.
- An old witness that receives a rotation that removes it receipts the rotation if it has receipted nothing at that position. If it has receipted another event at that position, it refuses the rotation and returns that event.
- A witness keeps no claim of having seen an event first at a position where the identity's accepted KEL does not list it. For example, rotation 9 would add witness W, reaches W first, and then loses to another rotation 9 that does not list W. W keeps no claim at position 9, and if a later rotation adds W, W receipts the identity's events from there on.
- A witness that an identity no longer lists keeps serving that identity's KEL up to the event that changed the witnesses, for as long as the witness runs. A device that knows only earlier witnesses of an identity, such as a recovering device, follows each change of the witnesses in the KEL to the current witnesses.
- An operator of witnesses that plans to shut down or retire witnesses announces the plan to the witnesses' users with a notice period. It keeps receipting until those users have changed to other witnesses by ordinary rotations. The app supports this planned rotation: it tells the user, proposes new witnesses, such as another operator's, and carries out the change of the witnesses with the usual 2 parties.
- When a majority of an identity's witnesses is gone for good, or refuses the identity, the identity can no longer rotate. No device can be linked or revoked, and no stamp can be formed for its devices' records. Its devices keep writing, and each member keeps accepting their records until the 7-day window of DR-20 closes for each device, on that member's witness time. A member's device whose hosted identities all use the same operator has a witness time that stands still until that member moves to a new identity too. A member's device that also hosts an identity on other witnesses keeps its witness time moving (DR-15).
- Within that time, the user moves to a new identity. In each pod where the old identity is an owner, the old identity adds the new identity as an owner and leaves the pod. In each other pod, an owner invites the new identity. The old identity's membership act that adds the new identity is the evidence that the 2 identities are the same person.
- Records of the old identity that are already accepted stay accepted and attributed to the old identity. A member accepts no further records from a device of the old identity once its window for that device has closed, and the app writes the content of those records again under the new identity. A pod whose affected owners did not act in time, and that has no other owner, can no longer add anyone. Its members keep its data, and they continue in a new pod into which they copy the records. A user who lost every device before moving cannot recover, since a recovery rotation also needs receipts. Members invite a new identity of hers by hand.
- Every signer stores the new keys and the signed event durably before it releases the event. It resends the same event on a retry. Once another event is accepted at that position, the signer discards its stored event, and the app offers the act again, such as the linking of a tablet. The app lists a rotation that its signers have signed but that the witnesses have not yet accepted. How such a rotation can be cancelled is an open question, described at the end of this document. A device that co-signs refuses a rotation unless an own fetch made for that rotation succeeded and its copy of the KEL reaches the position that the answers give (DR-15, DR-29).
- A device finds its committed key by the digest that the latest KEL holds. It looks among its own keys of that identity in its hardware, and picks the key whose public key matches that digest. It finds its record key in the same way, as the key whose public key the latest role statement lists as a record key. What the app's data says about either key is only a hint. A device deletes a key only once it has seen an accepted event that no longer lists that key or commits to it.
- Receipts by one witness for 2 different events at one position prove that the witness misbehaves. The identity then replaces that witness by an ordinary rotation while a majority of its witnesses still answers. Otherwise the user moves to a new identity, as described above. Whoever retires a witness destroys the witness's key.
- When a device holds 2 different events at one position of an identity's KEL, each receipted by a majority of the same witnesses, the identity is frozen at that device. The device keeps the event that it saw first, and every verdict on records that it has already reached. From then on, the device accepts no further records and no further events from that identity, in any pod. It shows the user the 2 events with their receipts, and it passes them on to its pod peers together with the KEL, so that each member freezes the identity once the evidence reaches it. This is each device's sync policy, not part of the rule that decides which records are accepted.

**Why.**

- Only the old witnesses can tell that they hold nothing at a position, so every change of the witnesses needs their majority. A change that only the new witnesses receipted could create a second accepted event at a position that the old witnesses have already receipted. The members would then split for good. With the old majority required, keys that were valid at an earlier position never sign an accepted event. Examples are the key of a paper sheet that was replaced long ago, and the keys of revoked devices. In KERI, the keys committed at a position may sign the event at the next position. But the old witnesses have already receipted the real event there, and they refuse any other. An old witness receipts a rotation that removes it. Otherwise a change that removes a majority of the old witnesses could never collect the receipts that it needs.
- A recovering device learns the witnesses from a paper sheet or from the app, and both may be out of date. Since earlier witnesses keep serving the KEL up to the change, an out-of-date list still leads to the current witnesses, unless every witness on the way is gone.
- Sending a change to the new witnesses first and to the departing witnesses last keeps the old witnesses stamping until the change takes effect. And new witnesses that never answer do not lock the identity. A device saves its new keys and the signed event before it sends the event. So if the device crashes after the witnesses have receipted its rotation, the device does not lose the keys that the rotation committed to, and it does not build a second, conflicting rotation. A device refuses to co-sign without the latest KEL, so it does not sign a rotation that the witnesses will refuse.
- A restore of a device's app data, such as a Time Machine restore, brings back an older note of which key is committed, while the hardware keeps every key (DR-22). The KEL holds the digest of every committed key, and a device fetches it before signing a rotation anyway, so the KEL rather than the app's data tells the device which key to use. Listing a device's few keys and computing their digests takes well under a millisecond.
- An operator that shuts down its witnesses is the usual way for a majority of an identity's witnesses to disappear. With a notice period, each user changes witnesses by an ordinary rotation while the old witnesses still receipt it. Her AID stays the same, so her pods and her contacts notice nothing. The app does the work, so that a user who never chose her witnesses does not have to understand them.
- Without a majority of the old witnesses, no rotation is accepted, a recovery rotation included, so the AID cannot be kept. The user's pods can be kept. Members keep accepting the old identity's records for 7 days of their own witness time (DR-20). That is long enough for the membership acts that hand each pod over to the new identity, and the act that adds the new identity shows the members that it is the same person. This situation ends visibly once those 7 days have passed, when the members stop accepting the old identity's records. Members whose devices host only identities on the same operator keep accepting them until they have moved themselves, since their witness time stands still until then. Once the old identity has left a pod, its leave lists its newest records (DR-40). So stamps that hostile old witnesses form later, by signing key state statements, bring no further record of the old identity into that pod. There are 3 costs. Her contacts see a new AID. Pods that she does not own need an owner to invite her. And a user who lost every device before moving cannot recover, which is accepted (Risk 19). A user who adds witnesses of her own that outnumber the operator's keeps a majority without that operator, and changes witnesses without it (DR-15).
- Losing 1 of 3 witnesses needs only an ordinary rotation, since the other 2 still form a majority of the old witnesses, and that rotation replaces the lost witness.
- 2 events at one position that each have a majority of receipts need 2 things. They need a witness that receipted both, since any 2 majorities share a witness. They also need signers that meet the threshold for both events. Such events come from a dishonest user with colluding witnesses, or from a thief who holds keys that meet the threshold and controls a single witness that receipts both. Freezing the identity takes away whatever such a party hoped to gain, and keeping the history that each device holds keeps that party from rewriting it. Treating the fork as a revocation of every device at its position would give every device the same verdicts. But a dishonest user would then place a fork at an old position and disown years of records. Members may still disagree about records that were in transit when the evidence reached them, since each device stops at its own moment. That is the same kind of disagreement that the 7-day sync policy of DR-20 accepts. An honest user whose witnesses were turned against her loses the identity, which is accepted (Risk 17).

**Examples.**

- **A retry.** Alice's phone and laptop sign rotation 13, which changes her witnesses. The phone sends rotation 13 to the new witnesses, and crashes. On restart, the phone finds rotation 13 and its new keys saved. The phone resends the same rotation 13 instead of building a second, different event at position 13.
- **A restored Mac.** On Saturday, Alice's Mac and phone sign rotation 7, which reveals Mac key 2 and commits to Mac key 3. On Sunday, Alice restores the Mac's app data from Friday's Time Machine backup. The restore brings back older data, so the app's data names Mac key 2 again, while every key stays in the Secure Enclave. When Alice links a tablet with the Mac, the Mac fetches her KEL and finds the digest of Mac key 3 in rotation 7. It finds Mac key 3 among its keys in the Secure Enclave, and signs with it. The backup does not hold the Mac's iroh endpoint secret (DR-7). If the restore lost the secret, the Mac is linked again with a new device id. If the secret survived, the Mac asks its pods' peers for its own newest records before it writes. A rollback that this check misses makes a fork, which also ends in a new linking (DR-22).
- **A planned rotation.** Tellipod announces that its witnesses shut down in 90 days. Alice's app tells her, and proposes the 3 witnesses of another operator. In week 2, Alice's phone and laptop sign a rotation that lists those 3 witnesses. It goes to the new witnesses first and to Tellipod's last, and it takes effect once 2 of Tellipod's 3 witnesses have receipted it. Her AID stays the same, so nothing changes for her pods or her contacts.
- **Witnesses that lie.** Dishonest Alice runs her own instance with 3 witnesses. At position 12 she signs 2 events, one that revokes her laptop and one that does not, and has her witnesses receipt both. She shows the first to the Tokyo pod and the second to the Hiking pod. Dave's phone, in both pods, holds both. It keeps the event that it saw first, accepts nothing more from Alice, shows Dave the evidence, and passes it on to both pods, whose members then freeze Alice's identity as well.
- **Witnesses gone for good.** Tellipod's witnesses vanish without notice on a Monday. Alice is an owner of the Tokyo pod, Bob and Carol are plain members, and all 3 use Tellipod's witnesses. Alice's phone keeps writing in Tokyo, and Bob's and Carol's phones keep accepting its records. Their own witnesses are gone too, and their phones host no other identity. So their witness time stands still, and their 7-day windows for Alice's phone do not advance. On day 2, Alice's app creates her new identity on the witnesses of another operator. Her old identity adds the new identity to Tokyo as an owner and leaves, and her new identity invites Bob's and Carol's new identities. The phone's records #1 to #440, written under her old identity, stay accepted and attributed to it. Suppose instead that Bob moved to a new identity on day 2 and Alice waited until day 9. Bob's phone would take its witness time from his new identity's witnesses. On Monday, Bob's phone stored its witness time when it received the first record of Alice's phone that no stamp covers. By day 9, his witness time would be more than 7 days past that value. So Bob's phone would no longer accept the records of Alice's old identity, including the act that adds her new identity. Tokyo would then have no owner left who could add anyone, so Bob and Carol would continue in a new pod and copy the records into it.

**To verify.** How the old witnesses' receipts of a rotation that changes the witnesses are encoded. KERI and keripy count receipts only from the new witness list, at the rotation's own threshold. So the old witnesses' receipts travel without an index into that list, and a test vector has to show that keripy still accepts such a KEL.

## Records and revocation

### DR-17. Records form hash chains

**Decision.** Each device's records in a pod form a hash chain: every record carries its sequence number and the digest of the device's previous record. The history of a record is the record itself, together with every earlier record that its hash chain leads back to. Wherever this design says that something names a record, it names the record by the record's digest. A stamp's leaf, a removal, a leave and a device's first record after its identity joins a pod again all name records in this way. A record of a revoked device is accepted only if it lies in the history of a record that a stamp from before the revocation names (DR-20). A record of a member who was removed or who left is accepted only if it lies in the history of a record that the removal or the leave lists. This limit holds until the member joins the pod again, which starts a new interval (DR-40). A record is identified by the digest of its signed body, without the signature. The signed body carries a domain tag, the pod, the identity's AID, the device id, the sequence number, the digest of the previous record, the record type and the digest of the record's content. The content travels beside the signed body. A device signs every record that it writes. Deleting a record is itself a record, a deletion. A device of the deleted record's identity writes the deletion, and the deletion names the deleted record's digest. A replica that holds an accepted deletion removes the deleted record's content and keeps a tombstone: the deleted record's signed body and its signature, without the content. Such a replica does not take that content again while the deletion stays accepted. If the deletion later loses acceptance, for example because a revoked device wrote it and no stamp from before the revocation covers it, the replica takes the content again when a peer offers it, after checking it against the digest in the signed body. A membership act is never deleted, and a deletion that names one is rejected, since DR-40 and DR-41 read the membership acts. A record whose content is missing counts as a tombstone only where its deletion is held. A tombstone is checked on its own, like a record, and it is never removed. P-256 signatures on records use the low-S form. A verifier indexes records by device, branch and sequence number. Checking whether one record lies in another record's history is then a lookup, not a walk back through the chain.

**Why.** A signature or an anchor proves that a record existed, but never that another record did not exist. A record's position in its chain lets a verifier reject a record that was written later but claims to be older. Position also tells the branches of a fork apart. A stamp or a removal that names a record on one branch therefore does not extend to the other branch. In both cases, the honest records around the rejected record stay accepted. Because of the chain, a stamp that names a record covers that record's whole history. A record's digest leaves out the signature, so nobody can make a second item at a position by changing a signature's encoding. The body names its pod, so nobody can replay a record from one pod in another pod. Either would otherwise let any member make an honest device look forked. A tombstone keeps everything that the record's digest is computed from, so the chain still leads through it. It keeps its signature, so that a replica can check it on its own, in whatever order it arrives, as it checks every record. Signing in the device's hardware takes about 10 to 50 ms for each record. So an import of 1,000 photos takes 10 to 50 seconds of signing, which the app does in the background, while a single write is not noticeably slowed down. Signing every record lets each record sync and be checked on its own, in any order. The sync engine needs this, since it reconciles records independently of each other. Tombstones are never removed, since a chain that skipped a record could no longer show that an earlier record lies in a later record's history. So a deleted record still costs about 140 bytes in every replica of its pod, for as long as the pod exists. If every record is deleted, a typical user who receives about 300 records a day keeps at most about 16 MB of tombstones a year. A heavy user who receives about 3,000 records a day keeps at most about 155 MB. Members who want to shed the tombstones of a pod start a new pod and copy into it the records that they keep.

**Example.** Alice's phone writes record #440 in the Tokyo pod, and #440 carries the digest of #439. A stamp whose leaf names #440 therefore covers #1 to #440. Malware on the phone later gives Bob a rival record at position 1. That rival record lies outside the history of #440, so the stamp does not cover it. In another case, Alice deletes #437, "I'll pay the hotel deposit, 500 EUR". Every replica removes the text and keeps the tombstone of #437. #438 still names the digest of #437, so the stamp that names #440 still covers #1 to #440, with #437 as a tombstone. In a third case, Alice's phone imports 5 photos as records #441 to #445 and signs each of them. Each record syncs on its own: Bob's phone may receive #444 before #441, and it checks and accepts #444 at once. If Alice then deletes #445, its tombstone keeps the signed body and the signature. Carol's tablet receives the signed body of #445 and the deletion that names it, and checks both at once.

**To verify.** Whether the sync engine's records can carry a sequence number and the digest of the device's previous record, and whether a replica can replace a record by its tombstone.

### DR-18. A record is pod data, verified against the identity's KEL

**Decision.** A record is signed by one device's record key and stored as pod data, never as a KEL event. A record names the identity's AID and the device id, and it carries no reference to a key state. A verifier checks the record's signature against the record key that the identity's KEL lists for that device id. The verifier also checks in the identity's KEL that the device id was linked. If the device has since been revoked, the verifier checks that a stamp from before the revocation covers the record (DR-20). A record is verified against one KEL, the identity's.

**Why.**

- A record cannot be an event of the identity's KEL. That KEL holds rotations only (DR-8), and each rotation needs 2 parties and receipts from a majority of the identity's witnesses (DR-15). A device writes records all day, often offline, and at the same time as the identity's other devices, while a KEL is a single sequence.
- A record cannot be signed with the device's key in the identity's key set either. Unless the device is the identity's sole device (DR-10), that key carries weight 1/2, below the threshold of 1, so a signature by one device alone is not valid for the identity. That key is also replaced every time the device signs a rotation. And because that key can rotate the identity, using it for every record would expose it many times a day.
- The record key gives the device a key that it may use again and again, and the device id gives it a name that stays the same across the identity's rotations (DR-6). So every record has a stable author.
- The role statement answers both questions about a record's author at once: which key signs the device's records, and whether the device belongs to the identity. A device id's record key never changes, so a record needs no reference to a key state. Without the check against the role statement, anyone could make a key and sign records in Alice's name.
- Keeping records out of KELs keeps pod activity private and the KELs small (DR-13). Otherwise every holder of a KEL, including the witness, would see when and how often the identity writes. Records, by contrast, reach only the members of the pod.
- After a revocation, a signature alone cannot show when a record was signed, because there is no trusted clock. So after a revocation, the verifier relies on stamps (DR-20). The witnesses order each stamp against the revocation.

**Example.** Alice's laptop writes a record in the Hiking pod, and the record names Alice's AID and `D-laptop`. Bob's phone verifies the record against the record key that Alice's KEL lists for `D-laptop`. An accepted rotation of Alice's KEL lists `D-laptop`, and no later one drops it.

### DR-19. A device syncs a pod only while it is linked and its identity is a member

**Decision.** A device may sync a pod only while its identity is a member of the pod and the device is linked to that identity. Every peer checks both conditions, for the devices of its own identity and for other members' devices alike. A revocation must therefore reach every device of every member of every pod that the identity is in. A device may hold a removal of its identity from a pod, or a leave written in its identity's name. It receives such a removal or leave once, from an honest device that gives it the pod's membership store up to and including the removal or the leave (DR-40). In that same exchange, it hands over its stamps that cover its identity's records up to the removal or the leave, and honest peers check them like any stamp and publish them into the pod. It then stops all sync with the pod, the membership store included, but keeps its replica. Honest devices serve it nothing more of the pod. A device that writes a leave itself keeps syncing the record store until a stamp that covers the leave is published there, and only then stops, since otherwise no stamp would cover the leave, and the leave would lose acceptance once that device is revoked. For example, Alice's phone writes its leave A70 from the Hiking pod, gets a stamp a second later, publishes it in Hiking, and then stops syncing Hiking. After Bob removes Mallory, her phone receives the removal from Carol's phone, hands Carol's phone its last stamp in the same exchange, and stops syncing the pod. Carol's phone publishes the stamp. A device that holds a removal or a leave can tell its user why it stopped. It checks the removal or the leave again whenever the KEL of the identity that wrote it changes, and it resumes syncing the pod if the removal or the leave is no longer accepted. A device that does not yet hold its removal, because the exchange was cut off, asks again at its next session with a member's device. Otherwise the member comes back only through a new join of her own, which reaches her other devices, including those that already stopped, through the identity's private metadata store, which her devices always sync among themselves (DR-40). The device then resumes syncing the pod, and every device that holds the join treats the member as present and syncs with her devices as with any member's.

**Why.** Membership lists identities, not devices (DR-38). Without the check that the device is linked, a revoked laptop would keep syncing with Bob's devices. A removal written by a revoked device is accepted only if a stamp from before the revocation covers it (DR-20). The revocation of the device that wrote the removal reaches the removed member through the KEL of that device's identity. The removed member's device gets that KEL from any peer or from the identity's witnesses (DR-15). The revocation does not reach the removed member through records of the pod from which the member was removed. Without checking the removal again, a removal that a thief wrote after the revocation would cut honest members off for good. The removed member's device keeps its replica so that it can resume if the removal loses acceptance. The cost is that a former member keeps the pod's data up to the removal. Once a device holds its removal, the pod has nothing more to give it. Later membership acts would only show a former member every later join and removal, and her way back is a new invite, which reaches her outside the pod's sync. A stamp that the device does not hand over in that one exchange never reaches the pod, and its records would then lose acceptance once the device is revoked (DR-20).

**Example.** Alice revokes her laptop. Bob's phone stops syncing with the laptop once Bob's phone holds the revocation. In another case, a thief has Alice's phone, and the phone is revoked at 10:06. At 10:07, the thief uses the phone to write record #441 in the Tokyo pod, and that record removes Bob. At 10:08, Carol's phone, which has not yet seen the revocation, gives Bob's phone the Tokyo membership store up to #441. Bob's phone hands over its last stamp and stops syncing the Tokyo pod, and it shows Bob that he was removed. At 10:10, Bob's phone asks Alice's witnesses for her KEL, as it does while it holds a removal (DR-15). It sees the revocation, finds that no stamp from before the revocation covers #441, and resumes syncing the Tokyo pod.

### DR-20. A revoked device's records are accepted when a stamp from before the revocation covers them

**Decision.**

- Revoking a device is a rotation of the identity's KEL whose role statement no longer lists the device's entry (DR-14). The rotation also drops the device's key from the key set, except when a device replaces its own record key (DR-6, DR-22). Then the device's new entry pairs the key that the rotation commits to for the device with the new record key. From then on, the old record key and the old device id's endpoint binding have no authority. Whether a device is revoked is decided by the role statement alone. A record key that a rotation dropped is never listed again, so every new linking uses a new device id. Nothing about pods is anchored in the identity's KEL.
- A stamp is a set of key state statements (DR-15) from a majority of the identity's witnesses that agree on the position, the event digest and the root. One of the identity's devices requests it. Each statement names the identity's AID. It gives the position of the latest event of the identity's KEL that its witness has receipted, and the digest of that event. It also carries the root that the requesting device supplied, and the date on which its witness signed it. The witnesses' dates may differ, and each statement keeps its own. The root is the root of a Merkle tree. Each leaf of the tree names a pod, a device id of the identity and the digest of the newest record on one branch of that device id's chain in the pod. Each leaf also holds a fresh random salt. A tree holds one leaf for each branch that it covers. The leaves are in random order, and the tree is padded to 256 leaves. Leaves and inner nodes carry distinct prefixes, and leaves have a fixed length. A device with more than 256 pods to cover requests several stamps. A device sends every stamp request, and so every own fetch, to every witness of its identity, and the request succeeds with the answers of a majority. The stamp holds the statements of the witnesses that answer with the same position and event digest.
- Every own fetch of the identity's KEL is also a stamp request for the device's own records (DR-15). So a device requests a stamp at the start of each signing session (DR-21) and at each of its other own fetches. The stamp covers the device's newest record in every pod in which the device wrote since its previous stamp. The device publishes the stamp into each of those pods, together with the path from that pod's leaf to the root. A device that wrote nothing since its previous stamp sends the root of a padded tree of random leaves, and publishes nothing. A stamp covers the record that a leaf names, and every record in that record's history (DR-17). No write waits for a stamp. A stamp request needs no user presence, since the device signs nothing to make it.
- A device may sign a revocation of a device of the identity, whether of another device or of its own old device id (DR-6, DR-22). Before it signs, it requests a stamp for the revoked device's records that it holds and that no published stamp covers yet. On each branch, that stamp covers the newest such record. The signer stores that stamp durably before it signs. It publishes the stamp once the revocation is released, or after a restart if it stopped before publishing.
- After a device is revoked at a position of the identity's KEL, a record of that device is accepted only if a stamp covers it. The stamp must give a position below the position of the revocation. It must name the identity of the record's device, and the event digest that it gives must equal the digest of the accepted event of the identity's KEL at that position. Its statements must come from a majority of the witnesses that the identity's KEL lists at that position, which are the witnesses that the event at that position lists. So at the position of a rotation that changes the witnesses, the KEL lists the new witnesses. The dates of the statements play no part in this rule, so a stamp from March still covers its records in November. A covered record is accepted on every branch of the revoked device's chains (DR-22).
- Every member's device checks that the other members' devices keep requesting stamps. For each other device and each pod, the member's device stores its own witness time at the moment when it receives the first record of that device that no stamp covers. This value is the start of the window, and the member's device stores it durably with the replica. When a stamp covers the record that set the start, the start moves to the witness time at which the member's device received the oldest record of that device that is still not covered. For example, Bob's phone receives Alice's #431 on Monday at 17:40 of its witness time and #441 on Tuesday at 9:00. A stamp that covers #440 arrives on Tuesday at 10:00, so the start moves from Monday at 17:40 to Tuesday at 9:00. Once its witness time is 7 days past the start and the records are still not covered, the member's device shows its user that the other device's records are not stamped. It then accepts no further records from that device in that pod until a stamp covers them. This period is called the 7-day window. This is each device's sync policy, not part of the rule that decides which records are accepted.
- A stamp's digest is computed over what its statements agree on: the domain tag, the identity's AID, the position, the event digest and the root. It leaves out the dates, the signatures and which witnesses signed. A replica checks a stamp before it stores it. Among other things, it checks that the leaf that the stamp uses names the replica's own pod and the record's device id. A replica stores stamps by their digest and keeps the first valid copy of each, so a stamp is never overwritten. For each device and each branch of its chain, the replica keeps the stamp that covers the highest record. It drops an older stamp only once it holds 3 things. The first is a valid newer stamp that covers the same record or a later one on the same branch. The second is the records that place the older stamp's record in the history of the newer stamp's record. The third is a KEL that shows that no event after the older stamp's position, up to and including the newer stamp's position, revokes that device. After a device is revoked, the replica drops the device's stamps at the position of the revocation and at higher positions.
- At each start, a device repeats every step that an event triggers and that a kill of the app may have cut short. It checks again each removal or leave of its identity that it holds, against the current KEL of the identity that wrote it (DR-19). It removes the content of each record whose deletion it holds as accepted (DR-17). It publishes each of its stamps into every pod that the stamp covers. A device counts its own record as covered only once a stamp that covers it is in that pod's replica. For example, Alice's phone is killed after the witnesses answer its stamp request and before it publishes the stamp in the Hiking pod. At the next start, it publishes the stamp there. Until then, it counts its Hiking records as not covered, so its next own fetch covers them again.
- A replica keeps the records of a revoked device that nothing covers, marks them as not accepted, and passes them on to other devices. It keeps at most 1 MB of the headers of such records for each identity, and it fetches no record's content until the record is accepted. It keeps first the lowest positions after the highest covered record on each branch, taking branches and devices in turn. It accepts such a record once a stamp that covers it arrives.

**Why.**

- The goal is bounded non-repudiation: a user may disown her most recent records, but never a device's history. A user cannot disown older records by declaring the device stolen. Otherwise a promise made last year could be disowned today. Non-repudiation covers a record's existence, its author, its position and the digest of its content, and the content itself only until the record is deleted (DR-17). A deleted record still leaves its tombstone, the signed body with the content's digest and the signature, so a member who kept a copy of the content can show that it is the content that the device signed.
- There is no trusted clock. The witnesses are the only parties that order anything against the revocation, because they receipt the revocation itself. Each witness receipts each position once and in order, and it signs no key state statement below a position that it has receipted. The majority whose statements make up a stamp and the majority that receipted the revocation share at least one witness (DR-15). So whatever a stamp covers existed before any event after the stamp's position was accepted, and so before any revocation after that position.
- Each device requests stamps for its own records, and the other members only check that it keeps doing so. So the records that a user can disown are at most those written since her device's last stamp. An honest user whose phone is stolen loses at most the records that the phone wrote since its last own fetch and that none of her other devices holds. A dishonest user may have a modified app that never requests stamps, or witnesses of her own that refuse them. She can disown at most 7 days of records for each of her devices, counted on the members' witness time. She can disown those records at any later time, by revoking that device. After those 7 days, the other members accept no further records from that device, and everything stamped before stands.
- Only the member's own witnesses advance the 7-day window, through the member's own fetches. So neither a thief who controls the stolen device's network nor a writer who hides her own witnesses from the members can stop the window. An outage of the member's own witnesses, or a network that cuts the member off from them, does stop it. It stops it visibly, since the member's device shows "can't reach your witnesses", and it stretches the window by the length of the outage (Risk 21). A group that is offline together, on a boat or on a local network without internet access, keeps accepting each other's records. Once back online, each device stamps its records at its first own fetch, so nothing is lost. The start of the window moves when a stamp arrives, so a device that writes and is stamped every day is never shut out after 7 days of ordinary use.
- Members do not request stamps for other identities' records. That would multiply the requests by the number of devices in each pod, and it would show each identity's witnesses who shares pods with whom.
- A stamp names the identity and the digest of its KEL event, so a stamp that an attacker obtains under an AID of the attacker's own covers no record of another identity.
- A record that no stamp from before the revocation covers cannot be told apart from a thief's record written after the revocation. No rule can accept the first and reject the second, and no act of the user can either. Before a device signs a revocation, it requests a stamp for every record of the revoked device that it holds. So a record that no stamp covers is one that none of the user's devices holds. Replicas fetch no content of a record that is not accepted, so for such a record the user's devices hold only its header. An act of the user that accepted it would accept text that nobody on the user's side has seen, possibly the thief's. What is given up are the records that a stolen device wrote since its last own fetch and that no other device of the user holds. The user writes them again if they were hers.
- Because of the salts, the random order and the padding, the witnesses learn neither a pod nor the number of pods. A leaf and its path are published only in the leaf's pod, so pod members do not learn the identity's other pods. The dates in a stamp tell the members of a pod when a member's device fetched its own KEL, such as at the start of a signing session. They already see when that member's records arrive.
- A revocation needs no statement of its own, since the next role statement simply leaves the device's entry out, and it reveals nothing about the identity's pods. A thief who holds the device still holds its record key, and can sign records after the revocation. That is why stamps, not signatures, decide which of the device's records are accepted. The user repairs what a thief did by means of ordinary records, and the thief's records stay in the pod.
- Storing stamps by digest keeps a thief from replacing an older stamp with a useless one. The digest leaves out the dates, the signatures and the choice of witnesses. So 2 copies of one stamp, which cover the same records at the same position, never count as 2 stamps. The dates matter only for freshness (DR-15), and every device keeps the newest statements for that separately. A newer stamp of a higher record on the same branch proves everything that an older one proved, unless a revocation lies between their positions. So the number of stamps that a replica keeps does not grow from day to day. A replica keeps the headers of unaccepted records because a stamp from before the revocation can arrive after them, such as a stamp that the revoking device publishes after a restart. The limit on unaccepted records keeps a revoked device from filling replicas, and peers stop syncing with a revoked device anyway (DR-19).

**Example.** Alice has a phone and a laptop, and Alice's KEL is at position 8.

- Bob is a member of the Tokyo pod. In that pod, the phone wrote records #1 to #430 by Monday afternoon. On Monday at 17:30 the phone starts a signing session, and its stamp at position 8 covers #430. At 17:40 the phone writes #437, "I'll pay the hotel deposit, 500 EUR", and by 17:55 it has written up to #440. The laptop syncs #431 to #440 at 17:56.
- Carol is a member of the Ginger pod. In that pod, the phone wrote #1 to #55, and the phone's latest stamp covers #55.
- Dave is a member of the Hiking pod. In that pod, the phone wrote #1 to #120, and in March it wrote Alice's leave. Stamps covered all of these records at the time.
- The phone is stolen on Monday at 18:00. On Tuesday at 10:00, the laptop and the co-signer revoke the phone. Before it signs, the laptop requests a stamp for the phone's #440, which it holds. The revocation is position 9 of Alice's KEL.
- At 10:30, the thief writes #441 in the Tokyo pod. No stamp below position 9 covers it, so #441 is rejected everywhere.
- In the Tokyo pod, #1 to #440 are accepted, including the promise. In the Ginger pod, #1 to #55 are accepted. In the Hiking pod, #1 to #120 and the leave are accepted.
- Suppose instead that at 17:58 the phone also wrote #441, "hotel booked", and #442. Suppose too that its fetch after writing got no answer before the theft, and that only Bob's phone received the 2 records. Before it revokes the phone, the laptop stamps #431 to #440, the records that it holds. #441 and #442 stay rejected, and the thief's record at 10:30 is #443, which is rejected too. Alice's devices hold only the headers of #441 and #442, and Alice writes "hotel booked" again if it was hers. Nothing older is lost.

**To verify.** That the sync engine can undo the effects of a record that is no longer accepted, redo them when a stamp arrives later, accept both branches of a fork, store stamps by digest, and keep the headers of unaccepted records without their content. Also, that a replica can hold at most 2 branches of a device's chain in a pod, refuse a record that would start a third, and pass branches on in the order in which it accepted them (DR-22).

### DR-21. A revocation names no record, and a device fetches its KEL before writing

**Decision.** A revocation names none of the revoked device's records, so the revoking parties have no say in which of those records are accepted. Every record of the revoked device that a stamp from before the revocation covers is accepted. Before a device writes in a signing session, it tries to fetch its identity's KEL from its identity's witnesses. That own fetch is also its stamp request for its own newest records (DR-15, DR-20). The answers also make its copy of the KEL fresh and move its witness time forward. The device writes whether or not the witnesses answer. It syncs with the identity's other devices whether or not it has reached the witnesses.

**Why.** If the revoking parties named the last record that they accept, a dishonest user could disown records. That user would let a device that holds none of the revoked device's records carry out the revocation, and that device would name an early record. The fetch before writing lets a device learn of a revocation early. Writing and syncing while the witnesses are unreachable do not change which records are accepted. So devices on a local network without internet access can still sync with each other, for as long as the outage lasts. No device reaches its witnesses, so no member's witness time moves, and the 7-day window of DR-20 does not advance. Once the devices are back online, each device's first own fetch stamps its records (DR-15).

**Example.** In the first case, Alice is dishonest. She wants to disown her phone's record #200 in the Tokyo pod, written last month. She links a tablet, which holds none of the phone's records, and the tablet revokes the phone. But the phone's own stamp from a signing session after #200 covers it, so #200 stays accepted. In the second case, Alice is in a cabin, and her phone and laptop sync over a local network without internet access. The phone writes #451 to #500, and the laptop holds them. The phone is stolen before it reaches the internet. When the laptop revokes the phone, the laptop first requests a stamp for #500, so #451 to #500 are accepted. In a third case, Alice, Bob and Carol spend 10 days on a boat, and their phones sync the Tokyo pod over a local network without internet access. No phone reaches its witnesses, so each phone's witness time stands still, and every phone shows "can't reach your witnesses". The 7-day window does not advance, so the phones keep accepting each other's records for all 10 days. On landing, each phone's own fetch carries the root of its records from the boat, and the witnesses stamp them at once.

### DR-22. A fork marks a device as compromised and rejects no record

**Decision.**

- A fork of a device's chain of records in a pod (DR-17), or 2 endpoint bindings with different bodies for its device id (DR-7), marks the device as compromised. Honest devices stop syncing with the compromised device, and the identity's other devices alert the user. The mark lasts until the identity revokes the device.
- A device that has marked another device as compromised sends it a fork notice in answer to every sync session that the compromised device opens, and then ends the sync session. The notice carries the 2 records at the fork position, or the 2 bindings. The compromised device checks that both items carry its own signature. It also checks that they are 2 different records of the same device id in the same pod with the same sequence number, or 2 bindings with different bodies. Otherwise it ignores the notice. Before it acts on a valid notice, it stores the notice durably, together with its state of writing nothing more under that device id. It then writes nothing more under that device id, and it offers the user a replacement of its record key. Before it signs, it requests a stamp for its old device id's records (DR-20). A sole device signs alone a rotation that drops its old entry and lists a new entry, with a new record key on the same hardware, and so a new device id (DR-6, DR-10). A single device with an external co-signer signs that rotation together with the co-signer. A device with siblings is revoked and linked again. The app then lists the records that the device wrote after the fork position, and it offers to send them again, as new records under the new device id.
- The fork itself rejects no record. Until the revocation, the device's records on both branches are accepted, since the device is still linked. From the revocation on, stamps decide which of the device's records are accepted, and this holds on both branches (DR-20).
- A replica holds at most 2 branches of each device's chain in each pod. It refuses a record that would start a third branch, and it never drops a branch that it holds. Records that extend a held branch are accepted as usual. A device passes a forked device's branches on to its peers in the order in which it accepted them. This is each device's sync policy, not part of the rule that decides which records are accepted.
- After a device starts, and before it writes in a pod, it asks the pod's peers for its own newest record in that pod, and it continues its chain from there. It writes anyway if no peer answers, since local-first operation requires this, and it catches up once a peer is reachable. Every platform does the same, and no device keeps the position of its newest record anywhere outside the app's data.
- A device commits each record durably before the record leaves it, whether in a sync session or as a leaf of a stamp request. A failed commit, such as on a full disk, ends the write with an error, and nothing is sent.
- Sometimes a device's data goes back to an older state while its hardware keys survive, as after a Time Machine restore or the restore of a Windows system image. This is called a rollback. A rollback that the check of peers misses makes a fork, such as a rollback after which the device writes while no peer answers. The fork notice tells the device, and the device gets a new device id, as described above. A device with siblings is revoked and linked again. A sole device, or a single device with an external co-signer, replaces its own entry. The fork rejects no record, so both branches stay accepted until the revocation. After the revocation, a record of either branch stays accepted when a stamp from before the revocation covers it (DR-20). The records that the rollback erased from the device and that no stamp covered lose acceptance at the revocation, even though members accepted them before. The device does not hold them, so it cannot stamp them. These are the records that the device wrote after both the backup and its last own fetch before the restore. A device fetches, and so stamps, after it writes. So these are usually the records of the last few minutes of writing before the restore, or before the device went offline. Keeping them is a route not taken, described at the end of this document.

**Why.**

- The witnesses order the identity's KEL (DR-15), but they see none of a device's record chains and none of its endpoint bindings, so the pod members detect a fork. A device signs one binding for life (DR-7). So a second binding with a different body is evidence of the same kind as a fork: 2 different items that the device's record key signed where it signs one. A pod member's device notices a fork as soon as it holds both branches, and a second binding as soon as it holds both bindings.
- A fork has one of 2 causes. In the first, a thief or malware shows different records to different members. In the second, an honest device's data goes back to an older state while its hardware key survives, which is a rollback. Nothing in the records tells the 2 causes apart, so both causes are handled the same way.
- The fork rule picks no branch. A rule that rejected one branch would let a dishonest user disown records. A modified phone would sign a rival record at an earlier position, and the honest branch would be lost. Both branches are the identity's, since the device signed both while it was linked.
- For the same reason, no rule chooses which branches survive. Such a rule would let whoever made the fork choose which branch is dropped. If the lowest digest decided, that party would compute rival records at an old position until they had lower digests than the real record, and the real branch would be lost with everything after it. If the earliest stamp decided, rivals stamped months later would tie with the real branch, since the position of the identity's KEL can stay the same for months. A replica therefore keeps the branches that it accepted first, and refuses further ones. A branch that a replica has held for months is never pushed out by a rival that arrives later.
- The limit of 2 branches loses no honest record. An honest device forks only after a rollback, and its peers stop syncing with it once they see the fork, so its third branch would reach no peer anyway. The limit bounds what a modified app achieves by forking into many branches. Each replica holds at most one rival. The stamps that a replica keeps for each branch, and the records that a removal lists for each branch, stay few. Passing branches on in the order of acceptance gives a newcomer the long-held branch first. A member who writes too much on a single chain is no fork. The pod's owners remove such a member, and each device protects its storage with its own quota for each pod.
- A record that left the device before it was committed would be lost at an ordinary kill of the app. The device would then write a different record at the same position, which makes a fork.
- Asking peers works because everything that the device ever sent is held by some peer. A record that the device never sent can be replaced by a new one at the same position without harm, since no other copy of it exists for the new one to clash with.
- A device writes even when no peer answers, since otherwise every start without a reachable peer would stop the device from writing. A rollback that the check misses costs one linking and loses no accepted record. That cost is small enough that no platform stores positions outside the app's data to catch such a rollback. Such positions would have to be kept out of backups, and raised before every record is sent.
- An honest rollback happens on desktop computers. A Time Machine restore or a Windows system image brings back old app data, while the key stays in the Secure Enclave or the TPM. On Android, uninstalling the app, clearing the app's data or moving to a new phone deletes the Keystore keys together with the data. The phone then comes back as a new device, with nothing to fork. Keeping the key while the data goes back takes a rooted phone or a snapshot.
- An honest device that forks is revoked like a stolen device, because nothing in its records tells it apart from a device in a thief's hands. The cost is one linking.
- A sole device has no sibling to alert the user, and its peers go silent without a reason, which looks the same as a removal or a peer that is offline. The fork notice tells the device why. It comes in answer to every sync session, and the device stores it before acting, so a kill of the app before the device acts loses nothing. It cannot be forged, since both items carry the device's own signature, and it shows the device nothing that the device did not sign itself. The device cannot tell which of its records after the fork position reached a peer before its peers stopped syncing with it. So the app lists them all, and it leaves it to the user to send them again under the new device id.
- The fork rule is our own. On duplicity, KERI itself either stops trusting the identifier as a whole, or lets each validator keep the event that the validator saw first.

**Examples.**

- **A rollback that the check catches.** Alice restores her Mac's app data from last week's Time Machine backup. The restore brings back older data, while the Secure Enclave keys stay, so the Mac still signs with its record key, as `D-mac`. The backup does not hold the Mac's iroh endpoint secret (DR-7), and here the restore leaves the secret in place. Had the restore lost it, the Mac would be linked again with a new device id (DR-7). The restored data says that the Mac's newest record in the Tokyo pod is #300. During the week, however, the Mac wrote records up to #340, and Bob's phone holds all of them. When the Mac starts, and before it writes in the Tokyo pod, it asks the pod's peers for its own newest record. Bob's phone answers #340 and sends #301 to #340. The Mac's next record is #341, not a second #301. Suppose the Mac had also written a record #341 just before the restore, and that record never reached a peer. Then the new #341 takes the place of the old #341 without harm, since no other copy of the old #341 exists.
- **A rollback that the check misses.** Alice restores her Mac's app data from last week's Time Machine backup and boards a plane. The Secure Enclave keys stay, and the restore leaves the Mac's iroh endpoint secret in place. No peer is reachable, and the restored data says that the Mac's chain in the Tokyo pod ends at #300, so the Mac writes #301, "hotel booked", at once. But Bob's phone already holds the Mac's earlier #301 to #340, and a stamp from earlier in the week covers #340. When the Mac is online again, it requests a stamp, and Bob's phone receives the new #301. Bob's phone now holds 2 records at position 301, which is a fork. Bob's phone sends the Mac a fork notice and stops syncing with it, and Alice's phone tells her that the Mac looks compromised. She revokes the Mac and links it again, and the Mac gets a new record key and so a new device id. Stamps from before the revocation cover both branches, so the Mac's earlier #301 to #340 and the new "hotel booked" are all accepted. The Mac's app lists the new #301 as written after the fork position. Alice sees "hotel booked" in the Tokyo pod on her phone, so she does not send it again.
- **A sole device that forks.** Alice has only a Windows PC. She restores last week's system image on a plane, and the PC writes #301, "hotel booked", and #302 in the Tokyo pod. Bob's phone already holds another #301 of the PC, so it sends the PC both records at position 301 and stops syncing with it. The PC tells Alice that it wrote 2 different records at position 301, probably after a restore. Alice confirms, and the PC signs a rotation alone that drops its old entry and lists a new one, with a new record key. It finds its committed key by the digest in the KEL (DR-16), since the restore rolled back its app data too. The app then lists #301 and #302, the records that the PC wrote after the fork position. Bob's phone stopped syncing before it received #302, so Alice sends #302 again under the new device id, and Bob's phone syncs with the PC once it has fetched Alice's KEL.
- **A thief's fork.** Malware in the app on Alice's phone signs a second record at position 301 of the phone's chain in the Tokyo pod, and shows that record only to Bob. Carol's phone holds the real #301. When Bob's phone syncs with Carol's phone, Bob's phone holds both records at position 301. Every member's device that sees the fork stops syncing with Alice's phone. Alice's laptop alerts her, and she revokes the phone. The real #301 is accepted, since stamps from before the revocation cover it. The malware's record is accepted only if a stamp from before the revocation covers it. If a stamp does cover it, that is the accepted risk of malware in the app (Risk 2).
- **Android.** Alice clears the app's data on her Android phone. The Keystore keys are deleted together with the data, so the phone holds no record key of its old device id and cannot sign at an old position. The phone is linked again as a new device, and nothing forks.

**To verify.** That restoring an iPhone from a backup always erases its Secure Enclave keys, so that an iOS restore makes the phone a new device with nothing to fork, as on Android.

## Signing and presence

### DR-23. 2 strengths of signature, 2 levels of presence

**Decision.**

- There are 2 strengths of signature. Day-to-day acts are records. One device signs each record with its record key (DR-6). Linking a device and revoking a device are rotations of the identity's KEL, signed by any 2 parties, by a sole device or by a recovery key. A recovery rotation, signed by a recovery key, also adds the recovering device when that device is not already linked (DR-26, DR-27).
- A rotation asks for the user's presence, by fingerprint or device passcode, at every signature.
- The record key asks for the user's presence once per signing session, and then signs without asking until the signing session ends. A signing session ends when the app or the device locks, or after a period of inactivity that a product setting defines.
- On Android, the record key stays usable for a set time after authentication (`setUserAuthenticationParameters`). On iOS and macOS, one authenticated `LAContext` authorizes signatures until the app invalidates that `LAContext`, so the app ends the signing session itself.
- The platform makes the record key unusable while the device is locked. After an authentication, the key signs without a new authentication for at most 1 hour. That period is called the key's window. On Android, the Keystore enforces the window with its own timer. On iOS and macOS, the app enforces the window by invalidating the `LAContext`, on a platform timer that a change of the device's wall clock does not move. There, the bound that the platform itself enforces is the device lock. When the window closes, the app asks for presence again. The window only limits how long the device signs without asking, and it decides nothing about which records, stamps or rotations count.

**Why.** A fingerprint before every record would be too much, while one fingerprint at the start of a signing session is acceptable. The signing session itself is a rule of the app. On Android, an unlock of the lock screen also opens the record key's window, and the window runs on its own timer. So the platform's limits keep a locked phone from signing anything. A thief who uses a stolen, unlocked phone through the app signs for at most an hour, unless the thief can authenticate again (Risk 9). On Android, the Keystore enforces that hour. On iOS and macOS, the app's own timer enforces it, so there the hour relies on the app. Malware inside the app bypasses the app's timer, and malware inside the app is an accepted risk too (Risk 2). The price is at most one prompt an hour. Rotations change who controls the identity, so every rotation needs the user to be present on each device that signs it.

**Example.** Alice opens Tellipod at 9:00 and touches the fingerprint sensor once. She then writes in 3 pods without a prompt until 10:00, when the app asks for her fingerprint again, and so on through the day, at most once an hour. In the evening, linking her new tablet asks for her fingerprint again, and her laptop, which co-signs the rotation, asks for it too.

**To verify.** Windows: Windows Hello has no stable, documented mode in which a key stays usable for a set time. It has only a prerelease cache configuration, `KeyCredentialCacheConfiguration`. Until that configuration is tested, a Windows device may have to ask for presence at every record. iOS and macOS: whether the platform caps how long an authenticated `LAContext` authorizes signatures with a Secure Enclave key, and whether one authenticated `LAContext` also authorizes the device's key in the key set without a new prompt.

### DR-24. Nothing is signed without the user present

**Decision.** No device signs a record outside a signing session. Anything that the app would write on the user's behalf waits for the next signing session. Background sync continues: it moves records that others signed, and it authenticates with the iroh endpoint key, which signs no records. Stamp requests continue as well, since they sign nothing (DR-20).

**Why.** Every record that an identity signs is binding (DR-20). Signing only while the user is present keeps the number of acts that nobody chose small.

**Example.** Alice sets a reminder to post in the Tokyo pod at 7:00. The reminder is posted when she next opens the app, at 8:15.

## Recovery and the co-signer

### DR-25. Recovery is the user's choice: the Tellipod service, a paper sheet, both or neither

**Decision.** The design offers 2 ways back: a recovery key held by the Tellipod recovery service, and a recovery key written on a paper sheet. An identity commits to either, to both, or to neither, as its user chooses, and the user may add or drop either one later. Each recovery key has weight 1, so either one alone can recover the identity. The app offers the service first. A person who does not want to rely on Tellipod uses the paper. A person who relies on something else may use neither. Whether a backup of a device made by a tool of her own can serve as a way back is an open question, described at the end of this document. A user without a recovery key who loses every device loses the identity.

**Why.** Whether to keep a way back is the user's call, since each way back is also a way in: a recovery key that someone else obtains can take the identity. The design provides the options and does not require one. Where a recovery key exists, it must outrank a stolen device whose thief does not know the user's PIN. The exception is a sole device without an external co-signer, which carries weight 1 (DR-10). A thief who has both the device and the PIN is an accepted risk (Risk 1). Recovery must also restore an identity whose devices are all lost. With both recovery keys, the identity survives the loss of either backend. The price is that a theft of either backend's key exposes the identity, since the first recovery can drop the other backend's key. For an identity with an external co-signer, the paper outranks a stolen device only together with an honest external co-signer. An honest external co-signer drops or replaces the paper's key only after the PIN check (DR-30). The paper also outranks the stolen device only while the thief holds no second device of the user.

**Example.** Alice's next keys are: phone 1/2, laptop 1/2, co-signer 1/2, recovery service 1, paper 1. A burglar who finds the paper owns the identity, even though Alice still knows her PIN. Dave chooses neither way back and keeps encrypted backups of his phone with a tool of his own. If he loses his phone and cannot restore it, his identity is gone.

### DR-26. The recovery service is non-custodial

**Decision.** The Tellipod recovery service keeps the recovery key inside the enclave that checks the PIN (DR-31). For each identity, the enclave keeps 4 things. The first is the PIN's verifier, which lets the enclave check a PIN without storing the PIN itself. The others are one count of wrong PINs, one sealed secret, and, when the identity uses the Tellipod co-signer, the Tellipod co-signer's keys for that identity. The sealed secret holds what the app puts in it: the recovery key, the identity's AID and its witnesses. The app first encrypts that content under a key derived from the PIN, so the enclave holds only that ciphertext. The enclave stores it sealed, which means encrypted again under a key that only the enclave can use, and it never reads it. The enclave releases the sealed secret only after the user passes the email check and enters the correct PIN (DR-32). An email code works once, and the next request voids it. After every change of the identity's witnesses, the app refreshes the sealed secret with a request that carries the PIN and replaces only the sealed secret, keeping the enrolment and its co-signer's keys. It sends that request the next time the user types her PIN, such as at the next co-signing, so it never asks for the PIN for this alone. The sealed secret then names the current witnesses, as the card does for the paper sheet (DR-27). The phone that carries out the recovery takes the AID and the witnesses from the sealed secret. It fetches the identity's KEL from those witnesses, and it follows each change of the witnesses (DR-16). It then signs the recovery rotation itself. The app lists the identity's devices and selects all of them to be dropped by the recovery rotation, and the user may keep a device that she knows is safe, such as a laptop at home, by unselecting it. A device that is dropped is revoked, and only the records that a stamp from before the recovery covers stay accepted (DR-20). For example, Alice's phone is stolen, and she recovers with the service on a new phone. She keeps her laptop, which is switched off at home, and the recovery drops only the stolen phone. That rotation lists the phone's entry, with its key in the key set and its record key, as a linking does (DR-6). The phone also enrols the identity again, with a newly generated recovery key. For an identity with the Tellipod co-signer, the phone also enrols a new co-signer's key. The recovery rotation commits to the new keys. A user who has lost the PIN and every device, and has no paper sheet, has lost the identity. Each enrolment is stored under a random enrolment identifier, which the email check finds and the identity's devices keep. The identifier travels among the identity's devices in the identity's private metadata store. Each device keeps it out of backups, beside the wrapped secret of its endpoint key (DR-7). Every request to the enclave names the enrolment identifier. It reaches the enclave over a channel that ends inside the enclave, so the operator sees neither the PIN nor what an enrolment holds. The enclave answers a request that names an enrolment that it does not hold with the refusal "no such enrolment", which differs from the refusal of a wrong PIN. The app attaches an encrypted label to each enrolment. A user with several identities under one email address then picks the enrolment, and a PIN is tried only against the enrolment that she picks. For example, "Alice" and "Alice-work" are enrolled under one address. After the email check, Alice's new phone shows both labels, she picks "Alice-work", and her PIN is tried against that enrolment alone. Tellipod runs both the recovery service and, by default, the witnesses, and its witnesses see the enrolling and the recovering rotation seconds after the service sees the enrolment, so Tellipod can still connect an enrolment to its AID. A new enrolment of the identity names the enrolment that it replaces, passes the email check of that enrolment's address, and gives the old enrolment's correct PIN. A user who has forgotten her PIN does not replace her enrolment: her devices make an independent new enrolment, the rotation commits to its keys, and the old enrolment stays behind unused, holding only keys that the KEL no longer commits to. At each signing session, the app asks the enclave whether its enrolment still exists. On the refusal "no such enrolment", it alerts the user and enrols the identity again with 2 parties. The enclave keeps the new enrolment beside the old one, and the old one keeps working. Once the rotation that commits to the new enrolment's keys is accepted, the device confirms the new enrolment with the PIN, and only then does the enclave erase the old enrolment, together with its sealed secret and its co-signer's keys. If that rotation never takes effect, the device tries again with the enrolments as they are. The same order applies when an identity is created with the Tellipod co-signer: the enclave first creates the co-signer's keys under a new enrolment whose sealed secret is still empty, the inception commits to those keys, and after the inception the device sets the sealed secret once, with the AID, the witnesses and the recovery key. Every revocation of a device of an identity that has an enrolment also enrols the identity again, in the order above: the revocation rotation commits to the new enrolment's keys, the revoking device confirms the new enrolment once that rotation is accepted, and the old enrolment is erased. An identity that uses the Tellipod co-signer always keeps an enrolment, since the enrolment holds the co-signer's keys. When such an identity does not use the recovery service, its sealed secret holds no recovery key, only the AID and the witnesses. Leaving the recovery service therefore replaces the enrolment with one that holds no recovery key, in the order above, and an enrolment is erased outright only when the identity uses neither the recovery service nor the Tellipod co-signer. Erasing an enrolment on request needs the correct PIN, and a wrong PIN in an erase request counts like any other wrong PIN (DR-32). The enclave reads no KEL, and it has no other rule for erasing. The service notifies the enrolled email address of every wrong PIN.

**Why.** A service that held a usable recovery key, of weight 1, could rotate any identity alone. Its operator, an intruder or a legal order served on the service could then rotate any identity through the service. The service does hold personal data: an email address tied to a sealed secret. Through that data, Tellipod can tell that 2 identities belong to one person when they recover through the same email address. A recovering phone knows neither the identity's AID nor its witnesses. So the sealed secret carries them, as the paper sheet does (DR-27), and the enclave keeps no AID of its own. Erasing needs the PIN, so a thief who finds the enrolment identifier on a stolen phone cannot erase the user's recovery key by asking. A distinct refusal for a missing enrolment keeps a device whose enrolment was replaced or erased from taking that for a wrong PIN. A PIN tried against one picked enrolment spends no tries of the user's other identities. A new enrolment replaces the old one, so a recovery or a new PIN leaves no old key behind, and the enclave needs no rule that reads the KEL. The replacement waits for the device's confirmation, because a rotation can fail to take effect after its keys exist: the app can be killed before the rotation is stored, or another rotation can take its position. The KEL then still commits to the old keys. If the new enrolment had already erased them, an ordinary interruption would leave the identity committed to keys that nobody holds, and a user without a paper sheet or another device would lose the identity. Keeping both enrolments until the confirmation means that one of them always holds the keys that the KEL commits to. The enclave still reads no KEL: the device, which holds the KEL, decides when to confirm. An identity's AID is the digest of its inception, the inception lists the co-signer's keys, and the sealed secret holds the AID, so at creation the keys come first and the sealed secret last. A user who leaves the service first drops the service's recovery key by a rotation (DR-28). If she keeps the Tellipod co-signer, her phone then confirms a new enrolment without a recovery key, and the old one is erased. Erasing her enrolment outright would also erase the co-signer's keys that her KEL commits to, and her devices could then never rotate with the co-signer again. Only a user who leaves both the service and the co-signer has the enrolment erased with her PIN. Replacing an enrolment needs the old PIN, so that whoever takes over the user's mailbox cannot replace her enrolment with one of his own and so erase her recovery key and her co-signer's keys. The check at each signing session lets a device learn that its enrolment is gone before the user needs it, for example when a stolen phone has to be revoked. A revocation enrols again because the enrolment identifier is a handle for PIN tries and for requests for new co-signer's keys, and a revoked device keeps it. Without a new enrolment, a stolen phone would keep trying PINs after its revocation: each correct PIN that the user enters resets the count of wrong PINs (DR-32), so the thief would get 9 more tries after every co-signing, and his guesses would add up. After the new enrolment, the revoked device names an enrolment that no longer exists and gets only the refusal "no such enrolment". For example, Dana switches from the service to a paper sheet and keeps the co-signer: her enrolment is replaced by one that holds only her AID and her witnesses, and the co-signer's key C5 that her KEL commits to stays in the enclave.

**Example.** Alice loses every device. On a new phone, she confirms her email address and types her PIN. The phone receives the sealed secret, reads her AID and her witnesses from it, fetches her KEL, and signs the recovery rotation. It enrols again with a fresh recovery key, a fresh co-signer's key and her PIN, and the recovery rotation commits to the new keys. Once the witnesses have accepted that rotation, the phone confirms the new enrolment, and the enclave erases the old one. Had iOS killed the app before the rotation was stored, the old enrolment would still hold the keys that the KEL commits to, and Alice would simply recover again. In another case, a thief holds Alice's phone and its passcode, but not her PIN. He finds the enrolment identifier on the phone and asks the service to erase her enrolment. Without the PIN, the enclave refuses, and each wrong PIN that he tries adds 1 to the count (DR-32).

### DR-27. The paper sheet: 24 words, recovery only

**Decision.** The paper sheet holds one generated passphrase of 24 words, taken from the English word list of BIP-39, the Bitcoin standard for mnemonic phrases. That word list has 2,048 words. The 24 words seed one recovery key. The commitment to that key is carried forward from rotation to rotation until the key is used. The sheet also carries the identity's AID and its witnesses, as text and as a QR code. After each change of the witnesses, the app shows a new card with the AID and the current witnesses, for the user to keep with the sheet. The 24 words stay the same, so only the card is printed again. Every use of the paper ends with a new sheet. There is one sheet, kept in one safe place, and not several sheets with a threshold. The paper serves recovery only, and it never stands in for a second party at linking. Each identity gets its own sheet.

**Why.** 24 words carry 256 bits of randomness, plus a checksum that catches most typing mistakes. The 24 words give the recovery key, but not the identity that the key belongs to, nor where its KEL is. The AID and the witnesses are public, and each identity has its own sheet, so printing them connects no 2 identities. A recovering device asks the witnesses on the sheet, and the witnesses built into the app, and follows each change of the witnesses to the current ones (DR-16). The card matters only when, along the way from the sheet's witnesses to the current ones, every witness of one set is gone. Typing the words exposes the key, and that is why every use ends with a new sheet. Using the paper for routine linking would expose the key on devices that may be compromised, while linking can simply wait for a second party.

**Example.** Alice has no external co-signer, and she loses her phone. Her laptop alone carries 1/2. She types the 24 words on the laptop. The laptop shows the 24 words of a fresh passphrase, and Alice writes them down. The laptop then signs a recovery rotation that drops the phone, gives the laptop weight 1, and commits to the key of the fresh passphrase. Once the rotation is accepted, the app tells Alice to destroy the old sheet, and she does. In another case, Alice changed in 2027 from Tellipod's witnesses to her company's, and she did not keep the new card. In 2028, she loses every device. Her new phone scans the QR code on the sheet, gets her KEL from Tellipod's witnesses up to the change, and fetches the rest from her company's witnesses.

### DR-28. Replacing a recovery key is an ordinary rotation

**Decision.** Replacing, adding or dropping a recovery key is an ordinary rotation of the identity's KEL. Replacements include a switch from the service to the paper, a new service key, and a new sheet for a lost one. Like every other rotation, such a rotation is signed by any 2 parties, by a sole device (DR-10) or by a recovery key (DR-9), and it is final once it is accepted. Each device that signs it must have chosen that act, such as "replace the recovery key". A device that acts as second party shows that act next to the code that its user types (DR-29). The Tellipod co-signer signs such a rotation after the PIN check, like any other rotation (DR-30). A device keeps a new recovery key only under its wrapping key, out of backups, until the key is enrolled with the recovery service or the rotation that commits to it is accepted. For a new paper sheet, the app shows the new 24 words before the device signs the rotation. It tells the user to destroy the old sheet only once that rotation is accepted. No count of devices and no wait applies to such a rotation. There is no reset of a forgotten PIN. A user with 2 or more devices who forgot the PIN rotates with 2 of them, without the co-signer. Either the rotation replaces the service's recovery key and the co-signer's key, and she enrols again with a new PIN (DR-26), or it drops the co-signer. A sole device without an external co-signer carries weight 1 (DR-10), and it does the same alone. A user with a paper sheet does the same with the paper's key (DR-27). A user with one device, an external co-signer, no paper sheet and a forgotten PIN can no longer change her devices. Her device keeps writing records. When she needs a new device, she moves to a new identity. Her old identity hands each pod that she owns over to the new identity by membership acts. In her other pods, an owner invites the new identity, as DR-16 describes for lost witnesses. The app reminds every user of her PIN from time to time, as Signal does, so that few users forget it (Risk 16).

**Why.** "I lost my paper" is also what a thief would claim, but a count of devices or a wait would not stop a thief who meets the threshold. KERI's threshold cannot express a majority of the devices, since one device plus the external co-signer already meets the threshold. So such a rule would bind only the signers who choose to apply it. Any 2 parties may first revoke the identity's other devices, by an ordinary rotation that commits to the recovery key again, and they are then the majority. A thief who holds a device and the user's PIN first drops the external co-signer, which leaves no party to hold a wait (Risk 1). A majority of the devices or a wait would therefore bind only honest users, who would wait weeks for a new sheet. So a replacement is an ordinary rotation. The recovery key still outranks every party that cannot meet the threshold. A thief who holds one device without the PIN gets no second signature for a replacement: the Tellipod co-signer needs the PIN, and the user's other device needs the code from the thief's screen (DR-29). A rotation that is signed but never accepted leaves the KEL committed to the old recovery key. So the old sheet has to survive until the new one is committed. A new key kept in a backup would be a recovery key that the backup's holder could use. A reset of a forgotten PIN would be the one act that the co-signer signs without the PIN. One device and the co-signer meet the threshold. So without a wait, a thief who holds the phone and its passcode would take the identity at once through such a reset. A wait needs time inside the enclave, and the enclave has no notion of time (DR-31). Every user who has a second device, a paper sheet or no external co-signer rotates without the co-signer, and so needs no reset. The one user left without a way back is the user with one device, an external co-signer and no paper sheet who forgets her PIN. While her device works, she keeps her pods by moving to a new identity, and the app's reminders of the PIN make that case rare (Risk 16).

**Example.** Alice has a phone, a laptop, the Tellipod co-signer and a paper sheet, and she loses the paper. On her phone, she chooses "replace the recovery key". Her laptop shows that act and asks her to type the code that the phone shows. The phone and the laptop sign the rotation that commits to the key of a new sheet, and it is final at once. Had her laptop been at the office, her phone and the co-signer would have signed the same rotation once she entered her PIN. In another case, Bob has 4 devices and no external co-signer, and he loses his paper. His phone and laptop sign a rotation that commits to the key of a new sheet, and it is final at once. A thief who steals Bob's phone and laptop, with their unlock secrets, can do the same, as he could revoke Bob's other devices first (Risk 4). In a third case, Dana has a phone, a laptop, the Tellipod co-signer and the recovery service, and she forgets her PIN. Her phone and her laptop sign a rotation that commits to a new service recovery key and a new co-signer's key, and she enrols them with a new PIN. In a fourth case, Carol has only a phone, the Tellipod co-signer and the recovery service, with no paper sheet, and she forgets her PIN. Her phone keeps writing in her pods, but it can link no device. When she buys a new phone, the new phone creates a new identity. Her old phone hands each pod that she owns over to the new identity by membership acts, and in her other pods an owner invites the new identity (DR-16).

### DR-29. The second party of a rotation is a role

**Decision.** The second party of a rotation is another device of the user, or an external co-signer. An external co-signer is either the Tellipod co-signer or a co-signer node that the user hosts on an always-on machine. An external co-signer is a PDN node that serves the identity without being one of its devices, and it is reachable over iroh like any device. An identity has at most one external co-signer, and switching to another external co-signer is a rotation. Every second party reads the rotation before signing it, and asks for its user's presence. A device acting as second party derives every change of a rotation from the difference with the previous establishment event. It compares the devices and their record keys, the witnesses and their threshold, the external co-signer, and the recovery keys. It names each change in its prompt, and it refuses a change that its user did not choose. Its user chooses the changes by typing the code under the prompt that names them. For example, Alice's phone asks her laptop to approve a rotation that links a tablet and also replaces her witnesses. The laptop's prompt names both changes, "link a tablet" and "replace your witnesses". Alice chose only the linking, so she does not type the code, and the laptop signs nothing. Before a rotation lists a new device's record key, every signer of the rotation checks the new device's endpoint binding (DR-6). A device acting as second party signs only after its user has typed a code that the device which started the rotation shows. The code belongs to that one rotation and that one asking device, and it is worth nothing for any other. Every prompt of a second party names the act and the device that asks, such as "approve linking a tablet?" or "replace the recovery key?" from the user's phone. The act and the asking device appear next to the request for the code, together with the warning "Tellipod will never ask you for this code. Type it only if you are holding the device that shows it." The app collapses repeated requests from one device into one notice that names the asking device and offers to revoke it: "Your phone keeps asking to link devices. Was it stolen? Revoke it?" A device acting as second party checks in the app that the rotation commits again to every recovery key that the previous establishment event commits to. There are 2 exceptions: a rotation that replaces a recovery key (DR-28), and a rotation that adds a recovery key or drops one, down to none (DR-25). A device signs such a rotation only when its own user chose that act, which means only once its user has typed the code under a prompt that names that act. A device refuses a rotation unless an own fetch made for that rotation succeeded and its copy of the KEL reaches the position that the answers give (DR-15). The Tellipod co-signer checks only the PIN: with a correct PIN, it signs the rotation that it is given (DR-30, DR-32). While no second party is reachable, linking waits.

**Why.** Users choose whether to rely on Tellipod. Another device of theirs can be the second party instead of the external co-signer. Suppose that a thief holds one device without the PIN. The Tellipod co-signer gives him no signature. The user's other devices refuse a rotation that drops the recovery key unless their own user chose that act. So the thief cannot drop the recovery key. A thief who holds a device and the user's PIN gets any rotation signed by the Tellipod co-signer, which is accepted as Risk 1. The witnesses, not the second parties, keep 2 rotations at one position from both being accepted (DR-15). A fetch made for the rotation itself carries a root of its own, so it cannot be answered with statements collected earlier. The device therefore signs only on the KEL that the witnesses hold at that moment, whatever its clock says. Without the code, a thief who holds one device without the PIN could ask another device of the user again and again, until the user taps "approve" out of habit. The code alone makes an approval from a distance impossible, since the user has to see the screen of the device that started the rotation. So however often the thief asks, the user cannot approve by mistake. Showing the act next to the code keeps a user who believes that she approves a linking from replacing her recovery key. Deriving the changes from the rotation itself, rather than from what the asking device says, keeps a stolen device from hiding a second change behind the one that it names. A limit on prompts would add no protection, and it would harm the user. A stolen device that asks 3 times a day would keep the user's other devices from showing the prompt that approves its revocation. A device that keeps asking is a sign that it was stolen, so the app turns its requests into one notice that offers to revoke it. The cost is that 2 devices that sign a rotation together have to be in one place. A lost phone can still be revoked from a distance, through the external co-signer with the PIN, or with a recovery key.

**Example.** Alice links a tablet with her phone. Her laptop shows "approve linking a tablet?" from her phone, checks that the rotation keeps the commitment to her paper's key, asks her to type the code that her phone shows, and asks for her fingerprint. In another case, a thief holds Alice's phone and its passcode, but not her PIN. At 8:00, he asks 3 times to link his own tablet, while Alice is at home with her laptop and her desktop. The laptop shows one notice: "Your phone keeps asking to link devices. Was it stolen? Revoke it?" To approve, she would have to type the code that the phone shows. She does not have the phone, so she cannot approve, even by mistake. At 8:05 she revokes the phone with her laptop and her desktop, and the desktop signs after she types the code that the laptop shows.

### DR-30. The Tellipod co-signer lives in an enclave

**Decision.** The Tellipod co-signer's signing key for each identity is generated inside an enclave and is never exported from the enclave. The enclave signs only after a correct PIN, and with a correct PIN it signs the rotation that it is given, without checking anything else about it (DR-32). Each key of the co-signer signs one rotation, as every key in the identity's key set does (DR-11). So the enclave holds a sequence of keys for each identity, and it answers 2 requests. On the first, it creates a new key and returns its public key, whose digest the device puts among the rotation's next keys. On the second, which carries the PIN, it signs the rotation with the key whose digest the request names, if it still holds that key. The device reads that digest from the identity's KEL. The enclave keeps the last 3 keys that it created for each identity and drops older ones. Witness receipts and key state statements may be produced outside the enclave. A self-hosted co-signer needs no enclave.

**Why.** Without the enclave, Tellipod's operator could co-sign without the PIN. An operator colluding with a thief who holds the user's phone could then drop the user's paper. The enclave checks no rotation. A check inside the enclave would stop nobody who knows the PIN. Such a person can first have the co-signer sign a rotation that links a device of his own, and then rotate with the stolen device and his own device as he likes (Risk 1). Every such check would also be a place for errors in the most critical component (DR-31). The device, which holds the KEL, names the key, so the enclave needs no knowledge of the KEL. A key that is never committed, or whose rotation is never accepted, does no harm. The KEL still commits to the earlier key, and the device tries again. The enclave still holds that earlier key, unless 3 newer keys have been created since, which is Risk 15. Signing with an older key gives nothing, since the witnesses already hold the accepted event at that key's position (DR-16). The witnesses already keep 2 events at one position from both being accepted (DR-15). A dishonest witness receipt is detectable without an enclave, since 2 receipts at one position are evidence in themselves. A stamp at an out-of-date position, by contrast, produces no such evidence, and that risk is accepted (Risk 17).

**Example.** A thief takes Alice's phone and bribes a Tellipod admin. The admin asks the co-signer to sign a rotation that drops Alice's paper. The enclave refuses, since the PIN is missing. A thief who knows the PIN needs no admin, which is accepted as Risk 1. In another case, rotation 4 of Alice's KEL commits to the co-signer's key C5. To link a tablet, her phone first asks the enclave for a new key and gets C6, whose digest it puts into rotation 5. It then sends rotation 5 with Alice's PIN, naming the digest of C5, and the enclave signs with C5.

### DR-31. One PIN, checked in an attested enclave

**Decision.** The Tellipod co-signer and the recovery service share one PIN. One service, backed by an enclave and modelled on Signal's secure value recovery, checks that PIN. Before the app sends anything, it checks the enclave's attestation, a signed statement about the code that the enclave runs. The app checks 3 things about the attestation. The attestation must be signed by a key that is built into the processor and certified by the chip vendor. It must give the hash of a public, reproducible build. Finally, it must show firmware that the vendor has not withdrawn. The app checks the dates of the vendor's certificates and of its list of withdrawn firmware against witness time, never against the device's clock. It refuses a list that was issued more than 30 days before its witness time. As Signal does, the app stretches the PIN into 2 values with Argon2, a function that is slow to compute, so that each guess at a PIN costs time. One value proves the PIN to the enclave, and the other encrypts the sealed secret (DR-26). The app sends the first value over a channel that ends inside the enclave, and every other request to the enclave travels over that channel too. The enclave keeps for each identity only what DR-26 lists, and it checks only the PIN (DR-32). The count of wrong PINs is replicated across several enclaves. The enclave has no notion of time, and none of its rules depends on a clock. A desirable enhancement is to split the sealed secret and the count of wrong PINs across enclaves of different chip vendors at different cloud providers, or across independent operators. A self-hosted co-signer checks its own, separate PIN with OPAQUE, a password protocol that never sends the PIN to the server. Like the enclave, it keeps one durable count of wrong PINs, and it erases its keys at the 10th wrong PIN in a row (DR-32).

**Why.** The rules fit in one paragraph that the app can show its users: "Tellipod keeps your recovery key in a sealed vault that only your PIN opens. Nobody at Tellipod can open it. After 10 wrong PINs, the vault destroys the key for ever. Tellipod's co-signer approves changes to your devices only with your PIN, and the same 10 tries count for it too."

The rules are kept this simple for 2 reasons. Users have to be able to understand them and to trust them. And every rule about time or about the KEL inside the enclave would be a place for errors in the most critical component of the design. So the enclave keeps 4 things for each identity (DR-26), checks nothing but the PIN, and erases after 10 wrong PINs in a row (DR-32).

A short PIN is safe only if nobody can guess it offline, the operator included. On its own, a password protocol such as OPAQUE keeps the PIN off the network. But whoever holds what the server stores for the user can still try all 1,000,000 PINs of 6 digits in seconds. The enclave's hardware enforces the limit on guesses. Signal's code is under the AGPL-3.0 license, so it serves as a design reference only. The trust that remains lies with the chip vendor and with anyone who has physical access to the server, cloud staff included. In 2025, WireTap extracted an Intel SGX attestation key, and Battering RAM broke the attestation of Intel SGX and AMD SEV-SNP. Both attacks worked on DDR4 memory. TEE.fail extracted Intel SGX and TDX provisioning keys and AMD SEV-SNP keys on DDR5 memory. Rolling the enclave's stored state back would reset the count of wrong PINs. So the count is replicated across several enclaves, and rolling one of them back does not reset it. AWS Nitro Enclaves attest with AWS's own certificate authority, not with a chip vendor's, so they do not qualify. The app encrypts the sealed secret under a key derived from the PIN. So whoever breaks an enclave and copies its stored data still has to guess each user's PIN offline. With Argon2 set to about 1 second for each guess, the 1,000,000 PINs of 6 digits take about 11 days of one processor for each user. That is feasible against a chosen victim, but costly against every user at once. The co-signer's keys cannot be encrypted that way, since the enclave has to use them, but each carries only 1/2.

**Example.** A Tellipod admin copies the PIN database and gets only ciphertext. Code without the limit of 10 wrong PINs fails attestation, so the app sends that code nothing. In another case, a thief has entered 9 wrong PINs, and a bribed admin restores one enclave's stored data from a week earlier, when the count was 0. The other enclaves still count 9, so the thief has 1 try left.

### DR-32. 10 wrong PINs erase the recovery key and the co-signer's keys

**Decision.** The enclave checks the PIN on 2 paths. On the recovery path, a correct PIN releases the sealed secret (DR-26), and the email check stands before every PIN try. On the co-signer path, a correct PIN makes the enclave sign the rotation that it is given (DR-30). Every request on either path names the enrolment identifier, which the identity's devices keep and the email check finds (DR-26). The enclave keeps one count of wrong PINs for each identity, for both paths together, and a wrong PIN in an erase request counts too. A correct PIN resets the count to 0. A wrong PIN adds 1 to it. The 10th wrong PIN in a row erases the sealed secret and the co-signer's keys of that identity, for ever. Nobody, Tellipod included, can undo that. Nothing in these rules depends on time: the enclave has no delays and no other limit.

**Why.** An attacker gets 10 guesses in a row out of the 1,000,000 PINs of 6 digits, which is about 0.001%. There is one count for both paths, whichever path he uses and from however many devices. A correct PIN resets the count, so an attacker gets 9 wrong PINs between 2 correct ones, and a user who mistypes now and then never comes near 10. Nothing depends on time, so manipulating the enclave's clock gains nothing, and the enclave needs no trusted time. Erasing makes the loss of an identity possible, but never a takeover: an erased key signs nothing for anyone. A user with a second device or a paper sheet rotates to new keys and enrols again (DR-28), and a user without either loses the identity, which is accepted (Risk 14). Erasing both keys at once leaves nothing to guess for, so no lock has to last for ever.

**Example.** Alice has a phone, a laptop and a desktop, with the Tellipod co-signer and the recovery service. A thief steals her phone. He knows its passcode, but not her PIN. He reads the email code in the phone's mail app and enters 10 wrong PINs on the recovery path. The enclave erases Alice's sealed secret and her co-signer's keys, and her mailbox shows each wrong PIN. The thief has taken nothing. Alice's laptop and desktop, each carrying 1/2, sign a rotation that revokes the phone and commits to a new service recovery key and a new co-signer's key, and she enrols them with her PIN. If Alice had a paper sheet instead of the desktop, she would type its 24 words on the laptop, and the laptop would sign the same rotation with the paper's key (DR-27). Suppose instead that the laptop were her only other device and that she had no paper sheet. The laptop alone would carry only 1/2 (DR-9), and she would have to move to a new identity (DR-16), which is an accepted risk (Risk 13).

### DR-33. What Tellipod learns

**Decision.** For a default user, Tellipod runs the co-signer, the recovery service and the witnesses. Tellipod holds less than the threshold only because the recovery service is non-custodial. The co-signer alone carries 1/2, and the recovery key that the recovery service stores is sealed in the enclave, which releases it only with the PIN (DR-26). The co-signer reads every rotation that it co-signs. Each such rotation shows the AID, the number of devices and the time. The co-signer also sees the requesting device's network address. For identities whose witnesses Tellipod runs (DR-15), the witnesses see every event of the identity. They also learn when and how often stamps are requested for the identity, and so roughly how active the identity's devices are (DR-20). They see when each device fetches, including right after it writes (DR-15), and so when its user writes. The witnesses learn nothing of pods, their members or their data, since a stamp request carries nothing about pods. Besides the identity's AID, it carries only a padded Merkle root. The witnesses also see the network address of every device that queries them. A device's own fetches tie its address to its identity, since only the identity's own devices request stamps. Its queries for other identities' KELs then show which identities it checks. From these, Tellipod can infer who shares pods with whom, though not which pod connects them or what the pods hold. Any other operator of witnesses learns the same about the identities that it serves. The recovery service ties an email address to a sealed secret, and the email provider learns that the user has a Tellipod recovery enrolment. A person may need a persona that neither pod members nor Tellipod can connect to the person's other identities. Such a persona uses other witnesses, another external co-signer or none, and another email address or the paper. A shared network address can still connect the persona to the person's other identities (DR-36).

**Why.** The co-signer signs each rotation itself, so it sees what the rotation holds, and the witnesses must see what they receipt. Pods stay out of the identity's KEL (DR-13), so nothing about pods reaches Tellipod.

**Example.** Tellipod sees that Alice linked a third device on Tuesday. Tellipod does not see that she is in the Tokyo pod. It does see that the device at the address 81.2.3.4 fetches Bob's KEL with a stamp root every day, and that it also asks for Alice's and Carol's KELs. So Tellipod can infer that Bob shares pods with Alice and Carol.

## Personas and privacy

### DR-34. Separate identities are opt-in, as personas

**Decision.** A person may want to keep contexts that pod members cannot connect to each other through any identifier. Such a person creates another identity, called a persona, on the same devices. There is no separate identifier for each pod.

**Why.** A separate identifier for each pod would repeat every device link, revocation and recovery in every pod. Personas put the cost only on the people who want them.

**Example.** Alice keeps 2 identities on her phone and her laptop: "Alice" for her family pods, and the persona "Alice-work" for her colleagues.

### DR-35. Several identities on one device

**Decision.** One device can host several identities. Each identity has its own record key, and so its own device id, and its own iroh endpoint key on that device.

**Why.** A person may keep separate identities (DR-34). If the identities shared a record key or an iroh endpoint key, that key would be a permanent identifier that connects them for anyone who is in pods with both identities. The cost is paid for each endpoint: a socket, connections, address discovery and probing for each identity on the device. Separate identities are opt-in (DR-34), so most devices host one identity and pay it once.

**Example.** Alice's phone hosts both "Alice" and "Alice-work", so it holds 2 record keys, 2 device ids and 2 iroh endpoint keys.

### DR-36. A persona hides identifiers, not the network or Tellipod

**Decision.** A persona has its own AID and KEL, its own record keys and device ids, its own iroh endpoint keys and its own recovery backend, if any, which for a paper user is its own sheet. No identifier therefore connects the persona to another persona. A persona does not hide the shared IP address, device changes that appear in several KELs on the same day, or habits of writing. Nor does it hide the connections that Tellipod can see. Tellipod sees them through the co-signer, through a shared recovery email address, and through the witnesses, which see the own fetches of both personas come from one network address (DR-33). These limits are accepted.

**Why.** The design cannot fully keep pod members from connecting personas in any case, since iroh exposes the same IP address. The design can still keep its own identifiers from connecting personas outright.

**Example.** Bob is in pods with both "Alice" and "Alice-work". He sees 2 unrelated AIDs and 2 unrelated sets of record keys and device ids, but the same IP address. Linking Alice's new tablet asks her twice, once for each persona.

### DR-37. The number of devices is visible

**Decision.** The role statements of each KEL, and the device ids that records name, show how many devices an identity has and how often those devices change. The design does not hide that information.

**Why.** Hiding the number of devices would take group signatures or ring signatures, which KERI's standard encoding does not offer. Pod members see which device signed each record in any case.

**Example.** Bob can tell that Alice writes from 3 devices and linked a new one last month.

## Membership basis

Pod membership will get a specification of its own. The decisions in this section are the basis of that specification.

### DR-38. Membership lists identities

**Decision.** Pod membership lists identities, by their AIDs, and never devices or device keys. A device that an identity links after the identity has joined a pod reaches the pod without any act of the other members.

**Why.** Operations on membership concern people, while data is synced between their devices.

**Example.** Alice links a tablet after joining the Tokyo pod. The tablet syncs the pod at once, and Bob does nothing.

### DR-39. Membership acts are records, without a TEL

**Decision.** A membership act is a record that one device signs and that is written into the pod's membership store. Examples are an addition, a join, a removal, a leave and a change of a member's role. A membership act is never anchored by a rotation, and it uses no ACDC registry (TEL). A membership act takes this design's own format, like every record (DR-17). Membership acts are signed and not anchored. A removed member's later acts are rejected by their position (DR-40). The non-repudiation of a membership act rests on 3 things: the signature of the device's record key, the check that the device is linked, and, after a revocation, a stamp from before the revocation (DR-20). Concurrent acts of several owners are ordered by the pod's own merge rule.

**Why.** Membership acts are frequent, so a rotation for each act is unacceptable. A KEL, and a TEL anchored in that KEL, have one writer. An identity, however, has several devices that write concurrently and offline, and a pod has several owners. A registry for each device would make memberships issued by a device that is no longer linked impossible to withdraw. One registry shared by all devices would fork whenever 2 of the devices write at once. A TEL could not order the acts of different owners anyway.

**Example.** Alice's phone, offline on a plane, removes Carol from the Tokyo pod. At the same time, Alice's laptop at home adds Dave. Both acts are records in the membership store, and nothing forks.

### DR-40. A removed member is kept out by position

**Decision.** A removal is a record that lists records of the removed member. For each device of the removed member and each branch of that device's chain, the removal lists the newest record that the remover holds. Of the removed member's records, only those in the history of a listed record are accepted (DR-17). Honest devices stop syncing with the removed member's devices once they hold the removal, apart from the one exchange described below. This has a cost. Suppose that the removed member honestly wrote a record that the remover had not yet received. That record is rejected everywhere. Whether such a removal can be corrected later is for the membership specification to decide. A member who leaves writes a leave. Like a removal, a leave is a record that lists the newest record of each of the member's devices and each branch that the leaving device holds. Membership runs in intervals. A removal or a leave ends the member's interval. A member who is out comes back only by accepting a new invite and writing her own join, which starts her next interval. Her join names neither the removal nor the leave. There is no other way back. An owner's other membership acts concerning a member who is out, such as a promotion, change nothing, and so does a removal of a member who is already out. A removal and a join written concurrently are left to the membership specification's merge rule for concurrent acts. In the new interval, her join is accepted. From each of her devices, the first record that names the join, and the device's records after it, are accepted. Records written while she was out are never accepted. A removal or a leave that is rejected ends no interval, since the member never left. A removed member's device receives its own removal once, from an honest device that gives it the pod's membership store up to and including the removal or the leave. Which acts that is, when owners act concurrently, the membership specification defines. The honest device gives it nothing else: no records, and no later membership acts. In that same exchange, the removed member's device hands over its stamps that cover the member's records up to the removal, and honest peers check them and publish them into the pod. The device then stops all sync with the pod, the membership store included, keeps its replica, and gets nothing more of the pod from honest devices (DR-19). Her join reaches her devices from her own devices. The device that writes it hands it to her other devices, and a device that she links after the join gets it from the device that links it, together with the pod's tickets. A device that holds her join treats her as present, and syncs with her devices as with any member's (DR-19).

**Why.** The goal is that a member removed by an owner can no longer write records in the pod. No anchor can prove that a record did not exist. Without a limit by position, a removed member could write a new record and claim that it came before the removal. Without intervals, a removal would keep a member out for good, even after she accepts a new invite. A record that names her join shows that it was written after she joined again. A leave that listed no records would let a member who left keep writing records, which devices that lack the leave would accept. Only her own join brings a member back, so no owner's act can do it without her. An owner offline on a plane, who still believes that a removed member is present and promotes her, therefore undoes no removal, and no owner brings back a member who left. A removed member's device that receives its own removal stops syncing the pod and can tell the user why, and the check of DR-19 runs on the honest removal. Syncing the membership store beyond the removal would show a former member every later join and removal, so the store stops at the removal. After that, the device needs nothing more from the pod, since its way back is a new invite. It hands its stamps over in the one exchange that it still has, since otherwise its records up to the removal would lose acceptance once the device is revoked (DR-20).

**Example.** Alice's laptop holds the records of Bob's phone up to #40, and the laptop removes Bob from the pod. The removal lists #40 for Bob's phone. Bob's phone receives the removal from Carol's phone, hands Carol's phone its last stamp, which covers #40, and stops syncing the pod. Carol's phone publishes the stamp. Bob's phone then writes #41 and claims that #41 came before the removal, but #41 is rejected. No record of Bob's tablet is accepted, since the laptop held none of them. Dave, an owner offline on a plane, still believes that Bob is a member and promotes him. Bob is out, so the promotion changes nothing. Meanwhile Bob's phone writes #42. In June, Alice invites Bob again. Bob accepts on his phone, and the phone writes his join J90, which is accepted. The phone's next record names J90, so that record and every later record of the phone are accepted. #41 and #42 were written while Bob was out, so they are never accepted. Bob's phone hands J90 to his tablet, and the tablet's records are accepted from its first record that names J90 onwards. A laptop that Bob links in July gets J90 from the device that links it, together with the pod's tickets. In a second case, after the removal, Bob's phone shows a second, different record at position 39. That record lies outside the history of #40, so it is rejected. The 2 records at position 39 prove a fork, and the fork marks Bob's phone as compromised (DR-22). In a third case, Bob leaves on Monday, and his leave lists #50 for his phone. Bob's phone writes #51 on Tuesday. Carol receives #51 before the leave, and she rejects it once the leave arrives.

### DR-41. A recovered identity gets its pods back from their members

**Decision.**

- When a member's device sees a recovery rotation that adds a device in the KEL of another member of a pod, it offers that pod to the added device. It dials the device through the iroh endpoint key that the device's endpoint binding names (DR-7). It makes the offer only while its copy of that KEL is fresh (DR-15) and lists the device.
- The recovered device keeps an offered pod only if 2 conditions hold. The pod's membership store holds a membership act for that pod that a device of the recovered device's own identity signed, accepted under DR-18 and DR-20. And that membership store shows the recovered device's identity as a current member. The recovered device drops any other offer without showing it to the user. It takes the pod from the first valid offer. It keeps as a peer of that pod every member's device that makes a later valid offer of the same pod. So no single member can keep the recovered device to himself and serve it an old copy.
- The membership specification therefore records each join in a membership act that a device of the joining identity signs, and binds the pod id to the pod's created event.
- A user of the Tellipod backup service, which is optional and stores end-to-end encrypted replicas of pods, also gets pods back from that service. This ADR does not cover the backup service's design.
- A pod that has no other member, no replica at the backup service and no copy in a backup of the device is lost with the identity's last device.
- How a member's device learns of the recovery and reaches the recovered device is an open question, described at the end of this document.

**Why.**

- Every pod still lists the identity as a member, and every other member's device holds the pod. The members therefore already hold everything that a saved list of pods would give, and they hand it over only to a device that the identity's KEL lists. A list kept with Tellipod would have 3 drawbacks. It would have to be encrypted again at every replacement of the recovery key. It would need a place to stay for paper users. And it would show Tellipod when the identity joins or leaves pods.
- The identity's private metadata store, and with it the user's contacts, is lost with the last device, so the recovered device knows no other AID. The identity of a caller alone therefore proves nothing, since a stranger can name an identity "Bob". A membership act that a device of the identity signed is the one thing in the pod's membership store that a stranger cannot forge. A member who offers an out-of-date copy of a real pod still offers that real pod, whose signed records cannot be changed, and the device gets the rest from the other members.
- Members' devices learn of the recovery at their next fetch of the identity's KEL (DR-15). How they come to fetch it while none of the identity's devices is online is an open question, described at the end of this document. So how soon a pod comes back after the recovery depends on that question. A pod also comes back only once one of its members is online. The app tells the user so.

**Example.** Alice belongs to "Family" with Bob and Carol, to "Hiking" with Dave, and to a pod for her own notes, in which she is the only member. She loses her phone and her laptop, and she recovers with her paper at 10:00. At 18:00, Bob's phone fetches Alice's KEL, sees the recovery rotation, dials her new phone and offers "Family". The membership store of "Family" holds Alice's join, which her old phone signed while it was linked and which a stamp from before the recovery covers, so the new phone keeps "Family". Dave's phone offers "Hiking" the next morning. Mallory creates another pod named "Family" that lists Alice's AID, and offers it. That pod holds no membership act that Alice signed, so the new phone drops it. Alice's notes pod has no other member. It comes back from the Tellipod backup service if Alice uses that service, and otherwise it is gone.

## Departures from KERI

This section lists where this design departs from KERI 2.0, as the Trust over IP KERI, CESR and ACDC specifications and keripy define it, and why. No departure changes the encoding of a KEL. A role statement is anchored by a standard digest seal, and the departing witnesses' receipts of a change of the witnesses are standard receipts without an index. Every KEL that this design produces is meant to validate in keripy with the same key state. The test vectors of DR-3 check this, and DR-11 and DR-16 name points that are still to be verified. 3 caveats matter. First, devices sign the identity's establishment events with indexed P-256 signatures. keripy defines the codes of these signatures and the CESR specification does not, so an implementation that follows only the specification cannot verify these KELs. Second, this design's validators reject some events that keripy accepts, and they are meant never to accept an event that keripy rejects. The events that only this design rejects are of 4 kinds: events that break the rules listed below under "Rules on top of conformant events", a change of the witnesses without receipts from a majority of the old witnesses, the later events of an identity that is frozen after duplicity, and every KERI 1.0 event. Third, a stock KERI tool verifies an identity's keys and nothing else that a device relies on. Only this design's validators read role statements, and endpoint bindings, key state statements, stamps and records are this design's own messages.

**Rules that differ from what KERI specifies**

- **Indexed P-256 signatures** — The CESR specification defines P-256 keys and plain P-256 signatures. But its table of indexed signatures, which "a compliant KERI/ACDC genus MUST have", lists only Ed25519, secp256k1 and Ed448. The devices' keys in the identity's key set are P-256 keys. Their signatures on the identity's establishment events use keripy's indexed codes `E` and `2E`. The second code is used when a signature's 2 indices differ, as they usually do in a rotation (DR-9). So only implementations that follow keripy can verify these signatures. Record keys sign only this design's own messages, never a KERI event. Binding keys to hardware outweighs conformance with the table, and the gap is tracked or pushed upstream (DR-2).
- **Receipts when the witnesses change** — KERI requires the receipts of a rotation to "satisfy the current witness threshold", counted against the witness list that the rotation itself sets up. keripy builds that list from the rotation's removals and additions. This design requires receipts from a majority of the new witnesses and from a majority of the old witnesses, which are those that the previous establishment event lists, without exception. The receipts of departing witnesses cannot be indexed into the new list, so they travel as receipts without an index. keripy keeps such receipts apart and does not count them. So keripy accepts such a rotation on the new witnesses' receipts alone, and this design is stricter. Only the old witnesses can show that they hold nothing at the position. Without their majority, a change of the witnesses could create a second accepted event where they have already receipted one (DR-9, DR-16).
- **Duplicity of the identity's KEL** — KERI says that an honest validator "MUST NOT trust when there is any evidence of duplicity unless and until the duplicity has been reconciled". It leaves to the validator "whether or not to treat its original copy as the authoritative one". When a device holds 2 events at one position, each receipted by a majority of the same witnesses, it freezes the identity. It keeps the event that it saw first and every verdict on records that it has already reached. It accepts no further records or events from the identity in any pod. And it passes the evidence on, so that every member freezes the identity too. Stopping is what KERI requires. Keeping past verdicts relies on KERI's permission to treat the first copy as authoritative, and it keeps a dishonest user from disowning years of records by forking at an old position (DR-16).

**Rules on top of conformant events**

- **Roles, weights and threshold** — KERI defines no roles, and it accepts whatever fractional weights and thresholds the signers of an establishment event set. Every validator of this design reads the role of each key from the role statement of the previous establishment event, whose indices count that event's next-key digests. It rejects an establishment event in 3 cases: when the event changes a key's role, when it commits to a next key with another weight than the key's role has, or when its thresholds are anything other than 1. The weight of a role is 1/2 for a device, or 1 for a sole device without an external co-signer, 1/2 for the external co-signer, and 1 for a recovery key. A stock validator accepts all of these events. So these rules are what keep a thief from relabelling a key as a recovery key or lowering the paper's weight (DR-9, DR-10, DR-14).
- **Devices as entries of the role statement** — KERI lets several parties hold the keys of one AID. keripy gives each such party an AID of its own whose KEL supplies its key, as a participant in a group identifier. KERI's other way to give a device keys of its own is a delegated AID. In this design, a device has no AID and no KEL. It is an entry of the identity's role statement that pairs one slot of the identity's key set with one record key. The entry's device id is a digest over a domain tag, the identity's AID and the record key. Every validator rejects a role statement that lists more than 32 device entries, lists one record key in 2 entries, or lists a record key that an earlier rotation dropped. A device is linked from the first accepted establishment event whose role statement lists its entry, and revoked from the first later one that does not. Stock tools verify the identity's KEL, but neither a record nor whether a device is linked. One KEL, which the witnesses order, holds every device's keys, so a record is verified against that KEL alone (DR-6, DR-14, DR-18, DR-20).
- **At least 3 witnesses, and a majority as the threshold** — KERI lets an AID have no witnesses. It lets the AID's controller set the witness threshold to any number from 1 to the number of witnesses. Its section on immunity describes a higher threshold, such as 4 of 5, that keeps one witness that receipts 2 events from producing 2 accepted events. Every validator of this design rejects an establishment event that lists fewer than 3 witnesses, or whose witness threshold is anything other than a majority of the witnesses that it lists, such as 2 of 3 or 3 of 5. So the threshold that keripy applies is always the majority that this design requires. A majority keeps an identity working while 1 of 3 witnesses is down. But one witness that receipts 2 events, together with signers that meet the threshold for both, gives 2 accepted events at one position. That case falls to the pod members, who detect the duplicity. Detecting the duplicity is the protection that KERI itself names when witnesses collude (DR-9, DR-15, DR-16).
- **Current weights copied from the previous next keys** — KERI requires that "the set of signatures on a Rotation event MUST satisfy two thresholds": the rotation's own current threshold and the next threshold of the previous establishment event. It lets the controller set the 2 independently. In this design, the current keys of a rotation are exactly its signers, each with the weight that the previous establishment event committed for it. So both checks add up the same weights, and a sole device can link a second device. This is within KERI's freedom, since a stock validator applies the check against the previous next keys in the same way (DR-11).
- **Freshness and witness time** — KERI leaves freshness to the validator. keripy reads its own clock where it uses time, for example to time out the events that it holds in an escrow. In this design, no rule that decides what counts reads a clock of the device. Every period runs on witness time, from the 24 hours of freshness to the 7-day window of DR-20. Witness time is the newest date that a majority of the device's own witnesses have each signed. It is stored durably and never moves backward. A copy of a KEL is fresh only when the device holds key state statements from a majority of the identity's witnesses, each dated no earlier than 24 hours before the device's witness time. No peer's word makes a copy fresh. A device's user, a thief or the device's network can set the device's clock. But no single witness or peer can move witness time, and the freshness bound limits how long a peer can withhold a revocation (DR-15).
- **Limits on KELs and escrows** — KERI sets no limit on the keys or events of a KEL, and it says that an event whose signatures do not yet meet its thresholds "SHOULD escrow". This design treats an identity whose KEL exceeds its limits on device entries or on size as invalid. Its escrow takes only events that carry a receipt from a witness that the latest validated event lists, and only within a share for each identity and each sender. Without these limits, a member with witnesses of its own could make every device store and check millions of valid events (DR-4, DR-13).
- **Refusals by second parties** — KERI validates the signatures on a rotation, not the reasons for them. An honest device that acts as second party of this design derives every change of a rotation from the difference with the previous establishment event. It names each change in its prompt. Its user chooses the changes by typing the code under that prompt, and the device refuses a change that its user did not choose. The device signs a rotation only when 4 conditions hold. Its user has typed the code that the asking device shows. The rotation commits again to every recovery key, unless the device's own user chose to replace, add or drop one. An own fetch made for that rotation succeeded, and the device's copy of the KEL reaches the position that the answers give. And the device has checked the endpoint binding of every new record key. The Tellipod co-signer checks only the PIN. These rules bind signers, not validators. A stock validator and this design's validators alike accept a rotation that 2 stolen devices sign to drop the recovery key (DR-6, DR-16, DR-28, DR-29, DR-30).

**KERI mechanisms not used or replaced**

- **KERI 1.0** — keripy produces and accepts both KERI 1.0 and KERI 2.0 events. This design's implementation follows KERI 2.0 and CESR 2.0 only, and it never produces or accepts a KERI 1.0 event. So a KEL that keripy writes in KERI 1.0 does not validate here. One version keeps the implementation and its test vectors to the subset in use (DR-3).
- **Superseding recovery** — KERI lets a rotation supersede the interaction events after the last establishment event, and "A non-delegated rotation may not supersede another rotation". The identity's KEL has no interaction events and no delegation, so nothing in it can be superseded, and a stock validator reaches the same verdict (DR-3, DR-8).
- **Interaction events** — KERI lets a KEL anchor data in interaction events signed with its current keys. The identity's inception sets KERI's establishment-only trait, `"c":["EO"]`, under which "A Validator MUST invalidate, i.e., drop any non-establishment events". So a stock validator enforces the same rule. Anything anchored in the identity's KEL costs a rotation by 2 parties, so no record is anchored anywhere (DR-8).
- **Anchoring, TELs and ACDC registries** — KERI orders signed data against key state by anchoring the data's digest in the signer's KEL. ACDC requires an issuer to "anchor an issuance proof digest seal to the ACDC in its KEL either directly or indirectly". The indirect way is a TEL, through which the issuer also withdraws a credential. This design anchors no record, no membership act and no deletion. Stamps order a device's records against its revocation, and membership acts and deletions are records in this design's own format. A KEL has one writer, while an identity's devices write concurrently and offline, and anchoring each act would make KELs grow with activity (DR-13, DR-17, DR-20, DR-39).
- **Watchers as a separate network** — KERI gives each validator watchers, jurors and judges of its own choosing. In this design, every member's device is the watcher for the KELs of the members of its pods. It takes those KELs from its pod peers, checks the receipts itself, compares copies and passes evidence on. The parties that rely on an identity's KEL are exactly its pod members, who sync with each other anyway. A separate network would only add a party that learns who checks whom (DR-15).
- **Choosing the key that signs** — keripy's key manager stores which of its keys is current, and it signs with that key. A device of this design finds its committed key among its keys of that identity in its hardware, by the digest that the latest KEL holds. It finds its record key as the key that the latest role statement lists. So what the app's data says about either key is only a hint. The Tellipod co-signer signs with whichever of its keys the device names, by a digest that the device reads from the KEL. This matters because a restore of the app's data brings back an older note of the current key, while the hardware keeps every key. It also means that the enclave needs no knowledge of the KEL (DR-16, DR-30).

**Messages and data outside KERI**

- **Role statements** — KERI anchors data by a digest seal and gives the data no meaning. A role statement is self-addressing data that every establishment event of the identity's KEL anchors by a digest seal, and it travels with the KEL. A stock tool carries the seal as event data. It checks neither the role statement against the seal nor the statement's meaning, which only this design's validators read (DR-14).
- **Endpoint bindings** — KERI ties an endpoint to an AID with 2 dated reply messages: `/end/role`, which the AID's controller signs, and `/loc/scheme`, which the endpoint's own AID signs. A reply with a later date replaces one with an earlier date. An endpoint binding is a statement outside every KEL. It is signed by a device's record key and by its iroh endpoint key, it is identified by the digest of its body, and it carries no time. A device signs one binding for life. The binding travels with the identity's KEL among pod peers and never goes to the witnesses. It is valid exactly while the role statement lists its device id, so it needs no date, and a second binding for one device id marks the device as compromised (DR-7).
- **Key state statements** — The KERI specification defines a generic reply message but no key state notice. keripy's key state notice is a reply on the route `/ksn/<AID>` that carries the AID's whole key state and a date. This design's witness signs its own statement. The statement covers a domain tag, the identity's AID, the latest position that the witness has receipted, the digest of the event at that position, and the statement's date. For an own fetch, it also covers the device's Merkle root. The witness orders every statement against its receipts. The domain tag keeps a statement from verifying as a receipt, the position lets a stamp be ordered against the receipts, and any peer may pass a statement on (DR-1, DR-3, DR-15).
- **Own fetches** — KERI's query asks for key state or for a KEL, and it carries nothing that the answer has to return. Every fetch of a device's own identity's KEL carries the AID and a Merkle root. The root is computed over the device's records that no stamp covers yet, or over random leaves. Such a fetch succeeds only when a majority of the witnesses answer with statements that carry that root. Every fetch, of any identity's KEL, takes the newest accepted event among the answers of a majority. A root that the device computes for a fetch comes back only in statements signed after the fetch was sent. So whoever controls the device's network cannot answer with statements that it collected earlier, and so cannot hold witness time back unseen. And the witnesses cannot tell a fetch from a stamp request (DR-15, DR-20).
- **Stamps** — KERI has no message by which witnesses order data against a position of a KEL, and a stock KERI witness puts no root into what it signs. A stamp is a set of key state statements from a majority of the identity's witnesses that agree on the position, the event digest and the root, and each statement keeps its own date. The root covers some records of the identity's devices, through a Merkle tree with salted leaves that is padded to 256 leaves. Whatever a stamp covers existed before any event after its position was accepted. So stamps take the place of anchoring for records, and the witnesses learn no pod (DR-20).
- **Witness duties beyond KERI's** — A KERI witness receipts the first verified event that it sees at a position of an AID that lists it. This design's witness has further duties. It receipts only an event that passes this design's validator rules, so that an event that devices reject never takes a position. It also receipts a rotation that removes it, when it holds nothing at that position, and it keeps serving the KEL up to that change. It never restores its state backward. It dates its statements from a clock that it keeps accurate against several independent time sources, which are independent of the other witnesses' sources. It signs nothing while those sources disagree, and it never dates a statement for an identity earlier than its previous statement for that identity. It keeps no claim of having seen an event first at a position where the identity's accepted KEL does not list it. Without the first duty, a change that removes a majority of the old witnesses could never collect their receipts. Without the duty never to restore backward, a witness restored from an old backup would stamp a thief's records at an old position. Without the dating duties, devices, which read time only from their witnesses, would measure every period wrong (DR-3, DR-15, DR-16).
- **Fork notices** — KERI has no such message, and its nearest counterpart is the log of duplicitous events that a juror may keep. A device that has marked another device as compromised answers every sync session that the compromised device opens with a fork notice. The notice carries the 2 records at the fork position, or the 2 bindings. So a sole device learns why its peers went silent (DR-22).
- **Requests to the co-signer, the recovery service and the enclave** — keripy coordinates the signers of a rotation with KERI exchange messages. This design uses its own requests instead, which is within KERI's freedom. Each request carries a domain tag and a nonce that the receiving party issued for it, and it names what it applies to. A request to the enclave names the enrolment identifier, and a request to co-sign also carries the rotation, with its AID and its KEL position. A request to recover, to co-sign, to confirm a new enrolment, to refresh the sealed secret or to erase carries the PIN, and no request carries a KEL (DR-1, DR-26, DR-32).
- **Records** — KERI signs data of a transferable AID with the keys of an establishment event, which the signature names by AID, position and digest. A record's signed body is this design's own. It starts with a domain tag, and it names the pod, the identity's AID, the device id, the record's sequence number and the digest of the device's previous record. The device's record key signs it, and the body refers to no key state. Deleting a record is itself a record, a deletion, after which replicas keep the deleted record's signed body and signature as a tombstone. The record key is not in the key set, so a stock KERI tool verifies no record. A device id's record key never changes, so a record is checked against the identity's KEL alone (DR-17, DR-18, DR-39).

## Accepted risks

### DR-42. Accepted risks

**Decision.** This design accepts the risks numbered below rather than designing them out. Each is described with an example where one helps and, where one is proposed, a possible mitigation. A risk's number is never reused, like a DR number.

**Why.** Stealing a device together with the user's PIN is unlikely, although phishing and malware can obtain the PIN (Risk 1, Risk 2, Risk 10). A compromise of the app is a compromise of the device on every platform (Risk 2). Trusting a majority of the witnesses is the price of an order without a trusted clock (Risk 17). Witnesses with separate keys, machines and backups do not lose that majority by accident. A device's clock cannot be trusted, so the design reads time only from the witnesses. The witnesses are expected to be close to always available, and an outage of several days stays visible on every affected device (Risk 21). An operator that shuts down its witnesses with notice costs its users nothing but a rotation (DR-16), and one that vanishes without notice is rare (Risk 19). The risks that involve witnesses fall mainly on the user, because the thief's records become the user's. The effects of those records in a pod, such as the removal of a member, last until the user repairs them with ordinary records. This does not hold for deletions, which are a risk of their own (Risk 23). A thief's deletion that a stamp from before the revocation covers removes the content at every replica for good. The user can only write that content again, if she still has it. Erasing after 10 wrong PINs limits guessing without any notion of time, and its price is a possible loss of the identity, never a takeover (DR-32, Risk 14). A reset of a forgotten PIN would need a wait, and so time inside the enclave (DR-28). Reminders of the PIN keep forgetting it rare instead (Risk 16). User presence for every rotation means that an unattended, unlocked device is not enough, and presence once per signing session keeps records easy to sign (Risk 9).

**Example.** A thief watches Alice type her PIN on the train, and then steals her phone. At 9:00, the stolen phone and the co-signer, given the PIN that the thief saw, sign a rotation that links the thief's laptop and replaces Alice's paper with a sheet of the thief's own. At 9:02, the stolen phone and the thief's laptop drop the co-signer (Risk 1). In another case, a burglar takes Alice's phone and laptop from her bag, and knows how to unlock both. The burglar needs no Tellipod PIN. The 2 devices together rotate Alice's paper out (Risk 4).

### Risk 1. A thief with a device and the PIN takes the identity

A thief who holds a device and the user's PIN takes the identity for good. The Tellipod co-signer signs any rotation for whoever knows the PIN (DR-30). So the stolen device and the co-signer sign a rotation that links a device of the thief's own and replaces or drops the recovery key. The stolen device and the thief's device then drop the co-signer, without any wait. All of this takes minutes and needs only stock software. With the recovery service, the thief passes the email check in the stolen phone's own mail app, and releases the recovery key with the PIN.

### Risk 2. Malware inside the app takes the identity

Malware inside the app's process signs records while the record key's window is open. It captures the PIN when the user types it into the app, and it gets a rotation signature at the next prompt for presence. So with the Tellipod co-signer, it takes the identity without the device leaving the user's hands. It can also fork the device's chain at an old position, so that a newcomer's replica holds 2 rival branches and never the genuine one (DR-22, DR-23, DR-30).

### Risk 3. A thief with a sole device and its unlock secret owns the identity

A thief who holds a sole device and its unlock secret owns the identity.

### Risk 4. A thief with 2 devices and their unlock secrets holds 2 parties

A thief who takes 2 devices at once, with their unlock secrets, holds 2 of the parties that a rotation needs.

### Risk 5. A thief with a self-hosted co-signer's machine and a device holds 2 parties

A self-hosted co-signer keeps its key of weight 1/2 in a file on the user's machine. So whoever takes that machine and one device of the identity with its passcode holds 2 parties (DR-30).

For example, a burglar takes Bob's home server, which runs his co-signer, and his phone, whose passcode he saw. The burglar then links a laptop of his own and drops Bob's paper.

### Risk 6. A user can be talked into typing a second party's code

Someone may persuade a user to type a code that he reads out to her, for example a thief who holds her phone and calls her as "Tellipod support". The user then approves the act that the code belongs to (DR-29). The prompt names the act and the asking device, and it warns that Tellipod never asks for the code.

### Risk 7. Malware can copy a recovery key while a device creates or derives it

A device creates the recovery key in software, at enrolment and after each recovery (DR-26), and the paper's key is derived on a device from the 24 words (DR-27). Malware on that device at that moment copies the key. The copied key carries weight 1 and stays valid until the identity replaces it. A user who learns that a device was infected replaces the recovery key from clean devices (DR-28), after which the copied key is worthless.

### Risk 8. A copied endpoint key reads every pod unseen

A device's iroh endpoint key is a software key that sits unwrapped in memory while the app runs, and peers authorise a sync session by that key and the device's endpoint binding (DR-7). Whoever copies it once, by malware that runs on the device, a forensic tool on a seized phone or an attack on the memory of a running desktop, reads every pod of the identity as that device, from anywhere and with no signal, including pods that the identity joins later, until the device is revoked. The copy signs no record and makes no second binding, so nothing forks and no rule marks the device.

For example, at a border on 3 March an agency images Alice's phone, reads the endpoint key from memory and hands the phone back, and its node then syncs every pod of Alice's as her phone, while Alice, who still holds the phone, has no reason to revoke it.

A possible solution: each device holds one more hardware key, a session key that needs no presence and that its endpoint binding lists, signs the start of every sync session with it, and peers authorise a session only with that signature, so a copied endpoint key opens nothing. The cost is one hardware signature for each session, about 10 to 50 ms, one more key and one more field in the binding.

### Risk 9. A thief signs records during a signing session

A thief who takes a phone with a signing session open, or who knows its passcode and opens signing sessions, signs records until the signing session ends or the device is revoked. Those records become the identity's when a stamp from before the revocation covers them.

### Risk 10. A phisher with the email code and the PIN takes the identity

Whoever gets the user to type her email code and her PIN into a page or an app of his own, as a phisher posing as Tellipod does, takes the identity without any device of hers. He starts a recovery on his own phone, the service emails her the code, and once he has both, the enclave releases the sealed secret to him. His recovery rotation drops her devices and her other recovery key at once, and her co-members then offer his phone every pod (DR-26, DR-32, DR-41).

For example, Mallory sends Alice a page styled as a Tellipod security check that asks for "the code we just emailed you" and her PIN.

A possible mitigation: the email carries a link that opens the Tellipod app and works only for the app session that started the recovery, instead of a code to type, and every prompt for the PIN, and the email itself, warn that Tellipod never asks for them outside the app. A user who forwards the email and types her PIN for someone else would remain exposed.

### Risk 11. A thief gets 10 tries at the PIN for each identity

Whoever passes the email check or holds a device of the identity gets 10 tries at the PIN, across both paths of DR-32, since only the 10th wrong PIN in a row erases the keys. A correct PIN resets the count, so an attacker gets 9 wrong PINs between 2 correct ones. Each further identity on a stolen phone that uses the same PIN has a count of its own, and so adds 10 tries of its own: 3 such identities give 30. People choose PINs unevenly, and the 10 most common PINs of 6 digits cover far more users than 10 in 1,000,000. So a thief with the phone finds the PIN of a small share of users.

### Risk 12. PIN reminders can weaken the PIN

The PIN reminders that mitigate a forgotten PIN (DR-28, Risk 16) can weaken the PIN, depending on how a reminder checks it, which this design does not yet settle. A check on the device keeps something that verifies the PIN in the app's data, so a thief with the phone and its passcode can copy it, for example from a local backup, and try all 1,000,000 PINs offline: at about 1 second for each guess, that is about 11 days of one processor, or hours on rented machines, after which he holds a device and the PIN. A check in the enclave counts every wrong entry toward the 10 that erase the keys, and every correct one resets a thief's count (DR-32).

Possible mitigations: a local check whose verifier is stored encrypted under the hardware wrapping key and out of backups, like the endpoint key's secret (DR-7), and that stops after 3 wrong entries in a row and asks the user to confirm her PIN through a co-signing instead; reminders that only ask whether the user still remembers her PIN and check nothing, so that nothing exists to attack, at the cost of not telling a user who misremembers; or reminders checked by the enclave, accepting that they use up tries and reset a thief's count.

### Risk 13. An identity with only 2 parties cannot rotate after losing one

An identity can hold only 2 parties, such as 2 devices and nothing else, or one device and the Tellipod co-signer without a recovery key. If it loses one of them, the other carries 1/2 and can never rotate again, so it can neither revoke the lost device nor link a new one (DR-9, DR-25). A thief who holds a device and its passcode, but not the PIN, can bring a larger identity down to that state by entering 10 wrong PINs, which erase the service's recovery key and the co-signer's keys (DR-32).

For example, Alice has a phone, a laptop, the Tellipod co-signer and the recovery service, but no paper sheet. The thief burns the 10 tries on her stolen phone, her laptop alone carries 1/2, and the phone can never be revoked: it keeps syncing every pod and signing records that become hers, until she moves to a new identity (DR-16). Dave, with only a phone and a laptop, is in the same position as soon as his phone is stolen with its passcode.

A possible mitigation: the app treats an identity as exposed when it holds fewer than 3 parties, or has no paper sheet and fewer than 3 devices, and asks for a paper sheet, a third device, or the co-signer together with the recovery service. The user may decline, since keeping a way back is her choice (DR-25), but she is told plainly what she risks.

### Risk 14. Wrong PINs entered on purpose erase the recovery key and the co-signer's keys

Someone who passes the email check, through a stolen phone's mail app or a taken-over mailbox, can deliberately enter 10 wrong PINs and so erase the service's recovery key and the co-signer's keys (DR-32). A thief who holds a device of the identity can do the same on the co-signer path. Revoking that device ends this, since every revocation enrols the identity again (DR-26), but until the revocation the thief can do it. The identity is never taken over this way. But a user who has one device and no paper sheet, and whose device is stolen, loses the identity. The email check is considered sufficient protection.

### Risk 15. Requests for new co-signer's keys push out the committed key

Whoever holds an identity's enrolment identifier, such as a thief with a device of the identity but without the PIN, can ask the enclave for new co-signer's keys as often as he likes, since that request carries no PIN. The third new key pushes out the key that the identity's KEL commits to. The Tellipod co-signer then signs no further rotation of the identity, and no email tells the user (DR-30).

For example, rotation 4 of Alice's KEL commits to the co-signer's key C5, and the thief who holds her phone asks for C6, C7 and C8. When Alice's laptop then asks the co-signer to revoke the phone, the enclave no longer holds C5. Unless Alice has another device, a paper sheet or the recovery service, she cannot revoke the phone. 3 attempts at a linking that each ask for a new key and then fail push out C5 in the same way.

The recommended mitigation has 3 parts: each request for a new key names the digest of the key that it follows, the enclave returns the same new key for the same digest, and the enclave drops a key only once it has signed with a key that it created later.

### Risk 16. A user with one device and the co-signer who forgets her PIN cannot change her devices

A user with one device, an external co-signer and no paper sheet who forgets her PIN can no longer change her devices (DR-28). Her device keeps writing records. But when she needs a new device, she loses the identity, unless she has moved to a new identity first (DR-16).

This risk needs mitigation in the app: reminders of the PIN from time to time, as Signal shows them, and encouragement to link a second device or to keep a paper sheet.

### Risk 17. A majority of the witnesses can stamp a thief's records and block rotations

Whoever controls a majority of an identity's witnesses can sign key state statements that form stamps at an out-of-date position. Such stamps cover a thief's records written after the revocation, and those records then become the identity's. That party can also refuse to receipt the identity's rotations, so that no device can be linked or revoked.

Suppose that a majority of the witnesses of any identity that a device hosts date their statements later than the true time. They push the device's witness time forward for good, since witness time never moves backward. That makes the device's checks stricter: copies of other identities' KELs go out of date early, and the 7-day window closes early. A majority of a device's own witnesses that date their statements earlier than the true time hold its witness time back. That keeps old copies fresh and the 7-day window open, until a statement of another identity dated more than 24 hours ahead makes the device warn that its witnesses lag (DR-15). A fault in a time source that a majority of an operator's witnesses share has the same effect, at once for all of that operator's users. The effect lasts on every device that fetched while the fault lasted.

Freezing the identity takes less than a majority. A single witness that receipts 2 events at one position, together with signers that meet the threshold for both, makes the members freeze the identity (DR-16), so the user loses it. Such signers are, for example, a thief who holds a device and the user's PIN.

For a default user, the party that controls a majority of the witnesses is Tellipod as a whole. The user escapes by moving to a new identity (DR-16). A user who adds witnesses of her own that outnumber the operator's is not exposed to that operator at positions after the change. She remains exposed at positions before it, as Risk 18 states (DR-15).

### Risk 18. Witnesses that an identity no longer lists can stamp at positions before the change

Witnesses that an identity no longer lists can still sign key state statements, and so form stamps, at positions before the change of witnesses. A stamp needs the witnesses that the KEL lists at the stamp's own position, and its dates play no part. So an operator that the user left, or whoever later obtains its witnesses' keys, can stamp a thief's records written after a later revocation. It can also keep a member whose copy of the KEL predates the change on that copy (DR-16, DR-20).

For example, Alice changes from Tellipod's witnesses to her company's at position 10, and her laptop and desktop revoke her stolen phone at position 12. A compelled Tellipod signs statements at position 9 with the root of the thief's record #441, which then counts as Alice's in the Tokyo pod. Changing witnesses, or adding witnesses of her own that outnumber the operator's, does not take this power away for positions before the change. Moving to a new identity does.

### Risk 19. An operator of witnesses that vanishes forces its users to new identities

An operator of witnesses that disappears without notice, or that refuses an identity, leaves its users without a way to keep their AID. Every affected user has to move to a new identity before the 7-day window of DR-20 closes at the members' devices. That window runs on each member's witness time. So it stands still at the devices of members whose hosted identities all use the same operator, until those members move too (DR-16). Pods whose owners do not act in time continue only as new pods, and a user who lost every device in that time loses the identity.

This risk needs mitigation in the app, for example by automating the creation of the new identity and the membership acts that hand each pod over to it.

### Risk 20. The app cannot tell how long its witnesses have been silent

Suppose that the witnesses of a user's identity vanish without notice. Then the witness time stands still on each of her devices that hosts no identity on other witnesses. So her app cannot tell from witness time alone how long the outage has lasted, and she may miss the 7-day window in which to move to a new identity (DR-16).

For example, Tellipod's witnesses vanish on Monday. Alice's phone shows the same warning on day 6 as during a 2-hour outage. Meanwhile Dave, whose witnesses are another operator's, stops accepting her phone's records on day 8.

The recommended mitigation is for the app to measure how long the user's own witnesses have been silent. It can measure this by the dates of other identities' key state statements that it receives, or by a notice that the operator signs. It uses that measure only to prompt the user and to automate the move.

### Risk 21. An outage or a blocked network stretches every period

An outage of a device's own witnesses stops the device's witness time (DR-15). For its whole length, the outage stretches 2 periods: the freshness bound within which the device learns of a revocation, and the 7-day window within which it stops accepting records that no stamp covers (DR-20). A dishonest member of a group that is offline together for long, such as on a boat, can disown all her records of the offline period, since no stamp covers them. The device shows "can't reach your witnesses" throughout, and such an outage is treated as force majeure.

Whoever controls a device's network, such as a thief's hotspot or a state, can block the device's own witnesses or another identity's witnesses for as long as he likes. Suppose that another identity's witnesses are blocked, and that a device of that identity is revoked meanwhile. The revoked device keeps receiving the pod's new records from the device whose network blocks those witnesses. That device shows only that this identity's KEL has not been confirmed recently. For example, the thief's hotspot blocks Alice's witnesses for Bob's phone. Bob's phone then keeps syncing the Tokyo pod with Alice's revoked phone for as long as the thief likes. A user whose own witnesses are blocked has her records refused after 7 days by the members who reach theirs, since her devices get no stamps (DR-15, DR-20).

A proposed mitigation for the revoked device: after a fetch of another identity's KEL fails, a session with that identity's devices resumes for receiving only, so the device accepts their records under the usual rules but sends them nothing until a fetch succeeds. In the example, Bob's phone would then stop sending new Tokyo records to Alice's phone. The cost falls on an honest Alice whose witnesses Bob's phone cannot reach: her devices miss Bob's new records until a fetch succeeds, or until they get them from other members.

### Risk 22. Witnesses that date ahead cause false warnings

The witnesses of an identity that date their statements far ahead make every device in that identity's pods warn its user, falsely, that its own witnesses lag behind, since a statement dated more than 24 hours after a device's witness time makes the device fetch, and a fetch that leaves its witness time behind that date makes it warn (DR-15).

For example, Mallory has her own witnesses date her statements a year ahead, and every device in her pods shows the warning, so users may learn to ignore it.

### Risk 23. A thief can delete every record of the identity

A thief who opens a signing session on a device can delete every record of the identity in every pod, including records that its other devices wrote, since any device of the identity may delete them (DR-17). The phone's fetch after writing stamps the deletions before the revocation, so they stay accepted, and every replica drops the content, so the user cannot repair them with ordinary records (DR-20).

For example, at 18:10 on Monday the thief deletes 3 years of Alice's records in the Tokyo, Ginger and Hiking pods, and Alice revokes the phone at 18:30. The tombstones remain, but no replica holds the text any more.

The recommended mitigation: a device keeps, without sharing it, the content of records that another device of its own identity deleted, for 7 days of its witness time, and after a revocation it offers to write that content again as new records.

### Risk 24. A user may disown her most recent records

A user may disown her most recent records: those that her device wrote since its last stamp. With a modified app that never requests stamps, or with witnesses of her own that refuse them, these are at most 7 days of records for each of her devices, counted on the members' witness time. She can disown those records at any later time, by revoking that device (DR-20).

### Risk 25. A user may delete the content of any of her records

A user may delete any of her records at any time, and every replica then drops its content, so a member can show that she signed a record and the digest of its content, but not what it said, unless the member kept a copy of the content (DR-17, DR-20).

For example, in November Alice deletes #437, "I'll pay the hotel deposit, 500 EUR". Bob's replica keeps the tombstone of #437 with its signature, and Bob can prove what it said only with a copy of the text that he kept himself.

### Risk 26. Members may disagree about a forked chain

A member with a modified app can fork her own chain in a pod. Each replica holds the first 2 branches that it accepts, and every branch that it holds is accepted (DR-22). A device that sees the forked chain for the first time, such as a newcomer's, may hold a different pair of branches than other members do. So the members may disagree about that member's forked records.

### Risk 27. A recovered device can take an out-of-date copy of a pod

A member or a former member may offer a recovered device a copy of a pod that ends before the identity's leave or removal. Such a copy passes the check of DR-41, since every membership act in it is genuine. The recovered device then takes a pod that its identity has left. What it writes there reaches only that offerer, because no honest member offers a pod that the identity is not a member of (DR-41).

For example, Alice left the Hiking pod with her leave A70. After Alice recovers, Mallory offers her new phone the Hiking membership store up to A69. The phone shows Alice as a member, and what Alice writes in Hiking goes to Mallory alone.

Likewise, a former member can offer a pod that the identity is still in, with a copy that ends before his own removal. The recovered device then sends him what it writes there, until a current member's device reaches it (DR-41).

For example, Mallory was removed from "Family" with the act F80, and he offers Alice's new phone the "Family" membership store up to F79. The phone keeps the pod, and what Alice writes in "Family" goes to Mallory until Bob's phone offers the pod too.

### Risk 28. A pod with no other member is lost with the last device

A pod that has no other member and no replica at the Tellipod backup service is lost with the identity's last device, unless a backup of the device holds it (DR-41).

### Risk 29. A dishonest owner can reject a removed member's later records

An owner who removes a member lists the newest record of the member's devices that the owner holds, and nobody can check that list (DR-40). A dishonest owner lists an older record. The member's later records are then rejected everywhere, even at devices that hold them.

### Risk 30. The operator can restore every enclave and guess a PIN without limit

An operator can stop every enclave of the service and restart them all from stored data that he saved earlier. That sets the count of wrong PINs back everywhere at once. So he can try a chosen user's PIN 9 times, restore, and try again without limit. The email notices of wrong PINs go out through his own mail servers, so he can hold them back (DR-31, DR-32).

For example, a compelled Tellipod saves the stored data of its 5 enclaves, tries 9 of Alice's PINs, restores all 5 and repeats. The most common PINs fall within a few rounds, and all 1,000,000 within about 111,112 rounds. After that, Tellipod holds Alice's recovery key and the co-signer's signature.

### Risk 31. The operator can erase every enrolment

Tellipod, or whoever breaks into the storage of its enclaves, can erase every user's enrolment at once. It takes over no identity, but every user loses the recovery service and the Tellipod co-signer until she enrols again, and a user who has neither a paper sheet nor a second device can then rotate no more (DR-26, DR-32).

For example, after such an erasure, Carol, who has one phone and the co-signer, can no longer link a new phone or revoke a stolen one. Her app learns of the erasure at its next signing session, from the refusal "no such enrolment".

### Risk 32. The witnesses can match the moments at which users write

A device fetches its own KEL right after it writes, and the witnesses see the time and the network address of every fetch (DR-15, DR-33). Whoever runs the witnesses, Tellipod for a default user, can therefore match the moments at which users write, and so guess who writes to whom.

For example, over many evenings Alice's device fetches at 21:14:05 and Bob's at 21:14:41, again and again, which suggests that they are writing to each other.

Proposed mitigations: delay the fetch after writing by a random few minutes, so that the witnesses see only a window, at the cost of a slightly longer tail of records that a rollback can lose (DR-22) and that wait for a stamp; or delay it to the end of the signing session, which blurs more and costs more of the same.

## Open and deferred questions

### A thief's withheld records can win over the identity's repairs

**Problem.** A thief who holds a device with an open signing session writes records with timestamps in the future, and the device's stamp covers them before the revocation. The thief holds the records back. He releases them after the user has repaired the pod, either through a member who works with the thief or before the members learn of the revocation. A stamp from before the revocation covers the records, so they are accepted (DR-20, Risk 9). Where the pod's data keeps, for each field, the record with the newest timestamp, the thief's records also win over the repairs.

**Example.** On Monday, the thief writes "budget: 5,000 EUR" in the Tokyo pod on Alice's stolen phone, dated next month, and the phone's stamp covers it. On Tuesday, Alice revokes the phone and sets the budget back to 500 EUR. On Wednesday, a member who works with the thief releases the record. Bob's phone accepts it, and since its timestamp is the newer one, the budget reads 5,000 EUR.

**What is specific to this design.** Any member can date a record far in the future and win every comparison by timestamp. That question belongs to the specification of the pod's data. What is specific to this design is that a repair made after a revocation should win over the revoked device's records.

**Options.**

- Each record's signed body names the position and the digest of the latest event of the identity's KEL that its device holds. A record of a device that was revoked at some position never wins a conflict against a record of the same identity that names that position or a later one. Every other conflict is decided as before. A record cannot name an event that did not exist yet, so a record that names the revocation was written after it, whatever its timestamp says. The cost is about 40 bytes for each record, all of which stay in its tombstone. Ordering every record by the position that it names would be simpler. But then a laptop that was offline since before a linking would lose its newer edits to the phone's older ones.
- A repair names the records that it overrides. This does not help against records that the thief held back, since the user cannot name records that she has not seen.
- The risk is accepted as part of a thief's records becoming the identity's (Risk 9). A record dated many years ahead can then never be overridden by a timestamp.

**Leaning.** The first option, with the general problem of future timestamps passed to the specification of the pod's data.

### Breaking one enclave, or moving its data to hostile code, exposes every default user

**Problem.** One service, in an enclave, holds every default user's sealed secret, with its recovery key, and checks the PIN (DR-26, DR-31). Splitting the sealed secret across enclaves of different chip vendors is only a desirable enhancement there. Someone may extract the key that seals the enclave's stored data, as attacks published in 2025 did for Intel and AMD enclaves. That attacker decrypts the stored data for every default user. The attacker then tries all 1,000,000 PINs of each user offline, where the limit of 10 wrong PINs does not apply, and obtains every default user's recovery key, which carries weight 1. Separately, stored data is sealed so that new versions of the enclave's code can read it. If the operator can authorize a new version, a bribed or compelled operator can publish a version that hands the data out. The apps accept that version as long as it is a public, reproducible build.

**Example.** An attacker with physical access to one of Tellipod's servers extracts the sealing key of its enclave. Within days, the attacker holds the recovery keys of the default users whose PINs fell first, and uses each one to rotate that user's identity to keys of the attacker's own.

**Options.**

- Split the secret and pin the code. Each recovery key is encrypted under a key made of 2 shares, one in an Intel enclave and one in an AMD enclave, at 2 different cloud providers. Each enclave checks the PIN and releases its share only on a correct PIN, and both keep the count of wrong PINs. Stored data is sealed to the exact code. It moves to a new version only after that version's build hash has stood in a public append-only log for 30 days. The apps refuse an enclave whose code has not stood in the log that long. Breaking one vendor's enclave then yields half a key, and a hostile version is visible for 30 days before it can read anything. The costs are enclaves of 2 vendors at 2 providers, 2 round trips for each PIN check, a count of wrong PINs kept consistent across both enclaves, and 30 days before an urgent fix to the enclave's code takes effect.
- Pin the code only. This stops a hostile version, but one break still exposes everyone.
- Keep the split optional, and state both risks among the accepted risks (DR-42).

**Leaning.** The first option. This is the one place where a single technical break compromises every default user at once.

### Devices without hardware for their keys

**Problem.** Some devices have no hardware that can hold a key: an old PC, a computer whose TPM the app cannot reach, or a virtual machine, whose virtual TPM counts as no hardware (DR-2). On such a device, its key in the identity's key set and its record key would be files. Whoever copies the files gets the keys without the device and without the user's presence. The files can be copied from a backup or a stolen disk, or through malware that reads files. The device's key in the identity's key set carries 1/2, or 1 when the device is the identity's sole device (DR-10), and its record key signs records.

**Example.** Bob has a phone and a Linux workstation with no TPM. A burglar copies the workstation's key files from its disk. He signs records as the workstation until Bob revokes it. He also holds 1/2 of the identity's weight, enough to rotate with any second party that he gets to sign. If the workstation were Bob's only device, its key would carry 1, and the copied files alone would own the identity.

**Options.**

- Such a device is an entry of the role statement with a record key and no slot in the identity's key set. Its record key is kept out of backups like the iroh endpoint secret (DR-7), and it writes records. It never signs a rotation, never acts as second party, and cannot be a sole device. A copied file then signs records until the device is revoked, and it cannot touch the identity.
- Such a device holds a key in the identity's key set like any device, with its files kept out of backups, and the risk is accepted. A copied file then acts as a stolen device that needs no unlocking, and as a sole device it owns the identity.
- The key files are encrypted under a passphrase that the user types for each signature. A secret as short as a PIN falls to offline guessing once the file is copied. A long passphrase costs the user at every rotation and every signing session.

**Preliminary decision.** Such devices are not supported. A device can be linked only if it holds its keys in hardware (DR-2).

### Members may not reach a recovered device

**Problem.** In DR-41, a member's device that sees a recovery rotation dials the recovered device and offers it the pod. Neither step works in the design as it stands. A member's device fetches another identity's KEL when its copy is not fresh and it syncs with a device of that identity, or when a key state statement ahead of its copy reaches it (DR-15). After a user loses every device, none of her devices is online, so her co-members never fetch her KEL and never see the recovery. Even with the KEL, a member's device learns the new device's record key from the role statement, but not its iroh endpoint key. An endpoint binding travels only among pod peers and never to the witnesses (DR-7), and the recovered device is in no pod yet.

**Example.** Alice recovers with her paper at 10:00. Bob's phone last synced with Alice's old phone on Monday. Nothing makes it fetch Alice's KEL, and if it did, it would have no endpoint to dial.

**Options.**

- To notice the recovery, a member's device fetches the KEL of each member of its pods if it has reached none of that member's devices in the last 24 hours of its witness time. It does so with the queries of DR-15. This also spreads revocations to members who have been quiet, at the cost of a few queries a day for silent members.
- To reach the recovered device, a mailbox at the witnesses. A member's device leaves at the identity's witnesses an offer encrypted to the record key that the recovery rotation lists. The offer holds the member's endpoint and the pod's ticket. The recovered device collects its messages from its witnesses and dials the member. The witnesses learn that a device of the identity received a few sealed messages. From the senders' network addresses, they also learn which devices sent them. The cost is a new duty for witnesses: holding sealed messages for a device for a while, such as 30 days.
- To reach the recovered device, the witnesses hold its endpoint binding. The recovered device hands its binding to the witnesses together with the recovery rotation, and members fetch it with the KEL. This is the simplest option. But it publishes the tie between the device's endpoint and the identity's AID. So anyone who sees that endpoint on the network, Tellipod included, learns which identity is behind that device's traffic.
- No automatic offer. After a recovery, members invite the user again by hand. This drops most of DR-41, and a user in many pods has to ask each of them.

**Leaning.** Fetching the KEL of silent members, together with the mailbox at the witnesses.

### Route not taken: keeping the unstamped tail of a forked device's old branch

**Problem.** After a rollback, a device forks, and before its replacement it stamps only the records that it holds (DR-20, DR-22). The members accepted the records of its old branch that it wrote after both the backup and its last own fetch before the restore. But the rollback erased those records from the device, so no stamp covers them, and they lose acceptance at the revocation.

**Example.** On Thursday, Bob's laptop writes #321 to #340 in the Tokyo pod on a local network without internet access, so its last stamp covers up to #320. On Friday, Bob restores Wednesday's backup, and on a plane the laptop writes a new #301. When Alice's phone detects the fork, the laptop replaces its entry and stamps the new #301, but not #321 to #340, which only Alice's and Carol's phones hold. After the replacement, #321 to #340 are no longer accepted.

**The route not taken.** The fork notice also carries the newest record that the sender holds on each branch, as signed body and signature without content. The forked device checks that each of these records carries its own signature and names the pod, and it keeps up to 8 of them for each pod. Its stamp before the replacement names them, as well as its own newest records. A leaf may then name a record that the requesting device knows only from a notice. A replica keeps a stamp's path for a record that it does not hold, within the identity's 1 MB of headers. A device with siblings replaces its own entry, signed by itself and a sibling or the external co-signer, so that its stamp comes first. In the example, Alice's notice names #340, and the laptop's stamp covers it. Once the laptop syncs under its new device id and publishes the stamp, #321 to #340 are accepted again. Between the replacement and that publication, members see them as not accepted.

**Why it was not taken.** To keep the records of one session of an honest rollback, it adds 4 things: a rule for the fork notice, leaves that name records that the device does not hold, a storage bound, and a rule for devices with siblings. A variant in which the forked device answers the notice with a stamp at once needs the peer to wait for the answer, and a device cannot be trusted to keep such a wait. A variant in which the peer requests the stamp needs a member's device to contact another identity's witnesses.

**When to reconsider.** If rollbacks of desktop devices turn out to be common, or if users report records that disappeared after a fork.

### Anyone who knows a user's email address can block her recovery

**Problem.** An email code works once, and the next request voids it (DR-26). Anyone who knows the user's email address can therefore request codes for it again and again, and each request voids the code that the user is about to type. A limit on requests for each address would block the user in the same way. If the service also answers differently for an address that has no enrolment, it shows who uses Tellipod.

**Example.** Alice recovers on a new phone. Mallory, who knows her address, requests a code for it every 10 seconds, so every code that Alice receives is void by the time she types it.

**Proposed solution.** Each code belongs to the session of the channel into the enclave that requested it, and only a new request in that same session voids it, so another party's requests cannot void the user's code. A code allows few tries, such as 3, and is then void. The service answers in the same way whether or not an address has an enrolment.

### What the enclave does when asked to sign again with a co-signer's key

**Problem.** Each key of the Tellipod co-signer signs one rotation (DR-30), but nothing says how the enclave keeps to that, or what it does when the same request comes again. If the reply to a signing is lost, a refusal on the retry leaves the device stuck. If the enclave signs a second, different event with a key that it has already used, it helps make 2 events at one position, which only the witnesses' rule of the first event seen then stops (DR-15).

**Example.** The enclave signs rotation 9 of Alice's KEL with the co-signer's key C5, and the reply is lost on the way to her phone. The phone asks again. Separately, someone who knows Alice's PIN asks the enclave to sign another rotation at position 9 with C5.

**Proposed solution.** For each of its keys, the enclave remembers the digest of the event that it signed with that key. A request to sign the same event again gets the same signature, so a retry after a lost reply works. A request to sign a different event with a key that the enclave has already used is refused. This is a little state for each key and needs no KEL. A cancel of a pending rotation, an open question below, could then not be signed with the co-signer's key that signed the rotation it cancels.

### Cancelling a rotation that was signed but never accepted

**Problem.** A rotation that its parties have signed stays valid at its position until another rotation is accepted there, and its signer resends it on a retry (DR-16). So a linking or a revocation that the user gave up on can still take effect much later. A cancel cannot simply be a rotation at the same position that changes nothing. Such a rotation is checked against the same committed keys as the pending one, so devices that signed both would use one key twice, against KERI's rule of keys used once, which the identity's KEL declares (DR-8). The co-signer's key that signed the pending rotation cannot sign again, so a user with one device and the Tellipod co-signer could not cancel at all. A cancel of a recovery rotation would leave the typed paper key committed, against the rule that every use of the paper ends with a new sheet (DR-27). And the cancel must commit new keys for its own signers, so it does change something.

**Example.** Alice's phone and the co-signer sign rotation 9, which links a tablet, but the witnesses are unreachable, and Alice gives the tablet to her son. A week later the phone's retry reaches the witnesses, and her son's tablet becomes a device of Alice's identity.

**Possible solutions.**

- Only parties that did not sign the pending rotation can cancel it. In the example, Alice's laptop and desktop sign the cancel at position 9. The cancel commits new next keys for its signers, and it replaces any recovery key that the pending rotation revealed. Where no such parties exist, as for a user with one device and the co-signer, the app cannot cancel. It tells the user, and if the pending rotation takes effect later, she revokes what it linked.
- No cancel at all. The app lists pending rotations and warns the user. If one takes effect later, she undoes it with an ordinary rotation, such as revoking the tablet that her son now holds.

### A backup of a device restores no identity

**Problem.** DR-25 lets a user rely on something other than the recovery service or the paper sheet, and DR-41 and Risk 28 count a copy in a backup of the device as a way to keep a pod. But a device's keys live in its hardware and are never exported (DR-2), the secret of its endpoint key is kept out of backups (DR-7), and its replicas are kept out of backups or encrypted under the hardware wrapping key, which never leaves the device. A backup therefore holds no key of the identity. Restored onto a new device, it brings back neither the identity nor the pod data. Restored onto the same hardware, it can bring back encrypted replicas, but not the endpoint secret, so the device is linked again anyway.

**Example.** Dave chooses neither the recovery service nor a paper sheet, and keeps encrypted backups of his phone with a tool of his own. His phone is lost. He restores the latest backup onto a new phone, and the new phone holds no key of his identity and cannot read the replicas, so his identity is gone, while his pods' data survives with the other members.

**Options.**

- State plainly that a backup of a device restores no identity, and pod data only onto the same hardware. The ways back are then the recovery service, the paper sheet and the user's other devices, and DR-25, DR-41 and Risk 28 say so.
- Add a third kind of recovery key that can be exported: an encrypted copy of a software recovery key that the user keeps where she likes, such as in her own backups. It carries weight 1, like the paper's key, and it is exposed wherever it is kept.

### Records disowned long after the 7-day window

**Problem.** The 7-day window of DR-20 stops members from accepting a device's new records once its records have waited 7 days for a stamp. It leaves 2 gaps. The window is counted for each device, so a member who links a new device starts a new window. And records that members have already accepted stay accepted only until the member revokes that device, which she can do at any time she picks, so every record of that device that no stamp covers then loses acceptance, even months later.

**Example.** From 1 to 7 March, Mallory's laptop, with a modified app that never requests stamps, writes #1 to #60 in the Tokyo pod, including #12, "I'll pay the hotel deposit, 500 EUR". From 8 March, the members accept nothing more from the laptop, so she links a tablet and carries on. In November she revokes the laptop, and #12 is rejected everywhere, 8 months after she wrote it.

**Options.**

- One window for each identity and pod, which decides the records' status when it closes. A new device does not start a new window. When the window closes, members treat that identity's records in the pod that no stamp covers as a revocation would: not accepted until a stamp covers them. Disowning is then possible only within the 7 days. The cost falls on an honest writer cut off from her witnesses for longer than 7 days, whose records show as not accepted until her first stamp restores them, which is the outage that Risk 21 already treats as force majeure.
- Keep the window as it is, as Risk 24 states: at most 7 days of records for each device, which the member can disown later by revoking that device.

### How the label of an enrolment is read before the PIN

**Problem.** A user with several identities under one email address picks the enrolment to recover by its label, before she types her PIN (DR-26). The label is encrypted, but it cannot be encrypted under the key derived from the PIN, since the PIN comes after the choice, and nothing says under which key it is.

**Example.** "Alice" and "Alice-work" are enrolled under one address. After the email check, Alice's new phone has to show her 2 labels to pick from, before it asks for any PIN.

**Proposed solution.** The label is sealed in the enclave like the rest of the enrolment, but not encrypted under the PIN. After the email check, the enclave returns the labels of that address's enrolments over the channel that ends inside it, so the operator never sees them. The app suggests a label that does not identify the identity, such as a colour and a word that the user picks, since anyone who passes the email check sees the labels.

### Witness time at a device's first contact with the enclave

**Problem.** The app checks the dates of the enclave's attestation and of the vendor's list of withdrawn firmware against witness time (DR-31). A device that hosts no identity yet has no witness time: a phone that creates an identity, or that recovers through the service and learns the identity's AID and witnesses only from the sealed secret that the enclave releases. Such a device takes its first witness time from what the linking or the recovery passes to it (DR-15), but it contacts the enclave before that.

**Example.** Alice recovers on a new phone through the service. Before her phone has any witness time, a hostile network serves it a vendor's list of withdrawn firmware that is 2 years old, in which a broken enclave still looks valid, and her PIN goes to that enclave.

**Proposed solution.** A device that hosts no identity takes its first witness time from a majority of the witnesses that are built into the app, by a fetch with a root of its own, before it contacts the enclave.

### A notice by email at every co-signature

**Problem.** Malware inside the app that has captured the user's PIN can have the Tellipod co-signer sign a rotation that the user never sees, such as one that links the attacker's device (Risk 2). Nothing outside the device tells her.

**Example.** Malware on Alice's phone records her PIN, then has the phone and the co-signer link a laptop of the attacker's while Alice is asleep.

**Proposed solution.** The co-signer, which reads every rotation that it signs (DR-33), has the service send the enrolled email address a notice at every co-signature, naming the act, such as "Your identity linked a new device at 03:12". The user who did not do it then knows to revoke.

### A word for a device in the role statement

**Problem.** The role statement lists each device as an "entry", which pairs a slot of the key set with a record key (DR-6). The word "entry" is a platform term with another meaning, which the platform's rule of one word for each concept forbids.

**Example.** "The rotation drops the laptop's entry" can be misread as dropping a stored item of a pod.

**Proposed solution.** Choose another word, such as "device listing", and use it throughout this document.

### Other deferred topics

- **The linking ceremony** — how a new device and an existing device find each other, how each one confirms the other, and what happens when the ceremony is interrupted. It also sets the screens and the format of the code that a second party types (DR-29), and how the signers check the new device's endpoint binding before they list its record key (DR-6).
- **Pod invite and join via QR code** — how a newcomer first obtains a member's AID and KEL, and what an invite carries.
- **How a revocation reaches other members' devices** — how peers pass new KEL events on, and how fast. The freshness bound of 24 hours of witness time, with its fallback to the witnesses, is already decided (DR-15).
- **Planned witness rotation** — how an operator of witnesses announces that it shuts down or retires witnesses, the notice period, how the app proposes new witnesses and changes the witnesses of every identity on a device, and what a self-hosted operator commits to (DR-16).
- **Moving to a new identity when the witnesses disappear** — how the app automates the creation of the new identity and the membership acts that hand each pod over to it, before the members' 7-day windows close (DR-16, DR-20, Risk 19).
- **Tools and Services** — including the restricted identity that a Service uses. Tools have no identity of their own.
- **Organizations** as identities.
- **The Tellipod backup service** — an optional service that stores end-to-end encrypted replicas of pods, and through which a recovered identity also gets its pods back (DR-41).
- **A passive co-signer** — a co-signer key kept in an encrypted file, in storage that the user picks. A related option is recovery through delegation: a recovery AID delegates the identity's AID, signs approvals with the passive co-signer's key, and holds the offline recovery key as its next key.
- **Apache 2.0 KERI building blocks as dependencies** — whether the implementation may depend on cesride for the encoding, or whether everything is written from scratch. The licenses of cesride and parside still have to be checked.
- **The membership specification** — the format of membership acts, what owners may do, the merge rule for concurrent acts of several owners, and the lifecycle of a pod's membership store. It records each join in a membership act that a device of the joining identity signs, and binds the pod id to the pod's created event. A recovered device can then tell its own pods from forged ones (DR-41). It also has to decide whether a removal can be corrected when it lists fewer records of the removed member than a device of the remover's identity held. For example, Alice's laptop holds Bob's record #40, and her phone, which lags behind, removes Bob while it holds only #35. If the removal is corrected, Bob's records #36 to #40 are accepted. It also defines which membership acts a removed member's devices receive when owners act concurrently, since "up to and including the removal" (DR-40) has no single order then: for example, Alice's laptop removes Bob while Dave's offline phone adds Erin, and the specification says whether Bob's devices receive the addition of Erin. One candidate: each membership act names the acts that its author's device held, and a removed device receives the removal and every act in its history. Its merge rule also settles a removal and a join written concurrently. For example, Bob left the Tokyo pod, and Dave invited him again. While Bob's phone writes his join, Alice's laptop, which holds neither the invite nor the join, removes Bob. A join names neither the removal nor the leave that it follows (DR-40), so the specification also says how a device tells that a join came after them.
