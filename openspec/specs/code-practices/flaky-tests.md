# Flaky tests: reproduce with statistics, fix the mechanism

A test that fails rarely is not "unstable" — it is a test that has caught a rare defect. In this codebase the scenario tests drive real networking (endpoints, gossip, sync actors), so a race that strikes once in 100 runs is a product race that will strike a user's device pair once in 100 linkings. The discipline below exists because rare failures cannot be reasoned about from one observation: they demand statistics before the fix and statistics after it.

## Rules

1. **Reproduce before fixing.** Capture the exact failing assertion (test name plus panic message) on the unfixed code first. The signature is what tells you later whether a candidate fix changed anything, and whether a new failure is the same defect or a different one. A fix authored without a reproduced baseline cannot be verified at all.
2. **Expect reproduction to take hundreds of runs, not a handful.** A real race can hide behind long green streaks. Plan the hunt as a counted loop with a per-iteration verdict line, sized in the hundreds, and keep the full output of every failure. Five green runs after a change mean nothing.
3. **Size the verdict with the rule of three.** N consecutive green runs bound the failure rate at roughly 3/N with 95% confidence. Declaring "fixed" therefore needs N such that 3/N sits a few times below the baseline rate you measured — against a defect seen once in 60 runs, 200 consecutive green runs merely reach parity with the baseline bound; 400–600 give an actual margin. Runs of the same configuration made under the same harness pool. Anything less is "did not reproduce today".
4. **Fix the mechanism, not the test.** A timing flake in a scenario test is a product race until proven otherwise. Find the stranded state in the code (a session slot that stays `Running` forever, a broadcast fired before the swarm exists) and fix it there. Raising the test timeout, adding sleeps, or retrying in the test hides the defect from the suite and hands it to production. Reject any fix whose whole content is "wait longer".
5. **Minimize by measuring, hunk by hunk.** When a candidate fix has several independent pieces, apply them separately (working tree is enough — no commits) and stress each configuration with the same harness. Keep only the pieces that change the outcome; the rest is cargo-culted robustness that obscures what the defect was.
6. **Pin the mechanism with a deterministic test.** Once the race is understood, encode it as a unit test of the state machine that fails in one run on the unfixed code — the scenario suite then guards the integration, not the probability. A defect that only a 1-in-60 stress run can detect will regress unnoticed; a deterministic test will not let it.
7. **Diagnose in isolation.** Hunt flakiness on a tree that contains only the code under suspicion — not through an unrelated feature branch. If the flake was first seen while feature work was in flight, cherry-pick the suspect fix onto the clean base and reproduce there; never interleave "make the feature work" with "make the tests stop flaking", or each investigation poisons the other.

## How

- Loop harness: a shell loop around `cargo test` (or the built test binary), one `ok`/`FAIL` line with duration per iteration, full output saved only for failing iterations. Restrict the loop to the affected test binaries to raise iterations per minute — the failure cost is dominated by the liveness timeout burning on the wedged wait.
- Load is not a multiplier by default: in the July 2026 device-linking hunt, 3 parallel copies of each test binary did not raise the per-act failure rate over plain sequential runs — the race lived in millisecond-scale actor scheduling, not in CPU starvation. Measure before assuming parallel stress buys reproduction speed.
- Count acts, not only runs: if one run exercises the racy path 9 times, 100 runs is 900 chances. Rates per act compare configurations that exercise the path a different number of times per run.
- Keep the harness: the loop script and its logs are the evidence appendix of the fix, and the tool for the next hunt.

## Worked example (device linking, July 2026)

The `device_linking_bootstrap` scenario failed with `phone did not see the newly linked device`: on the unfixed tree, once in 64 plain full-suite runs plus once in 15 loaded rounds of 3 parallel copies — 2 failures in about 170 bootstrap linking acts, roughly 1.2% per act, with a 60-second liveness wait burning on every failure. The mechanism composed two engine facts: the one-shot gossip broadcast of the registration write fires into a not-yet-formed neighborhood and is lost, and the rescue resync that should redeliver it can be silently dropped — a dial rejected by the remote as already-syncing left the (namespace, peer) session slot `Running` forever, eating every later trigger.

Hunk-by-hunk measurement then inverted the initial guess about which piece mattered. The engine-state fix alone (clear the slot on the remote abort — `abort_connect`) left the failure rate unchanged: 2 failures in 140 runs, same signature — clearing the slot does not redo the lost delivery, and nothing else retriggers it. Adding the registration-confirmation loop in `link_device` (re-request a sync every 500 milliseconds until one session that started after the write completes) eliminated the failures: 0 in 470 runs plus 10 loaded rounds. The loop is the retry driver; the engine fix is still required so a wedged slot cannot starve that driver until its deadline — a permanent-wedge defect too rare to discriminate statistically, so it is pinned by 3 deterministic unit tests of the sync-state machine instead. The third candidate piece, a blanket 20-second per-session timeout, was not needed to eliminate the observed failures and stayed out of the minimal set (its separate justification — dials to unreachable addresses — is a product concern, not a test-observed one). Cost accounting closed the loop: the confirmation wait added about 0.8 seconds per linking act, visible as the stress iteration average moving from 13.1 to 18.8 seconds.
