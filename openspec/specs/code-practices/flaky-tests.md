# Flaky tests: reproduce with statistics, fix the mechanism

A test that fails rarely is not "unstable" — it has caught a rare defect. Scenario tests drive real networking (endpoints, gossip, sync actors), so a race that strikes once in 100 runs strikes a user's device pair once in 100 acts. Rare failures cannot be reasoned about from one observation: they demand statistics before the fix and statistics after it.

## Rules

1. **Reproduce before fixing.** Capture the signature on the unfixed code first: test name, panic message, and which waits passed before the one that starved. A fix authored without a reproduced baseline cannot be verified. One carve-out: hardening justified structurally — closing a gap known by inspection, not by the observed failure — may land without a baseline, but it must not claim the observed flake, which stays open.
2. **Verdicts are statistics.** Reproduction takes hundreds of runs, not a handful. N consecutive green runs bound the failure rate at roughly 3/N with 95% confidence; size N so that bound sits a few times below the measured baseline rate. Anything less is "did not reproduce today", not "fixed".
3. **A verdict binds to its harness pool.** A pool is the whole measurement configuration: which binaries run, in what order, under what competing load, on what machine state. Changing any of it opens a new pool — green streaks from the old pool are not controls for the new one. Compare arms only within one pool, and let exactly one variable differ between arms; an incomplete comparison grid invites confident misattribution.
4. **Localize the starved step before hypothesizing.** Map the failure to the exact wait that starved, and enumerate what could have delivered it. Two failures under one test name can be two different defects; the passed-vs-starved split is what tells them apart.
5. **Interrogate the machine before the code.** Timestamp the failure (the failure log's mtime), then spend minutes on cheap forensics around that instant: sleep/wake events, network-stack events, durations of neighboring iterations, competing processes. Each check kills or confirms a whole hypothesis branch for free.
6. **Fix the mechanism, not the test.** A timing flake in a scenario test is a product race until proven otherwise. Raising timeouts, adding sleeps, or retrying in the test hides the defect from the suite and hands it to production. When the mechanism is best-effort delivery with no rescue trigger, the fix is a guarantee layer with bounded staleness — a retry driver, a periodic reconcile — not a stretched wait.
7. **Minimize by measuring, hunk by hunk.** Apply candidate pieces separately and stress each configuration in the same pool. Keep only the pieces that change the outcome; the rest is cargo-culted robustness that obscures what the defect was.
8. **Pin the mechanism deterministically.** Once the race is understood, encode it as a unit test that fails in one run on the unfixed code. Where the code offers no place to attach a deterministic pin, say so explicitly and name the stress configuration that guards it instead — an unstated statistical guard is a regression waiting to pass review.
9. **Diagnose the suspect delta in isolation.** Never interleave "make the feature work" with "make the tests stop flaking" — cherry-pick the suspect onto a clean base and reproduce there. When the flake is only observable through new feature tests, the isolation lives in the pool and the arms instead.

## How

- Runner: `cargo nextest run` (process-per-test; `--test-threads` defaults to CPU cores). `just stress` forwards all its arguments to it. Repeat a suspect with `--stress-count N` (or `--stress-duration`); narrow with `-E 'binary(<name>)'` or `-p <crate>`; handle a known-flaky test with `--retries N` plus `--flaky-result fail` (which still fails the run, but records the retry). When hunting, narrow to the affected binary: failure cost is dominated by the liveness timeout burning on the starved wait.
- Broad and fast before deep and narrow. When a pass has both a wide sweep (the whole suite once) and a long `--stress-count` pass on the suspects, run the wide sweep first: a failure in the deep loop stops everything and sends the work off to a fix, and a stop must never be what cancels the cheap full-tree picture. The deep loop loses nothing by going second — its verdict is the last thing needed anyway.
- Count acts, not only runs: one run may exercise the racy path many times; rates per act compare configurations that exercise it differently.
- Concurrent execution saves wall-clock but is not automatically a reproduction multiplier. nextest runs tests process-per-test up to CPU cores, so independent tests overlap — the suite's fixed-sleep negatives especially, cutting the full run materially. That is throughput, not reproduction rate; whether exercising the racy path under load changes its per-act failure rate is a separate question — measure before assuming. One environment caveat: on macOS a per-process cost in iroh node startup (measured at about 0.4 seconds; cause not pinned down, though the host firewall is ruled out) serializes across processes, so parallel _repeats_ of a node-spawning test gain almost nothing locally — `--stress-count` scales roughly linearly with count. `just hammer` sidesteps this by running a whole test binary per process (one startup cost amortized across the binary's tests) rather than per test.
- Monitor a long series instead of just waiting on it. A rule-2-sized series runs for hours, so run a watcher beside it that reports one line per pool every 2 minutes — "broad pool: 47/100 iterations, 0 failures" — read from the runner's log (nextest prints a `Stress test iteration N/M` line per iteration and a `FAIL` line per failed test). The line answers the two questions worth asking mid-run — how far along, and has anything failed — and a run that stopped advancing is noticed within minutes rather than at the end of its time budget.
- Keep the run's output: nextest's summary (and JUnit, via a profile) is the evidence appendix of the fix and the tool for the next hunt.

## Precedents

_The rates below were measured under an earlier homegrown harness (a shell loop over the test binaries, with the heavy binaries serialized one-test-at-a-time); the runner is now `cargo nextest run` (process-per-test) — a different pool per rule 3._

- **Device linking (July 2026).** `device_linking_bootstrap` failed at about 1.2% per act. Mechanism: the one-shot gossip broadcast of the registration write fired into a not-yet-formed neighborhood and was lost, and the rescue resync was silently dropped by a session slot wedged `Running` forever. Hunk-wise measurement inverted the initial guess: the engine-state fix alone changed nothing (2 failures in 140 runs), the confirmation loop in `link_device` eliminated the failures (0 in 470); the wedge fix stayed as prevention, pinned by 3 deterministic sync-state unit tests; a blanket session timeout was measured unnecessary and stayed out. The confirmation wait's cost was measured too: about 0.8 seconds per linking act. Closed out by direct-device-linking (July 2026): the confirmation loop is gone with `link_device` itself, superseded structurally rather than by another measurement — the inviter now writes the newcomer's device record into its own replica before replying (ADR-0012), so the cross-node delivery the loop waited on is out of the linking critical path and the race has no site left. The wedge fix and its unit tests remain.
- **Post-linking convergence (July 2026).** A connection recorded after linking starved for the full liveness budget at 2.5% per run (5 failures in 199): the write's broadcast was lost and every rescue trigger rides the same gossip, so no session ever started — localized by the passed-vs-starved split (catch-up passed, live update starved) after machine forensics cleared the environment. Fixed by a periodic reconcile pass over every open doc (bounded staleness independent of gossip health) — 0 failures in 100 full-roster iterations, with the rule-2-sized series still owed; the session-timeout arm measured 2.1% against the 2.9% no-timeout arm — statistically indistinguishable, so the timeout is not this defect's fix. An earlier 0-in-248 streak from a different roster was discarded as a control per rule 3.
